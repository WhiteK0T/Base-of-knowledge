# 🐧 strace — трассировка системных вызовов (диагностика зависаний и 100% CPU)

**strace** показывает, какие **системные вызовы** (syscalls) и сигналы делает процесс: имя вызова, аргументы, результат, а с ключами — время и частоту. Классический сценарий (из поста): процесс **жрёт CPU на 100%**, `top` показывает только PID — цепляемся к нему по PID и смотрим, на чём он «сидит».

```bash
strace -cp <PID>     # сводная статистика syscalls живого процесса (Ctrl-C — отцепиться и вывести итог)
```

> [!info] Как читать сводку `-c`
> Колонки: **% time** (доля времени в этом вызове), **seconds**, **usecs/call**, **calls** (сколько раз вызван), **errors**.
> - Много времени в **`futex`** → блокировки/контеншн на мьютексе (в Java — `synchronized`/`Lock`, иногда safepoints JVM) или дедлок.
> - **`read`/`write`/`pread`/`pwrite`** → упор в I/O: диск, **NFS**, сокет. Проверяй хранилище.
> - **`connect`/`sendto`/`recvfrom`** → ждём ответа другого сервиса (БД, API).
> - **`epoll_wait`/`poll`/`select`** → ожидание событий (для event-loop это может быть просто **простой**, а не работа — см. нюанс ниже).

## 🔧 Шпаргалка по ключам

| Команда | Что делает |
| :--- | :--- |
| `strace -cp <PID>` | только **статистика** syscalls (низкий вывод, но см. про оверхед) |
| `strace -p <PID>` | трассировка **в реальном времени** |
| `strace -p <PID> -e trace=network` | только сетевые вызовы (`connect`, `sendto`…) |
| `strace -p <PID> -e trace=file` | только файловые операции (`open`, `stat`…) |
| `strace -p <PID> -e trace=write` | конкретный вызов |
| `strace -p <PID> -T` | **время в каждом** вызове (`<0.000123>`) |
| `strace -p <PID> -tt` | абсолютные **таймстемпы** с микросекундами |
| `strace -fp <PID>` | трассировать **вместе с потоками/дочерними** (`-f`) |
| `strace -yp <PID>` | печатать **имена файлов/сокетов** для дескрипторов |
| `strace -p <PID> -o out.txt` | писать в файл (не мешать stdout процесса) |
| `strace -s 256 …` | увеличить длину печатаемых строк-аргументов (по умолчанию 32) |

## ⚠️ Что в посте не сказано — критично для диагностики CPU

> [!warning] strace видит ТОЛЬКО системные вызовы, а не userspace-CPU
> Если процесс жжёт CPU **в пользовательском коде** (горячий цикл, вычисления, регэкспы, крипта, **GC/JIT в Java**), то syscalls он почти **не делает** — и `strace -c` покажет **пусто/копейки**, хотя CPU в полке. strace хорош для **syscall-bound** проблем (I/O, сеть, блокировки), но для **CPU-bound в userspace** нужен **профайлер**: `perf top`/`perf record`, `bpftrace`, а для Java — `async-profiler`, `jstack`, `top -H`. **Пустой strace при 100% CPU — это диагноз: причина в userspace, копай профайлером.**

> [!caution] «% time» в `-c` — это НЕ время CPU, а время В вызове (включая ожидание)
> Блокирующий вызов (`futex`, `epoll_wait`, `read` с сети) висит в сводке с большим **% time**, даже если поток при этом **спит** и CPU не ест — это latency, а не загрузка. Поэтому «90% в futex» может значить, что поток **ждёт** лока (простой), а не «грузит ядро». Для CPU-нагрузки смотри скорее **высокую частоту (calls)** быстрых вызовов, либо (если syscalls мало) вывод выше — причина в userspace.

> [!danger] Оверхед: «-c оверхед минимальный» — вводит в заблуждение
> strace работает через **`ptrace`** и перехватывает **каждый** syscall с остановкой процесса — это может замедлить цель **в разы-десятки раз** и «подвесить» латентно-чувствительный сервис. Ключ `-c` **убирает вывод**, но **не убирает** ptrace-перехват — накладные расходы остаются. **На проде безопаснее eBPF-инструменты** с околонулевым оверхедом: `perf trace`, `bpftrace`, `bcc` (`funccount`, `syscount`, `biosnoop`). strace — для стенда/короткого точечного снятия, не для «повесить на боевой процесс надолго».

> [!note] Права: ptrace может быть заблокирован (Yama)
> Нужен тот же пользователь, что владеет процессом, либо root/`CAP_SYS_PTRACE`. На многих дистрибутивах **Yama** ограничивает трассировку: `sysctl kernel.yama.ptrace_scope` — если `1`, не прицепишься даже к своему не-дочернему процессу без sudo. Временно: `sudo sysctl kernel.yama.ptrace_scope=0` (осознанно, это ослабляет защиту).

## ☕ Если это Java-процесс (канал-то про Java)

Процесс на JVM в полке по CPU — частый кейс. Порядок:
1. **`top -H -p <PID>`** → найди **поток** (TID), который грузит CPU.
2. Переведи TID в hex: `printf '%x\n' <TID>`.
3. **`jstack <PID>`** (или `jcmd <PID> Thread.print`) → найди строку `nid=0x<hex>` — это и есть зависший/горячий стек.
4. Если виновата **сборка мусора** — стеки будут в GC-потоках; смотри GC-логи (`-Xlog:gc`), возможно утечка/недостаток heap.
5. **Контеншн на локах** (`futex` в strace) ↔ в `jstack` увидишь много `BLOCKED`/`WAITING` на одном мониторе.
6. Точный профиль горячих методов — **async-profiler** (`profiler.sh -d 30 -f flame.html <PID>`), flame graph.

Итог: **strace ловит I/O/сеть/лок-контеншн**, а **чистый CPU в байткоде/GC — только jstack/async-profiler**.

## 🖥️ Установка на системах владельца

| Система | Установка |
| :--- | :--- |
| **Gentoo** (основная) | `emerge dev-debug/strace` (профайлеры: `perf` из `dev-util/perf`, `bpftrace`) |
| **Debian / Ubuntu** | `sudo apt install strace` (eBPF: `bpfcc-tools`, `linux-perf`) |
| **Arch** | `sudo pacman -S strace` (`perf`, `bpf`/`bcc` для eBPF) |
| **Entware / RT-AX56U** | `opkg install strace` (**есть**, v6.18) — полезно для отладки прямо на роутере; `ltrace`/`perf` там обычно нет, так что strace — основной инструмент |

## 🧰 Чем дополнять strace

- **[lsof](lsof%20%E2%80%94%20%D0%BA%D1%82%D0%BE%20%D1%87%D1%82%D0%BE%20%D0%B8%20%D0%BA%D1%83%D0%B4%D0%B0%20%D0%BE%D1%82%D0%BA%D1%80%D1%8B%D0%BB%20%28%D0%BE%D1%82%D0%BA%D1%80%D1%8B%D1%82%D1%8B%D0%B5%20%D1%84%D0%B0%D0%B9%D0%BB%D1%8B%2C%20%D1%81%D0%BE%D0%BA%D0%B5%D1%82%D1%8B%2C%20%D0%BF%D0%BE%D1%80%D1%82%D1%8B%20%E2%80%94%20%D1%88%D0%BF%D0%B0%D1%80%D0%B3%D0%B0%D0%BB%D0%BA%D0%B0%29.md)** — какие файлы/сокеты открыл процесс (дополняет `-y`).
- **`ltrace`** — вызовы библиотек (не syscalls).
- **`perf top`/`perf record`** — где горит CPU в userspace (то, чего strace не покажет).
- **`bpftrace`/`bcc`** — низкооверхедная трассировка на eBPF (для прода).
- **`cat /proc/<PID>/stack`**, `wchan` в `ps -eo pid,wchan:32,comm` — где поток спит в ядре, без ptrace.
- **`gdb -p <PID>`** + `thread apply all bt` — снять стеки нативных потоков.
