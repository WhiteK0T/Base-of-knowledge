# 🎓 Jenkins — план изучения и использования

Практический маршрут: от «что такое задача и сборка» до пайплайнов, которые поднимают тестовые виртуалки, гоняют тесты и собирают скриншоты GUI. План рассчитан на два вида работы с одним сервером: **человек учится и пользуется Jenkins сам**, а **ИИ-агент (Claude Code) работает рядом** через тот же Jenkins, но с урезанными правами. Справочник по установке, синтаксису `Jenkinsfile`, агентам и JCasC — в основной заметке: [Jenkins — self-hosted CI/CD сервер](Jenkins%20%E2%80%94%20self-hosted%20CI-CD%20%D1%81%D0%B5%D1%80%D0%B2%D0%B5%D1%80%20%28Pipeline%20%D0%B8%20Jenkinsfile%2C%20%D0%B0%D0%B3%D0%B5%D0%BD%D1%82%D1%8B%2C%20%D0%BF%D0%BB%D0%B0%D0%B3%D0%B8%D0%BD%D1%8B%2C%20JCasC%3B%20%D1%83%D1%81%D1%82%D0%B0%D0%BD%D0%BE%D0%B2%D0%BA%D0%B0%20%D0%BD%D0%B0%20Gentoo%2C%20Debian%2C%20Arch%2C%20Docker%3B%20MCP%20%D0%B4%D0%BB%D1%8F%20Claude%29.md).

## Принцип: сначала руками, потом кодом

Типичная ошибка — сразу описать всё в Configuration as Code и Job DSL: сервер работает, но непонятно, *что* он делает. Поэтому:

1. **Сначала UI.** Каждую новую сущность (задача, параметр, агент, секрет) сначала создаём мышкой и смотрим, что получилось.
2. **Потом файл.** Ту же сущность переносим в код: `Jenkinsfile` в репозитории, затем JCasC/Job DSL.
3. **Код — в Git.** Конфигурация сервера и задачи живут в репозитории; руками в UI правим только то, что изучаем прямо сейчас.

Стартовая установка поэтому **минимальная**: JCasC задаёт только безопасность (пользователи, права, ноль исполнителей на контроллере) и плагины. Задач и агентов в ней нет — их создаём на этапах ниже.

**Учебный репозиторий:** [WhiteK0T/jenkins-sandbox](https://github.com/WhiteK0T/jenkins-sandbox) — `bin/greet.sh` (`greet.sh [-u] ИМЯ`), тесты `test/greet.bats`, `Jenkinsfile` (shellcheck → bats с JUnit → архив → запуск) и `Jenkinsfile.vm` (те же проверки в одноразовой ВМ). Публичный: Jenkins читает его по HTTPS без ключей. С этапа 4 все упражнения идут на нём.

## Словарь (минимум, без которого дальше никак)

| Понятие | Что это |
| :--- | :--- |
| **Controller** | сам сервер Jenkins: веб-интерфейс, очередь, история, планировщик. **Сборки на нём не запускают** |
| **Agent / Node** | машина или процесс, где реально выполняются шаги сборки |
| **Executor** | «слот» на агенте: сколько сборок агент делает одновременно |
| **Label** | метка агента (`linux`, `vm-host`) — пайплайн просит метку, а не конкретную машину |
| **Job / Project** | описание того, *что* делать: Freestyle (кнопками) или Pipeline (кодом) |
| **Build / Run** | один запуск задачи: номер, лог, статус, артефакты |
| **Workspace** | рабочая папка задачи на агенте (сюда клонируется код) |
| **Artifact** | файл, сохранённый из сборки (бинарник, отчёт, скриншот) |
| **Credentials** | хранилище секретов; в пайплайн попадают по ID, в логе маскируются |
| **Plugin** | почти вся функциональность Jenkins — плагины, у каждого свои обновления и уязвимости |

## Этапы практики

Каждый этап: цель → упражнение → «готово, когда…». Двигаться дальше только когда понятно, *почему* работает.

### Этап 1. Первая задача (Freestyle)

- **Цель:** понять задачу, сборку, консольный лог, историю.
- **Упражнение:** *New Item → Freestyle* → шаг *Execute shell*: `uname -a; date; echo "сборка $BUILD_NUMBER"`. Запустить 3 раза, открыть *Console Output*, посмотреть переменные окружения (*Environment Variables* у сборки).
- **Добавить:** параметр (*This project is parameterized* → строка `NAME`), расписание *Build periodically* `H/15 * * * *` (что значит `H` — разнос нагрузки по хэшу имени), *Discard old builds*.
- **Готово, когда:** можете объяснить, где лежит workspace, что такое `$BUILD_NUMBER`, `$WORKSPACE`, и почему у вас нет исполнителей на контроллере (задача не запустится, пока не будет агента — это нормально, см. этап 2; на время этапа 1 можно временно дать контроллеру 1 исполнитель и вернуть 0).
- **Замечено на практике:**
  - сборка по таймеру никого не спрашивает → параметры берут **значения по умолчанию**; у параметра всегда должно быть разумное значение по умолчанию;
  - `H` фиксирует минуту по имени задачи: `H/5` у задачи «Этап 1» срабатывал в :04, :09, :14…; подсказка под полем расписания показывает прошлый и следующий запуск — так проверяют запись;
  - *Discard old builds* удаляет лишнее **после следующей сборки**, номера при этом не сбрасываются;
  - `Execute shell` запускается как `sh -xe`: строки с `+` — это команды, первая ошибка роняет сборку;
  - таймер «раз в 5 минут» — 288 сборок в сутки: посмотрели — выключили.

### Этап 2. Агент

- **Цель:** понять, где выполняется код, и метки.
- **Упражнение:** *Manage Jenkins → Nodes → New node* → постоянный агент, метка `linux`, *Launch agent by connecting it to the controller* + **WebSocket**. Запустить агент как службу (OpenRC/systemd) от **отдельного** пользователя. В задаче указать *Restrict where this project can be run* → `linux`.
- **Готово, когда:** сборка идёт на агенте, на контроллере 0 исполнителей, и вы понимаете разницу: SSH-агент (контроллер заходит на машину по ключу) против inbound-агента (агент сам подключается к контроллеру с секретом — ключей SSH не нужно).
- **Замечено на практике:**
  - секрет узла — это пароль агента: файл `root:jenkins-agent 0640`, в репозиторий и лог не попадает;
  - в логе сборки появляется `Building remotely on agent-1 (…) in workspace …`, `id` показывает пользователя агента, а не `jenkins`;
  - **проверяйте *Remote root directory*:** путь, случайно вставленный дважды через пробел, дал workspace `/var/lib/jenkins-agent/ /var/lib/jenkins-agent/workspace/…` — сборки шли, но с пробелом в пути;
  - агент на том же VPS отделён пользователем и каталогом, а не машиной — `uname -a` тот же. Другие системы появятся на этапе 7;
  - **после перезагрузки сервера агент может не подняться**, хотя служба в автозапуске: `after jenkins` в OpenRC задаёт только *порядок* запуска, а не готовность — агент стартовал через доли секунды после контроллера, ещё до того, как тот открыл порт, скачать `agent.jar` не смог и сдался. Симптом — сборки висят в очереди с *‘agent-1’ is offline*. Лечение — в `start_pre` службы ждать контроллер (повторять запрос до `WAIT_TIMEOUT`, по умолчанию 180 с), а не падать с первой попытки. Общее правило: «запущен» ≠ «готов», зависимые службы должны ждать готовности сами.

### Этап 3. Pipeline в интерфейсе

- **Цель:** декларативный пайплайн: `pipeline`, `agent`, `stages`, `steps`, `post`.
- **Упражнение:** *New Item → Pipeline*, скрипт прямо в задаче:

```groovy
pipeline {
    agent { label 'linux' }
    options { timestamps(); timeout(time: 10, unit: 'MINUTES'); buildDiscarder(logRotator(numToKeepStr: '20')) }
    stages {
        stage('Проверка')  { steps { sh 'shellcheck --version' } }
        stage('Тесты')     { steps { sh 'echo тесты' } }
    }
    post {
        always  { echo "итог: ${currentBuild.currentResult}" }
        failure { echo 'упало — смотрим лог' }
    }
}
```

- **Посмотреть:** граф стадий (плагин Pipeline Graph View), *Replay* (поправить скрипт и перезапустить без сохранения), *Pipeline Syntax* (генератор сниппетов — главный помощник при обучении).
- **Готово, когда:** умеете уронить стадию нарочно (`sh 'exit 1'`) и понимаете, какие блоки `post` сработали.
- **Замечено на практике:**
  - **первый запуск — без параметров:** Jenkins узнаёт про блок `parameters` только выполнив скрипт, поэтому в сборке #1 `$NAME` пуст (даже не значение по умолчанию). Защита: `${NAME:-мир}` в shell, `params.NAME ?: 'мир'` в Groovy;
  - *Replay* наследует параметры исходной сборки и не меняет сохранённый скрипт задачи;
  - упавшая стадия → следующие пропущены: `Stage "Сборка" skipped due to earlier failure(s)`; `post { always }` срабатывает всегда, `success`/`failure` — по итогу.

### Этап 4. Jenkinsfile из Git

- **Цель:** пайплайн живёт рядом с кодом, а не в Jenkins.
- **Упражнение:** учебный репозиторий (например, bash-скрипт + тесты на `bats`) с `Jenkinsfile`; задача *Pipeline script from SCM*. Затем **Multibranch Pipeline** — Jenkins сам находит ветки с `Jenkinsfile`.
- **Триггеры:** если Jenkins не виден из интернета (только localhost/VPN), вебхуки GitHub до него не дойдут → *Poll SCM* (`H/5 * * * *`) или ручной запуск. Вебхуки — только через HTTPS-прокси. В Multibranch-проекте вместо опроса работает периодическое сканирование, и `pollSCM` в `Jenkinsfile` там лишний — с ним каждый коммит собирается дважды (этап 8, находка 6).
- **Готово, когда:** правка в ветке → сборка этой ветки без захода в UI.
- **Как сделано:** задача `sandbox` (*Pipeline script from SCM*, `https://github.com/WhiteK0T/jenkins-sandbox.git`, `*/main`), затем `sandbox-mb` (*Multibranch Pipeline*, источник Git, сканирование раз в 5 минут, *Discard old items*); старую `sandbox` после этого отключить — иначе каждый коммит собирается дважды.
- **Замечено на практике:**
  - `triggers { pollSCM('H/5 * * * *') }` в `Jenkinsfile` **регистрируется только после первой сборки**;
  - опрос собирает коммиты **пачкой**: два коммита между опросами — одна сборка с обоими в *Changes*;
  - в *Changes* автор `noreply`: плагин Git показывает коммиттера, а при правке в веб-интерфейсе GitHub коммитит сам GitHub. Нужен автор — *Additional Behaviours → Use commit author in changelog*;
  - **окружение агента ≠ ваш терминал:** служба OpenRC стартует без `LANG` (локаль `C`), и тест с кириллицей, зелёный в терминале, в Jenkins падал бы. Лечится в `Jenkinsfile`: `environment { LC_ALL = 'C.UTF-8' }`;
  - лог сканирования Multibranch объясняет всё: `‘Jenkinsfile’ found → Met criteria → Changes detected … → Scheduled build`;
  - **удалили ветку — удалилась и задача ветки со всей историей сборок** (*Discard old items*). Нужна сборка «на память» — *Keep this build forever* до удаления ветки.

### Этап 5. Тесты и отчёты

- **Цель:** Jenkins показывает не «зелёно/красно», а *какие* тесты упали и тренд.
- **Упражнение:** отчёт bats в JUnit → шаг `junit`; для Java — Maven/Gradle и `junit '**/target/surefire-reports/*.xml'`; `archiveArtifacts` для собранных файлов; позже `shellcheck -f checkstyle` → плагин Warnings NG (`recordIssues`).

```groovy
stage('Тесты') {
    steps {
        sh 'rm -rf reports && mkdir reports'
        // код выхода bats сборку не роняет — упавшие тесты разберёт junit (→ UNSTABLE)
        sh script: 'bats --print-output-on-failure --report-formatter junit --output reports test/',
           returnStatus: true
    }
    // отчёта нет (bats не запустился) — junit упадёт, и сборка станет FAILURE
    post { always { junit 'reports/*.xml' } }
}
stage('Упаковка') {
    steps {
        sh 'rm -rf dist && mkdir dist && tar czf "dist/greet-${BUILD_NUMBER}.tar.gz" bin/ README.md'
        archiveArtifacts artifacts: 'dist/*.tar.gz', fingerprint: true
    }
}
```

- **Три цвета:** **FAILURE** (красный) — сломан сам процесс (shellcheck, нет отчёта); **UNSTABLE** (жёлтый) — собралось, но тесты упали; дальнейшие стадии при этом выполняются; **SUCCESS**.
- **Грабли:** **workspace не очищается между сборками.** Маска `greet-*.tar.gz` в корне workspace подхватила архив прошлой сборки — в артефактах оказалось два файла. Решение — собирать в каталог, который каждый раз создаётся заново (`dist/`), или `cleanWs()`.
- **Готово, когда:** на странице задачи есть график тестов, упавший тест открывается с текстом ошибки.

### Этап 6. Секреты

- **Цель:** ни одного пароля или токена в коде и логах.
- **Упражнение:** *Manage Jenkins → Credentials* → секрет «Secret text» → в пайплайне:

```groovy
withCredentials([string(credentialsId: 'demo-token', variable: 'TOKEN')]) {
    sh 'curl -s -H "Authorization: Bearer $TOKEN" https://example.org/api'   // одинарные кавычки!
}
```

- **Понять:** почему в Groovy-строке в двойных кавычках секрет утекает (интерполяция до shell), как выглядит маскирование `****` в логе, чем отличаются области видимости (глобальные, папки).
- **Готово, когда:** секрет используется, а в логе и в `Jenkinsfile` его нет.
- **Проверено на практике** (Jenkins 2.568.3 LTS):

| Что в пайплайне | Что в логе |
| :--- | :--- |
| `sh 'echo "$TOKEN"'` | `****` — и в строке команды `+ echo …`, и в выводе |
| `sh "echo ${TOKEN}"` | вывод замаскирован, но выше жёлтое *Warning: A secret was passed to "sh" using Groovy String interpolation, which is insecure* — значение уже в тексте команды |
| `sh 'echo "$TOKEN" \| rev'` | **секрет открытым текстом** (перевёрнутый) |
| `sh 'echo "$TOKEN" \| base64'` | `****Cg==` — плагин маскирует и base64-форму, но только её; любое другое преобразование раскрывает |
| `usernamePassword(...)` | пароль `****`, **логин открыт** — скрыть его: галочка *Treat username as secret* у секрета |
| вне `withCredentials` | переменной нет |

- **Выводы:** маскирование — страховка, а не защита; код, который видит секрет, всегда может его вывести → ревью `Jenkinsfile` и узкие права на секреты. **Секрет утёк в лог — сначала перевыпустить, потом удалить сборку**: удаление лога не отменяет того, что его уже прочли.
- **Пользователь ИИ-агента** (без прав *Credentials*) на запрос хранилища секретов получает 404 — не видит даже их список.

### Этап 7. Тестовые виртуалки из пайплайна

- **Цель:** главный практический сценарий — проверять проекты не на сервере, а в чистых ВМ разных дистрибутивов.
- **Схема одной сборки:** поднять ВМ из базового образа как временную копию (qcow2-overlay) → дождаться SSH → скопировать код → прогнать тесты → забрать отчёты и скриншоты → **всегда** погасить и удалить ВМ (`post { always { … } }`).
- **Плагины:** Lockable Resources — чтобы две сборки не делили одну ВМ/порт (`lock('vm-debian-13') { … }`); `ws-cleanup` — чистый workspace.
- **GUI:** скриншот экрана ВМ через монитор QEMU (`screendump`) → `archiveArtifacts '*.png'`; живой просмотр — VNC через SSH-туннель.
- **Готово, когда:** одна задача прогоняет тесты в ВМ и оставляет после себя только артефакты.
- **Как сделано на этом VPS:**
  - ВМ — QEMU/KVM без libvirt: скрипты `vm-up` / `vm-ssh` / `vm-down`, «золотой» образ Debian 13 с bats и shellcheck (собран через cloud-init), машина поднимается за ~8 с, сеть пользовательская (SSH только на `127.0.0.1`);
  - **образы в одном экземпляре** — `/srv/virt/base`, их читают и владелец инфраструктуры, и агент; каждая сборка пишет только в свой одноразовый слой (qcow2 с `-b base`), который удаляется вместе с ВМ. Копировать образы под каждого пользователя незачем: сотни мегабайт на копию и два образа, которые разъедутся при пересборке;
  - у агента своё только `run/` (слои его машин) и копия ключа ВМ — `ssh` не примет ключ, читаемый кем-то кроме владельца; скрипты он исполняет, но изменить не может;
  - агенту — метка `kvm` (и группа `kvm` в системе), пайплайн просит `agent { label 'kvm' }`;
  - `Jenkinsfile.vm` в учебном репозитории; задача `sandbox-vm` — *Pipeline script from SCM* с **Script Path** `Jenkinsfile.vm` (один репозиторий — несколько пайплайнов).
- **Первая же находка:** в Debian тест `-u` упал, на Gentoo — зелёный. `awk '{ print toupper($0) }'` в Gentoo — это `gawk` (кириллицу понимает), в Debian по умолчанию `mawk` (только латиница). Ради таких ошибок ВМ и нужны: исправлено на GNU `sed 's/.*/\U&/'` → обе системы зелёные. Оговорка на будущее: `\U` — расширение GNU sed, в BusyBox (Alpine, Entware) его нет — появится такая ВМ, матрица это поймает.
- **Как выглядит в логе:** `Resource [vm-debian-13] did not exist. Created.` → `Lock acquired` → `vm-up` (≈8 с) → `PRETTY_NAME="Debian GNU/Linux 13 (trixie)"` → тесты → `scp` отчёта обратно → `junit` → `vm-down` → `Lock released`. Строка `[Checks API] No suitable checks publisher found` безвредна (отправка статусов в GitHub не настроена).
- **Скриншоты GUI** — отложены до проекта с графическим интерфейсом.
- **Ограничение `lock`:** он защищает от одновременных сборок Jenkins, но не от ручного запуска той же ВМ (тот же SSH-порт) в терминале. На этапе 8 причина убрана целиком — у каждой ВМ свой порт, `lock` больше не нужен (см. ниже).

### Этап 8. Матрица и параметры

- **Цель:** одна задача — несколько окружений. Вместо двух задач (`sandbox-mb` на Gentoo и `sandbox-vm` в Debian), которые запускают и смотрят порознь, — **одна сборка**, где все системы проверяются параллельно, а отчёт показывает, где что упало.
- **Подготовлено:** ветка [`matrix`](https://github.com/WhiteK0T/jenkins-sandbox/tree/matrix) учебного репозитория — новый `Jenkinsfile`, `Jenkinsfile.vm` удалён (его работу делает матрица).

Устройство нового `Jenkinsfile`:

```groovy
// команда «на платформе»: на агенте или по SSH в ВМ; команда идёт через env — без экранирования кавычек
def onPlatform(String platform, String cmd, boolean returnStatus = false) { … }

pipeline {
    agent none                                    // у каждой ячейки матрицы свой агент
    parameters { choice(name: 'ONLY', choices: ['все', 'gentoo', 'debian-13']) }
    stages {
        stage('Системы') {
            matrix {
                axes { axis { name 'PLATFORM'; values 'gentoo', 'debian-13' } }
                when { beforeAgent true; expression { params.ONLY == null || params.ONLY == 'все' || params.ONLY == env.PLATFORM } }
                agent { label 'linux && kvm' }
                environment { VIRT = '/srv/virt'; VM_ID = "b${env.BUILD_NUMBER}-${currentBuild.startTimeInMillis}" }
                stages {
                    stage('ВМ: запуск') { when { expression { PLATFORM != 'gentoo' } } … }   // vm-up + scp кода
                    stage('Окружение')  { … }                                               // uname, os-release, bats --version
                    stage('shellcheck') { … }
                    stage('Тесты')      { … post { always { junit 'reports/*.xml' } } }
                }
                post { always { /* vm-down, если ВМ */ } }
            }
        }
        stage('Упаковка') { agent { label 'linux' } … }   // после матрицы, один раз
    }
}
```

- **Новое на этом этапе:**
  - `agent none` наверху и `agent` у ячеек — каждая параллельная ветка получает свой исполнитель и свой workspace (`…@2`);
  - `axes`/`axis` — оси матрицы; ячеек = произведение значений осей (позже можно добавить вторую ось, например версию bats), `excludes` — выкинуть ненужные сочетания;
  - `when` у матрицы — фильтр ячеек по параметру `ONLY`;
  - Groovy-функция над `pipeline { }` — общий код для всех ячеек;
  - **у агента 2 исполнителя** — обе ячейки идут одновременно; с одним исполнителем матрица выполнилась бы по очереди.
- **Что выяснилось при подготовке** (ветка прогнана в `sandbox-mb`, сборки #1–#5):
  1. `No such property: PLATFORM` — в Groovy-выражениях (`when`, `script`, `options`) значение оси берут как **`env.PLATFORM`**; голое `PLATFORM` работает только внутри `sh '…$PLATFORM…'` (там это переменная окружения shell).
  2. `lock(resource: "vm-${env.PLATFORM}")` в `options` матрицы — и даже в `options` стадии внутри неё — дал **`vm-null`**: options вычисляются раньше, чем ячейке назначено значение оси. Обе ячейки делили один замок и шли **по очереди** — сборка зелёная, а параллельности нет. Видно только по логу (`Trying to acquire lock on [Resource: vm-null]`) — хороший пример, зачем читать лог и у зелёных сборок.
  3. Решение — убрать причину замка: **`vm-up` выбирает свободный SSH-порт** (пишет в `run/<имя>-<id>/ssh-port`), VNC-дисплей QEMU ищет сам (`-vnc …,to=99`, фактический — в `vnc-display` через QMP); `vm-ssh` находит машину по `VM_ID` из окружения. Теперь машин одного типа может быть сколько угодно, сборки разных веток и ручные ВМ друг другу не мешают.
  4. Итог (сборка #5): обе ячейки стартуют в одну секунду (`…/sandbox-mb_matrix` и `…/sandbox-mb_matrix@2`), Gentoo — 1 с, Debian с подъёмом ВМ — ≈15 с, вся сборка — **17 с**, в отчёте 12 тестов (по 6 на систему).
  5. **`beforeAgent true`.** По умолчанию `when` проверяется **после** того, как стадия заняла агента: ячейка, отфильтрованная параметром `ONLY`, всё равно ждёт свободный исполнитель, чтобы затем пропустить себя. Вскрылось, когда агент был выключен: сборка с `ONLY = debian-13` поставила в очередь **две** части вместо одной. С `beforeAgent true` пропущенная ячейка агента не занимает (`Stage "Matrix - PLATFORM = 'gentoo'" skipped due to when conditional` — сразу, по строке на каждую вложенную стадию), а значение оси (`env.PLATFORM`) в `when` при этом уже известно — в отличие от `options`.
  6. **Двойные сборки после слияния.** Слияние в `main` собралось дважды на одном коммите. Сначала #9 *Started by an SCM change*: её запустил `pollSCM` из `Jenkinsfile`, в *Changes* — 5 коммитов ветки. Через 10 с — #10 *Branch indexing* от сканирования `sandbox-mb`, *Changes* пустые. Новые коммиты замечали два механизма с одинаковым интервалом 5 минут. Если они срабатывают с разницей в секунды, пока сборка ещё в очереди, Jenkins склеивает их в одну сборку с двумя причинами (так было у `main` #8). Если разница больше — получается лишняя сборка и лишняя ВМ. Сканирование Multibranch и так находит новые коммиты во всех ветках, поэтому блок `triggers { pollSCM … }` удалён. Следующий коммит дал ровно одну сборку #11 (*Branch indexing*, 12/12). Из свойств задачи `main` пропал *PipelineTriggersJobProperty*: опрос снимается первой же сборкой без `triggers`.
- **Упражнения:**
  1. Посмотреть сборку ветки `matrix` в `sandbox-mb`: граф с двумя параллельными ветками `PLATFORM = 'gentoo'` / `PLATFORM = 'debian-13'`; в *Test Result* — тесты с пометкой системы.
  2. Сломать что-то только для Debian (например, вернуть `awk` вместо `sed` в ветке) → жёлтая ячейка Debian, зелёная Gentoo, сборка целиком UNSTABLE.
  3. *Build with Parameters* → `ONLY = debian-13` — ячейка Gentoo пропущена (*skipped*) и не стоит в очереди (*Build Queue* слева — одна часть сборки, а не две).
  4. Слить `matrix` в `main` через **Pull Request** на GitHub; задачу `sandbox-vm` после этого удалить.
- **Пройдено:** ветка слита в `main` через Pull Request; после очередного сканирования `sandbox-mb » main` собрался матрицей (Gentoo + Debian параллельно, 12/12 тестов, ≈20 с), задача удалённой ветки ушла сама (*Will remove matrix*), `sandbox-vm` и прочие учебные задачи этапов 1–7 удалены — остался один Multibranch-проект. `pollSCM` из `Jenkinsfile` убран: теперь каждый коммит — одна сборка.
- **Дальше:** собрать образы Ubuntu 24.04 и 26.04 (`vm-build-base`) → добавить их в `vms.conf` и в `values` оси — матрица вырастет на две ячейки без другой правки пайплайна.
- **Готово, когда:** одна кнопка (или коммит) гоняет тесты на всех системах, отчёт показывает, где упало.

## Как этим Jenkins пользуется ИИ-агент (Claude Code)

**Зачем:** агент пишет код и тесты, но проверять их на «голом» сервере неудобно и опасно, а GUI-программы ему вообще не видны. Jenkins даёт агенту **тот же конвейер, что и человеку**: чистые ВМ, разные дистрибутивы, отчёты тестов, скриншоты, история.

**Цикл работы:**

1. Агент правит код в рабочей копии и коммитит в ветку (не в `main`).
2. Запускает нужную задачу через MCP (`triggerBuild`) с параметрами — например, дистрибутив.
3. Ждёт результат (`getBuild`), при падении читает лог (`getBuildLog`, `searchBuildLog`) и отчёт тестов (`getTestResults`).
4. Для GUI — открывает архивные скриншоты сборки (по ним видно, отрисовалось ли окно, что в нём).
5. Исправляет и повторяет; итог показывает человеку: ссылка на сборку, что упало и почему.

**Границы (что агент НЕ делает):**

- **Отдельный пользователь с минимумом прав:** *Overall/Read*, *Job/Read*, *Job/Build*, *Job/Cancel*, *Run/Replay* — только на папку учебных/тестовых задач. **Нет** *Administer*, *Configure*, *Script Console*, доступа к Credentials.
- **Конфигурацию сервера не меняет через UI.** Изменения JCasC/Job DSL — только файлом в Git, который смотрит и применяет человек.
- **Собственный API-токен**, хранится в переменной окружения, не в файлах проекта; его можно отозвать одной кнопкой.
- Пайплайны агента выполняются на агенте Jenkins, а не на контроллере; ВМ временные и удаляются после сборки.

## Безопасность учебного сервера

- Jenkins слушает **только localhost**; заходить через SSH-туннель (`ssh -L`) или VPN.
- Анонимам — ничего, регистрация выключена, мастер первого запуска отключён (пароли задаются при установке).
- На контроллере **0 исполнителей**: код сборок не выполняется рядом с секретами Jenkins.
- Агент — отдельный пользователь, inbound через WebSocket на localhost, **без SSH-ключей**.
- Приватных ключей GitHub на сервере нет — пуш через проброшенный `ssh-agent`. Единственное исключение — deploy key учебного `jenkins-sandbox` (доступ только к этому репозиторию); удалить вместе с репозиторием после курса.
- `Jenkinsfile` — это код, исполняемый на агенте: сборки из чужих форков не запускать.
- Обновления LTS и плагинов — по бюллетеням безопасности.
