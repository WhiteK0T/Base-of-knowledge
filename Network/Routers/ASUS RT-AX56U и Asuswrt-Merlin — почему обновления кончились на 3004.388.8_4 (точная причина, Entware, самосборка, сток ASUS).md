# ASUS RT-AX56U и Asuswrt-Merlin: почему обновления кончились на 3004.388.8_4

> [!info] Короткий ответ
> **ASUS никогда не переводила RT-AX56U на ветку 388.** Сток этой модели как был, так и остался на `3.0.0.4.386_xxxxx`. Ветка 388 на AX56U существовала только у Merlin — и только потому, что RMerlin отдельно выпрашивал у ASUS специально собранные 388-GPL для уже снятой с поддержки модели. Последний раз ASUS дала такой GPL в январе 2024 (`388_24353`). После этого сборки для AX56U прекратились: **последняя — `3004.388.8_4` от 17 ноября 2024**, ровно та, что стоит у меня.
>
> Исходники модели из дерева при этом **не удалены** — собрать свежую версию самому формально можно, но на свой страх.

## 1. Что за железо и почему это важно

| Параметр | Значение | Откуда известно |
| :--- | :--- | :--- |
| SoC | Broadcom BCM6755 / BCM47622, ARMv7 (32 бита) | профиль `HND-947622_BASE` в `release/src-rt/target.mak` |
| RAM / Flash | 512 МБ / 256 МБ | ТТХ устройства |
| Каталог SDK в дереве Merlin | `release/src-rt-5.02axhnd.675x` | листинг репозитория |
| Ядро Linux | **4.1** | каталог `release/src-rt-5.02axhnd.675x/kernel/linux-4.1` |
| Профиль сборки | `export RT-AX56U := $(HND-947622_BASE)` | `release/src-rt/target.mak`, строки 65–66 |
| NVRAM / MTD | `NVSIZE="128"`, `LINUX_MTD="64"` | тот же профиль |

Ядро **4.1** — ключевая деталь. Это ядро 2015 года. Соседние модели того же вендора, ушедшие на SDK 5.04 (`release/src-rt-5.04axhnd.675x`), получили ядро **4.19**. AX56U туда не перевели, потому что для перевода нужен новый GPL-дроп от ASUS именно под эту модель, а его нет.

> [!note] Почему Entware вообще работает
> Ядро 4.1 ≥ 3.2, архитектура ARMv7 soft-float → подходит репозиторий Entware **`armv7sf-k3.2`**. В нём на момент проверки **3026 пакетов**. Это и есть главная лазейка для обновления пользовательского софта в обход прошивки.

## 2. Точная хронология: как модель то выбрасывали, то возвращали

Всё ниже — дословные цитаты из `Changelog-NG.txt` ветки `3004.388` официального репозитория `RMerl/asuswrt-merlin.ng`.

### 5 апреля 2020 — 384.16: поддержка появилась

> `NEW: Added support for the RT-AX56U, based on GPL + binary blobs from 384_8253.`

### 14 августа 2020 — 384.19: первый звоночек

> `NOTE: The RT-AX56U build is not available for this release.`

### 21 августа 2023 — 3004.388.4: первое официальное снятие с поддержки

> *«The RT-AX56U is no longer supported, as Asus has put it on End-of-Life status, and the previous Asuswrt-Merlin 388 releases for that model were all based on untested code.»*

Здесь сказаны обе причины сразу: **ASUS объявила модель EOL**, и **все предыдущие 388-сборки под неё делались на непротестированном коде**.

### 20 января 2024 — 3004.388.6: возврат «в порядке исключения»

> *«Since Asus provided GPL code for the RT-AX56U, this model will exceptionally be included with this release, despite still being considered being end-of-life.»*

### 26 апреля 2024 — 3004.388.7 и 21 июля 2024 — 3004.388.8

> `NOTE: RT-AX56U is exceptionally included in this release.`

### 17 ноября 2024 — 3004.388.8_4: последняя сборка

В самом changelog про AX56U ничего не сказано — модель просто перестала появляться в релизах. Файловый листинг SourceForge подтверждает это однозначно:

## 3. Техническая причина, а не просто «EOL»

Самое доказательное — история коммитов по бинарным блобам (проприетарные драйверы Wi-Fi и прочая закрытая часть, которую нельзя пересобрать из исходников).

**Для RT-AX56U:**

| Дата | Коммит | Сообщение |
| :--- | :--- | :--- |
| **2024-01-05** | `55948500` | **`Merged RT-AX56U binary blobs from 24353`** ← последний |
| 2023-02-25 | `9958b2c4` | `Merged RT-AX56U binary blobs from 22525` |
| 2022-10-21 | `7774c11f` | `Merge 388_21224 binary blobs for RT-AX56U` |
| 2022-05-26 | `6c7f3839` | `Merge 48966 binary blobs for RT-AX56U` |

**Для RT-AX58U — соседа по той же платформе и тому же каталогу SDK:**

| Дата | Коммит | Сообщение |
| :--- | :--- | :--- |
| 2026-06-05 | `00122ac4` | `Copy RT-AX58U binary blobs from 388_25633` |
| 2025-12-09 | `60506fcb` | `Merge RT-AX58U binary blobs from 25575` |
| 2025-09-17 | `20271c0b` | `Merge RT-AX58U prebuilt + SDK from 388_25523` |
| 2025-01-23 | `8773f186` | `Merge RT-AX58U binary blobs from 25373` |

Разрыв — **два с половиной года**. И вот решающий коммит, который вошёл в 388.9:

> `17dd95fb` (23 января 2025): **`Merged with GPL 388_25373 + SDK HND5.02ax-675x (from RT-AX58U)`**

С этого момента **сам SDK платформы 675x берётся из GPL другой модели** — RT-AX58U. Блобы AX56U при этом заморожены на `388_24353` (январь 2024).

> [!warning] Что это означает на практике
> Любая сборка AX56U из ветки 3004.388 начиная с 388.9 — это **свежее ядро и SDK от RT-AX58U поверх двухлетних бинарников RT-AX56U**. Ровно то, что RMerlin называет «untested code» и чего он делать не хочет: если Wi-Fi ляжет или роутер уйдёт в бутлуп, отлаживать это будет некому и не на чем.

### Цепочка причин целиком

1. ASUS ставит RT-AX56U в статус End-of-Life (до августа 2023).
2. ASUS не переводит модель на кодовую базу 388 — сток остаётся на 386.
3. RMerlin трижды выпрашивает спец-GPL под 388 (для 388.6, 388.7, 388.8) — ASUS идёт навстречу.
4. После `388_24353` (январь 2024) новых GPL для AX56U не поступает.
5. Январь 2025: платформенный SDK обновляется из GPL RT-AX58U — блобы AX56U больше не совпадают по версии с окружением.
6. Сборки прекращаются; модель уезжает в «No longer supported».

## 4. Форк gnuton не помогает

Логичный вопрос: gnuton собирает Merlin для моделей, которые не берёт RMerlin, — может, там есть AX56U?

Нет. Проверены ассеты **всех релизов** `gnuton/asuswrt-merlin.ng` начиная с середины 2024 года — RT-AX56U там **не было никогда**. Список моделей gnuton:

| Ветка | Модели |
| :--- | :--- |
| **3004 (Wi-Fi 6)** | DSL-AX82U/DSL-AX5400, RT-AX82U v1/v2, RT-AX92U, RT-AX58U v2, RT-AX5400, TUF-AX3000 v1/v2, TUF-AX5400, RT-AX95Q (XT8), RT-AXE95Q (ET8) |
| **3006 (Wi-Fi 7)** | GT-BE98 / GT-BE25000 |
| **386** | DSL-AC68U |

Проект живой (последний push — 5 сентября 2026, 2309 звёзд, релиз `3004.388.11_1-gnuton1` от 10 июня 2026), но AX56U в его матрицу CI не входит. Причина у него та же самая — нет свежих GPL под эту модель.

> [!tip] Косвенная польза от gnuton всё же есть
> Он собирает **тот же SDK** `src-rt-5.02axhnd.675x`, что нужен AX56U, в публичном CI и в готовом Docker-образе с тулчейнами. Это половина работы для самосборки — см. раздел 7.

Чего в репозитории **нет**: `unbound`, `nginx`, `sing-box` (эти ставятся отдельно или собираются вручную).

### Ключевая деталь: PATH уже настроен правильно

Asuswrt задаёт окружение в `release/src/router/rc/init.c` (строка 151):

```
PATH=/opt/usr/bin:/opt/bin:/opt/usr/sbin:/opt/sbin:/usr/bin:/bin:/usr/sbin:/sbin
```

`/opt` идёт **первым**. Это значит, что после `opkg install curl` любой скрипт и любая интерактивная сессия автоматически получают Entware-версию — никаких симлинков и подмен `/usr/sbin/curl` делать не нужно. Проверить у себя:

```sh
which curl          # ожидается /opt/bin/curl
curl -V             # 8.15.0 вместо 8.4.0
openssl version      # OpenSSL 3.5.5 (из /opt/bin)
```

### Обновление того, что уже стоит

```sh
opkg update
opkg list-upgradable                 # сначала посмотреть, что поедет
opkg upgrade curl libcurl libopenssl openssl-util ca-bundle wget-ssl
```

> [!warning] Не запускать `opkg upgrade` без аргументов
> Массовое обновление на роутере регулярно ломает зависимости и init-скрипты, а откатываться на встроенном железе неудобно. Обновлять пакеты списком, порциями, с проверкой после каждой порции. Подробнее об `opkg` — в [OPKG](../../Linux/Package-Manager/OPKG.md).

### Замена dropbear на настоящий OpenSSH

Делать строго в два шага, иначе можно отрезать себе доступ к роутеру.

**Шаг 1 — поднять OpenSSH на отдельном порту и убедиться, что он работает:**

```sh
opkg install openssh-server openssh-sftp-server openssh-keygen

# /opt/etc/ssh/sshd_config
#   Port 2222
#   PermitRootLogin prohibit-password
#   PasswordAuthentication no
#   PubkeyAuthentication yes
#   AuthorizedKeysFile /opt/root/.ssh/authorized_keys
#   Subsystem sftp /opt/libexec/sftp-server

mkdir -p /opt/root/.ssh && chmod 700 /opt/root/.ssh
cat >> /opt/root/.ssh/authorized_keys        # вставить свой публичный ключ
chmod 600 /opt/root/.ssh/authorized_keys

/opt/etc/init.d/S40sshd start
```

С другой машины: `ssh -p 2222 root@<IP роутера>`. Не закрывать текущую сессию, пока новая не заработала.

**Шаг 2 — только после успешной проверки** выключить штатный SSH в веб-интерфейсе (*Administration → System → Enable SSH → No*; это именно dropbear) и перевести OpenSSH на порт 22.

Автозапуск Entware-служб Merlin поднимает сам через `/jffs/scripts/post-mount` — отдельно ничего прописывать не нужно, при условии что Entware был установлен штатным `amtm`.

По ключам и настройке клиента — [SSH-Ключи](../SSH/SSH-%D0%9A%D0%BB%D1%8E%D1%87%D0%B8.md) и [SSH — продвинутое руководство](../SSH/SSH-%D0%9F%D1%80%D0%BE%D0%B4%D0%B2%D0%B8%D0%BD%D1%83%D1%82%D0%BE%D0%B5%20%D1%80%D1%83%D0%BA%D0%BE%D0%B2%D0%BE%D0%B4%D1%81%D1%82%D0%B2%D0%BE.md); удобно держать хосты в [sshm](../SSH/sshm%20%28Gu1llaum-3%29%20%E2%80%94%20TUI-%D0%BC%D0%B5%D0%BD%D0%B5%D0%B4%D0%B6%D0%B5%D1%80%20SSH-%D1%85%D0%BE%D1%81%D1%82%D0%BE%D0%B2%20%D0%BD%D0%B0%20Go%20%D0%BF%D0%BE%D0%B2%D0%B5%D1%80%D1%85%20~-.ssh-config.md).

### Чего Entware принципиально не чинит

| Компонент | Почему нельзя обновить через opkg |
| :--- | :--- |
| `httpd` (веб-интерфейс) | часть прошивки, слушает 80/443 на LAN |
| AiCloud | часть прошивки; **выключить** |
| Ядро 4.1 и драйверы Wi-Fi | закрытые блобы + монолит прошивки |
| VPN-сервер из веб-морды | прошивочный OpenVPN/WireGuard |
| miniupnpd | прошивочный; **выключить UPnP** |

> [!important] Компенсирующие меры вместо обновления
> - Выключить **AiCloud** (в 388.8_4 к нему относится незакрытая CVE-2025-2492).
> - Выключить **UPnP**.
> - Запретить доступ к веб-админке **с WAN**, оставить только LAN.
> - Доступ снаружи — только через VPN-туннель, не через проброшенный порт админки.
> - Гостевую сеть — с изоляцией от LAN.

## 7. Вариант 2 — собрать 3004.388.12_2 самому

### Хорошая новость: профиль модели из дерева не удаляли

Проверено на актуальном теге `3004.388.12_2`:

| Что | Статус |
| :--- | :--- |
| `release/src-rt/target.mak`, строки 65–66 | `export RT-AX56U := $(HND-947622_BASE)` — весь профиль на месте |
| `release/src-rt-5.02axhnd.675x/router-sysdep.rt-ax56u` | каталог присутствует |
| `release/src-rt/Makefile`, строка 5982 | есть ветка под `BUILD_NAME = "RT-AX56U"` |
| Ветка `3006.102-wifi6` | профиль `RT-AX56U` тоже присутствует |

> [!warning] Наличие профиля ≠ поддержка
> В том же `target.mak` ветки `3006.102-wifi6` лежат профили RT-AC3100, RT-AC5300 и RT-AC88U — моделей, которые в вики давно числятся в «No longer supported». Это просто неудалённый код, а не обещание сборок.

### Рецепт сборки

Проще всего повторить то, что делает CI gnuton: готовый образ с тулчейнами вместо ручной настройки Ubuntu 20.04.

```sh
# образ: gnuton/asuswrt-merlin-toolchains-docker:latest
#   ~1853 МБ, обновлён 07.01.2025, ~29 900 загрузок
docker run -it --rm -v "$PWD:/project" gnuton/asuswrt-merlin-toolchains-docker:latest

# внутри контейнера:
source /home/docker/envs/bcm-hnd.sh          # окружение для SDK 5.02axhnd(.675x)
sudo ln -sf /home/docker/am-toolchains/brcm-arm-hnd /opt/toolchains

git clone --depth 1 -b 3004.388.12_2 https://github.com/RMerl/asuswrt-merlin.ng.git
cd asuswrt-merlin.ng/release/src-rt-5.02axhnd.675x
make rt-ax56u

# результат: ./image/*.w  (образы с загрузчиком *cferom* прошивать НЕ нужно)
```

Соответствие SDK и окружения (из матрицы CI gnuton):

| SDK-каталог | Окружение | Ядро |
| :--- | :--- | :--- |
| `src-rt-5.02axhnd` | `bcm-hnd.sh` | 4.1 |
| **`src-rt-5.02axhnd.675x`** ← AX56U | **`bcm-hnd.sh`** | **4.1** |
| `src-rt-5.04axhnd.675x` | `bcm-hnd-ax-4.19.sh` | 4.19 |

### Хост для сборки: по системам

Сборка Merlin требует специфического окружения (32-битные библиотеки, свой gcc, старый Ubuntu). Собирать «нативно» на современном дистрибутиве почти гарантированно не выйдет — правильный ответ везде один: **контейнер**. Ниже — как подготовить хост.

**Gentoo (основная система).** Сборку в контейнере, свой Portage не трогаем:

```sh
# всё из исходников, как обычно
emerge -av app-containers/docker app-containers/docker-cli

# ядру нужны: NAMESPACES, CGROUPS, OVERLAY_FS, BRIDGE, VETH, NF_NAT,
# POSIX_MQUEUE, MEMCG, CPUSETS  — проверить скриптом из docker-репозитория
rc-update add docker default
rc-service docker start
usermod -aG docker "$USER"
```

Альтернатива без Docker — чистый chroot в Ubuntu 20.04:

```sh
emerge -av dev-util/debootstrap
debootstrap --arch=amd64 focal /var/chroot/focal http://archive.ubuntu.com/ubuntu/
# дальше внутри chroot ставить зависимости по вики RMerlin
```

Отдельный плюс Gentoo здесь: на нём уже привычно ждать долгую компиляцию, а полная сборка прошивки занимает десятки минут и требует ~30 ГБ свободного места.

**Debian / Ubuntu:**

```sh
apt install docker.io
systemctl enable --now docker
usermod -aG docker "$USER"
```

Это единственная платформа, где реалистичен и нативный путь — **если** это именно Ubuntu 20.04 LTS (официально рекомендованный вики Merlin хост): понадобится `dpkg --add-architecture i386` и пакеты 32-битной поддержки, дальше по официальной инструкции.

**Arch (планируется с июня 2026):**

```sh
pacman -S docker
systemctl enable --now docker
usermod -aG docker "$USER"
```

Нативная сборка на Arch практически безнадёжна: слишком свежие glibc и binutils для тулчейна 2015 года. Только контейнер. Из AUR ничего специального не нужно — образ уже содержит тулчейны.

**Entware / ASUS RT-AX56U:** ❌ **не хост для сборки.** 512 МБ RAM, ARMv7, нет ни места, ни кросс-тулчейна. Роутер здесь — только цель прошивки. Готовый `.w` заливается через веб-интерфейс (*Administration → Firmware Upgrade*) или, при проблемах, через ASUS Firmware Restoration по TFTP.

### Риски — честно

| Риск | Насколько вероятно |
| :--- | :--- |
| Docker-образ (январь 2025) не потянет SDK из 388.12 | вполне возможно — тогда собирать окружение по вики RMerlin вручную |
| Не поднимется Wi-Fi: новый SDK от AX58U + блобы AX56U от 388_24353 | это главный риск, ровно тот, о котором писал RMerlin |
| Не загрузится `dhd` / бутлуп | возможно |
| Кирпич | возможно, поэтому — только с готовым планом восстановления |

> [!danger] Перед первой прошивкой самосбора
> Обеспечить восстановление **заранее**: ASUS Firmware Restoration по TFTP (роутер в rescue-режиме — держать Reset при включении питания, пока не замигает индикатор), в идеале — доступ по UART. Без этого не начинать.

Люди с этой моделью такие сборки просят на SNBForums (есть тема с прямым запросом собрать `RT-AX56U_3004_388.12_2_puresqubi.w`), то есть путь ходибельный — но никем не гарантированный и никем не оттестированный.

## 8. Вариант 3 — вернуться на сток ASUS

Единственный путь, который **официально продолжает получать патчи**.

| Версия | Дата | Размер | Что внутри |
| :--- | :--- | :--- | :--- |
| **`3.0.0.4.386_52090`** | **6 мая 2026** | 78 861 372 Б | закрыт небезопасный механизм удалённого запуска скриптов, переполнение кучи при обработке кэша |
| `3.0.0.4.386_52088` | 13 марта 2026 | 78 848 204 Б | стабильность роуминга 802.11k, совместимость с iOS 26 |
| `3.0.0.4.386_52049` | 27 октября 2025 | — | закрыт обход пользовательских настроек |

Проверено: обе последние прошивки лежат на CDN ASUS и отдаются (`FW_RT-AX56U_300438652090.zip`).

**Что теряется при уходе со стока Merlin:** JFFS-скрипты и хуки (`services-start`, `post-mount`, `firewall-start`), VPN Director, полноценный WireGuard, нормальный SSH-доступ к системе, вся связка с Entware в привычном виде, кастомные конфиги dnsmasq.

Иными словами: сток свежее по вендорским фиксам, но радикально беднее по возможностям. Для сценария с туннелями и своими скриптами — неприемлемо.

## 9. Вариант 4 — сторонние форки и альтернативные прошивки

| Проект | Статус для RT-AX56U | Оценка |
| :--- | :--- | :--- |
| **OpenWrt** | ❌ страницы устройства в ToH нет | BCM6755 — закрытый Broadcom без открытых Wi-Fi-драйверов. Путь закрыт |
| **FreshTomato** | ❌ | AX-модели на HND не поддерживает по той же причине |
| **gnuton/asuswrt-merlin.ng** | ❌ никогда не собирал AX56U | см. раздел 4 |
| **SWRT-dev/asuswrt-bcm** | ⚠️ профиль `RT-AX56U` в `target.mak` есть, проект живой (54★, последний push 26 августа 2026) | лицензия не заявлена (`NOASSERTION`), образы публикуются вне GitHub, независимого аудита нет |
| **Самосбор из RMerl** | ⚠️ технически возможен | раздел 7 |

> [!caution] Про SWRT и подобные сборки
> Как источник патчей и идей — вполне. Но ставить готовый бинарник от стороннего сборщика на устройство, через которое проходит весь домашний трафик, — это отдельное решение с отдельной ценой ошибки. Если ставить, то только собрав из исходников самому.

## 10. Проверочная таблица: что говорят и как на самом деле

| Утверждение | Вердикт | Факт |
| :--- | :--- | :--- |
| «Merlin забросил RT-AX56U» | ⚠️ неточно | Формально снял в 388.4 (авг 2023), потом трижды возвращал по спец-GPL от ASUS. Реально кончилось на 388.8_4 (17 ноя 2024) |
| «388 — актуальная ветка для этой модели» | ❌ | ASUS никогда не переводила AX56U на 388; сток — всегда 386 |
| «Обновления 388 когда-нибудь доедут» | ❌ | Ветка `3004.388` жива (388.12_2 от 20 авг 2026), но AX56U в её релизах нет с ноября 2024 |
| «Виноват только EOL от ASUS» | ⚠️ половина правды | EOL — причина №1, но техническая причина — отсутствие новых GPL: блобы застряли на `388_24353`, а SDK с января 2025 берётся из GPL RT-AX58U |
| «Исходники выпилили, собрать нельзя» | ❌ | Профиль `RT-AX56U`, `router-sysdep.rt-ax56u` и ветка в `Makefile` присутствуют в `3004.388.12_2` |
| «Поможет форк gnuton» | ❌ | В его матрице CI AX56U нет и не было |
| «Можно перейти на OpenWrt» | ❌ | Устройства нет в ToH; BCM6755 без открытых драйверов |
| «Прошивка ASUS давно мертва» | ❌ | Последний сток — 6 мая 2026, с фиксами безопасности |
| «OpenSSH/curl обновить нельзя без прошивки» | ❌ | Можно через Entware, причём PATH в Asuswrt уже ставит `/opt` первым |
| «480/560 дней без патчей — не страшно» | ❌ | Незакрыты CVE-2025-2492 (AiCloud), CVE-2024-9143 и CVE-2025-9230 (OpenSSL), фиксы в `httpd`, Site Survey и пакет из ~15 OpenSSL-CVE |

## 12. Что делать по итогу

> [!tip] Рекомендуемая последовательность
> 1. **Остаться на 3004.388.8_4.** Откатываться на сток и терять JFFS-скрипты смысла нет.
> 2. **Закрыть поверхность атаки прошивки:** выключить AiCloud, UPnP, доступ к админке с WAN.
> 3. **Перевести весь пользовательский софт на Entware:** `openssh-server` 10.2p1 вместо dropbear 2024.84, `curl` 8.15, `libopenssl` 3.5.5, `ca-bundle`, `wget-ssl`, `tor`.
> 4. **Раз в пару месяцев** — `opkg update && opkg list-upgradable`, обновлять порциями.
> 5. **Самосборку 388.12_2** держать как эксперимент на свободные выходные, при наличии проверенного TFTP-восстановления. Не как основной план.
> 6. **Долгосрочно:** модель на ядре 4.1 с замороженными блобами — тупиковая ветка. При следующей замене железа брать то, что живо у RMerlin или хотя бы у gnuton (RT-AX58U v2, RT-AX82U, TUF-AX3000/5400, RT-AX86U, RT-AX88U).

## Кому что подходит

| Профиль | Что делать |
| :--- | :--- |
| Нужны свежие OpenSSH/curl/OpenSSL и ничего больше | **Entware.** Раздел 6, час работы, риска почти нет |
| Нужны свежие OpenVPN/dnsmasq/веб-морда | Только самосбор (раздел 7) или новое железо |
| Приоритет — вендорские фиксы, функции не нужны | Сток ASUS `386_52090` (раздел 8) |
| Готов экспериментировать, есть TFTP/UART | Самосбор `make rt-ax56u` из `3004.388.12_2` |
| Нужен OpenWrt | Менять железо: BCM6755 не поддерживается и не будет |
