# pdf-inspector (Firecrawl)

> [!info] Коротко
> Хорошая, честно быстрая Rust-библиотека: PDF → Markdown с разбором таблиц, колонок и заголовков. MIT, 15k ★, есть привязки к Python, Node.js и WebAssembly. Кириллица работает — я проверил.
>
> Но это **не «мощнейший PDF-парсер»**, а прямая противоположность: инструмент, который **не умеет OCR вообще** и предназначен решать, нужен ли OCR. Скормите ему скан — получите `markdown = None`. Заявленное «самый быстрый» верно внутри узкого сравнения, из которого все OCR/ML-парсеры исключены по условию.
>
> Цифра «200 документов за 2,8 секунды» — **устаревшая на месяц**: в текущем README стоит **0,470 с**, то есть пост занижает скорость в шесть раз.

---

## Что это на самом деле

Название говорит правду, а пост — нет: это **inspector**, а не парсер-комбайн. Описание репозитория: «определяет, отсканирован PDF или текстовый, чтобы принимать умные решения о маршрутизации».

Задача — сэкономить на OCR. Из README: библиотека сделана, чтобы обрабатывать текстовые PDF локально быстрее 200 мс и «не гонять через дорогие OCR-сервисы те ~54% PDF, которым это не нужно». Логика конвейера прямо нарисована в README:

```
PDF пришёл
  → классификация (~20 мс)
  → текстовый и уверенность высокая?
      ДА  → извлекаем локально (~150 мс), готово
      НЕТ → отправляем в OCR-сервис (2-10 с)
```

Автор — [Firecrawl](https://firecrawl.dev), реальная компания («Web data API for AI», 106 публичных репозиториев, с 2023 года). Инструмент вырос из их собственной боли: они пылесосят веб для LLM-конвейеров, и платить за OCR каждой попавшейся PDF-ке разорительно.

> [!warning] Скан он не прочитает — вообще
> Я собрал PDF из трёх страниц-картинок без текстового слоя и прогнал:
> ```
> classify: 0.9 мс | тип=scanned | уверенность=0.95 | нужен OCR: [0, 1, 2]
> process_pdf -> markdown: None
> ```
> Библиотека честно и мгновенно говорит «это скан, иди в OCR» — и на этом всё. Если вам нужно вытащить текст из сканов, нужен OCR-движок, а `pdf-inspector` в этой связке лишь диспетчер перед ним.

## Бенчмарк: что в нём есть и чего в нём нет

Текущая таблица README (корпус [opendataloader-bench](https://github.com/opendataloader-project/opendataloader-bench), 200 PDF, Apple M4 Pro, 31 июля 2026):

| Движок | Overall | Порядок чтения | Таблицы | Заголовки | Время на 200 док. |
| :--- | :---: | :---: | :---: | :---: | :---: |
| pdf-inspector | **0.875** | **0.915** | **0.814** | 0.788 | **0.470 с** |
| liteparse | 0.873 | 0.913 | 0.693 | **0.811** | 0.750 с |
| opendataloader | 0.831 | 0.902 | 0.489 | 0.739 | 2.569 с |
| pymupdf4llm | 0.735 | 0.886 | 0.401 | 0.424 | 17.117 с |
| markitdown | 0.589 | 0.844 | 0.273 | 0.000 | 16.165 с |

Плюс проекту: есть [ветка с воспроизводимыми результатами](https://github.com/firecrawl/opendataloader-bench/tree/abi/pdf-parser-benchmark-results) — конфиги, предсказания по документам, вывод оценщика. Это заметно лучше, чем «поверьте нам».

**Но из README пропала важная строчка.** В версии от 11 июля там было написано прямо:

> Для контекста: движки с OCR/ML (docling, marker, mineru) набирают 0.83–0.88 overall, но тратят на том же корпусе от 2 до 180 минут — pdf-inspector достаёт до нижней границы этого диапазона без всякого OCR, за 4 секунды.

Эта фраза честнее нынешней таблицы: она показывала, с кем на самом деле идёт сравнение и что ML-парсеры играют в другой весовой категории по качеству. Сейчас её нет, а в таблице остались только движки, которые заведомо слабее.

> [!note] Версия из бенчмарка не находится в реестрах
> README говорит, что мерили `pdf-inspector 0.2.6`. На crates.io версии идут `0.1.8` → `1.14.0`, в npm — `1.11.x` → `1.14.1`. Версии `0.2.6` нет ни там, ни там. Скорее всего мерили внутреннюю сборку; воспроизвести ровно тот прогон по номеру версии не выйдет.

## Мои замеры

Ставится обычным колесом, никакой сборки: `pip install pdf-inspector` (Python 3.8+). Проверял на двух статьях с arXiv и двух своих файлах.

| Файл | Страниц | Классификация | Полный разбор в Markdown | На страницу |
| :--- | :---: | :---: | :---: | :---: |
| «Attention Is All You Need» (2.1 МБ) | 15 | 21.9 мс | 59 мс | **4.0 мс** |
| WideSearch (3.9 МБ) | 29 | 8.8 мс | 56 мс | **1.9 мс** |
| Свой файл с кириллицей | 1 | — | 2.5 мс | 2.5 мс |
| Скан из картинок | 3 | 0.9 мс | не разбирает | — |

Скорость реальная и впечатляющая: 29-страничная статья со всеми таблицами и двухколоночной вёрсткой разбирается за 56 миллисекунд.

### Кириллица — работает

Это первое, что я проверил, потому что база знаний русская. Собрал PDF с шрифтом Liberation Sans:

```
тип=text_based conf=1.00 | 2.5 мс | проблемы кодировки: False

# Пакетные менеджеры Linux

Проверка извлечения кириллицы из PDF. Текст содержит русские буквы,
ёжик, съезд, объём, а также цифры 1234 и латиницу mixed text. ...

|Таблица 1. Менеджеры пакетов Система|Менеджер|Служба|
|---|---|---|
|Gentoo|emerge|OpenRC|
|Debian|apt|systemd|
|Arch|pacman|systemd|
|Entware|opkg|init.d|
```

«Ёжик, съезд, объём» вытащены посимвольно верно, `has_encoding_issues=False`, заголовок распознан как H1, таблица собрана правильно — все четыре строки и три колонки на месте.

**Но видно и баг:** подпись «Таблица 1. Менеджеры пакетов» приклеилась к первой ячейке заголовка вместо того, чтобы остаться отдельной строкой. В README есть отдельный пункт «Captions | детект по префиксам "Figure", "Table", "Source:"» — на русском «Таблица» он, ожидаемо, не срабатывает.

### Что ещё сломалось у меня

**Переносы не склеиваются, хотя README обещает.** В таблице возможностей заявлено «Hyphenation — Rejoins words broken across lines». На практике в статье с arXiv получилось `learned linear transfor- mation`, а в моём тесте — `Дефисный пере- нос слова`. Два независимых файла, оба разошлись с документацией.

**Формульные таблицы едут.** Таблица 1 из «Attention» распозналась структурно правильно, но границы ячеек поехали:

```
|Self-Attention|O ( n² · d|) O (1)|O (1)|
```

Закрывающая скобка уехала в соседнюю ячейку, а вторая строка шапки («Operations») стала отдельной пустой строкой таблицы.

**Нумерация страниц в API непоследовательна.** На одном и том же скане `pages_needing_ocr` вернул `[0, 1, 2]` (с нуля), а `ocr_reasons_by_page` — `page=1, page=2, page=3` (с единицы). В трекере есть открытая issue ровно про рассогласование индексов страниц в Python-привязке.

## Открытые проблемы в трекере

148 открытых issues, и это не мусор — там сидят настоящие пользователи с воспроизводимыми случаями. Что бросается в глаза:

**RTL сломан, хотя заявлен.** В README числится «RTL text support», а в трекере: [#327](https://github.com/firecrawl/pdf-inspector/issues/327) — арабский извлекается в обратном визуальном порядке, «символы печатаются задом наперёд, текст нечитаем»; отдельно «In Hebrew: space after each character»; отдельно просто «RTL Support». Если у вас арабский или иврит — не берите.

**CJK местами рассыпается:** «CJK text becomes U+FFFD on UniGB-UCS2-H Type0 fonts without ToUnicode».

**Регрессии.** «0.1.7 regression: six consecutive pages lose most of their text (0.1.6 extracted them)» и «Regression: pages with extractable text now return empty markdown (bisected)». Проект едет очень быстро — 447 коммитов за полгода, — и качество прыгает между версиями. Закрепляйте версию и проверяйте на своём корпусе после каждого обновления.

**Таблицы:** слипание соседних строк, когда содержимое ячейки переносится; перепутанные ячейки у повёрнутых заголовков колонок.

> [!danger] Была уязвимость: DoS через вложенные объекты PDF
> [Issue #310](https://github.com/firecrawl/pdf-inspector/issues/310): единственная зависимость по разбору PDF, `lopdf` версии 0.41.0, подвержена **RUSTSEC-2026-0187** — переполнение стека через глубоко вложенные объекты. PDF-файл размером ~21 КБ роняет процесс через `SIGABRT`, который **нельзя перехватить** (`catch_unwind` не помогает, это не паника). Публичный PoC идёт вместе с advisory. Достижимо через обычные точки входа: `process_pdf`, `process_pdf_mem`, `classify_pdf`.
>
> **Проверено: в актуальной версии починено.** `Cargo.toml` в `1.14.1` тянет `lopdf ^0.42.0` с исправлением. Затронуты версии по `0.1.7` включительно. Сама issue при этом до сих пор открыта.
>
> Для инструмента, который по замыслу жуёт PDF из недоверенного интернета, это ровно тот класс проблем, который надо держать в голове: **ставьте только 1.14.1 или новее и не закрепляйтесь на старых версиях**.

## Установка по системам

Ядро — Rust; наружу торчат CLI (`pdf2md`, `detect-pdf`), крейт, колесо Python, пакет npm и сборка WebAssembly для браузера. Готовые бинарники есть для x86_64 и aarch64 — **под 32-битный ARM ничего не собрано**.

### Gentoo (основная система)

Ebuild'а в дереве нет, ставим мимо Portage. Для владельца, который и так всё компилирует, это привычный путь:

```bash
# CLI и библиотека из исходников
sudo emerge -av dev-lang/rust        # если ещё нет
cargo install pdf-inspector          # даст pdf2md и detect-pdf в ~/.cargo/bin

# или привязка к Python
python3 -m venv ~/.venvs/pdf && ~/.venvs/pdf/bin/pip install pdf-inspector
```

Колесо `manylinux_2_17_x86_64` встанет и на Gentoo с glibc. Если система на musl — колеса нет, собирайте через `maturin` или ставьте крейт.

### Debian / Ubuntu

```bash
sudo apt install -y python3-pip
pip install pdf-inspector            # готовое колесо, сборка не нужна
```

Для Node.js: `npm i @firecrawl/pdf-inspector` — есть бинарники и под glibc, и под musl (`linux-x64-gnu`, `linux-x64-musl`, `linux-arm64-gnu`, `linux-arm64-musl`).

### Arch

```bash
sudo pacman -S python-pip rust
pip install pdf-inspector --break-system-packages   # либо в venv, что правильнее
```

В AUR пакета нет (проверил — поиск даёт ноль результатов), так что `cargo install pdf-inspector` для CLI.

### Entware (ASUS RT-AX56U)

> [!caution] Готовых сборок нет, но случай не безнадёжный
> Роутер на **armv7**, а колёс и npm-бинарников под 32-битный ARM никто не собрал: есть только `x86_64` и `aarch64`. Пакета в репозитории Entware, разумеется, тоже нет.
>
> Отличие от тяжёлых проектов в том, что здесь это **один статический бинарник на Rust без ML-моделей и внешних сервисов**. Кросс-компиляция реалистична:
> ```bash
> # на десктопе
> rustup target add armv7-unknown-linux-musleabihf
> cargo build --release --target armv7-unknown-linux-musleabihf --bin pdf2md
> scp target/armv7-unknown-linux-musleabihf/release/pdf2md router:/opt/bin/
> ```
> Я это не проверял — нужен собранный кросс-тулчейн, и упереться можно в зависимости вроде `rayon`. Но 256 МБ flash тут не помеха: бинарник маленький, а по ОЗУ разбор одного PDF укладывается в десятки мегабайт.

## Когда брать, а когда нет

**Берите, если** у вас конвейер, где PDF приходят пачками и большая часть из них — нормальные текстовые (отчёты, статьи, счета, договоры, документация). Тогда это почти бесплатный по времени фильтр перед дорогим OCR, и Markdown на выходе сразу годится, чтобы скормить его LLM. Скорость настоящая: десятки миллисекунд на многостраничный документ.

**Не берите, если** основная масса документов — сканы и фотографии (он их просто не умеет), если нужен арабский или иврит (сломано), или если нужна стабильность — проект переписывается на ходу и уже ловил регрессии, теряющие текст целых страниц.

**Разумный компромисс:** поставить `pdf-inspector` первым этапом ради классификации (`classify_pdf` — единицы миллисекунд, риска почти нет), а извлечение доверять ему только для тех файлов, где он вернул `text_based` с высокой уверенностью и `has_encoding_issues=False`. Всё остальное — в OCR.
