# 🔁 Harness² (Google Research) — рекурсивная доводка обвязки ИИ-агента под задачу

**Harness²** («Harness squared»: *Recursive Agent Harnessing for an Open World*) — открытый (Apache-2.0) исследовательский фреймворк команды Google Research к одноимённой [статье на arXiv](https://arxiv.org/abs/2610.14224) (октябрь 2026). Он **автоматически переписывает обвязку (harness) агента** — системный промпт, правила, память, скиллы, субагентов, скрипты, плагины — **под каждую новую задачу**, не трогая веса модели, и копит уроки для следующих задач. Репозиторий: [google-research/harness2](https://github.com/google-research/harness2) (v0.1.0, ~15 тыс. звёзд за две недели).

> [!note] Что это на самом деле (сверено с репозиторием и статьёй)
> - **Не готовый конфиг, а система, которая сама строит и улучшает конфиг** агента под задачу. Восемь компонентов — это **8 «ручек», которые правит модель-улучшатель**; в базовой обвязке их файлы **пустые** (`<!-- c1 system prompt. EMPTY in v0 -->`), стартом служит голый OpenCode или Codex.
> - **Статус:** исследовательский код к статье; README: «This is **not an officially supported Google product**». Сведений о том, что обвязка используется внутри Google, в материалах нет.
> - **Охват:** цель — задачи «открытого мира», не виденные при проектировании обвязки; релиз поддерживает **три бенчмарка**: JobBench, LAB (юридические задачи), WorkBuddy-Bench (офис, веб, код).
> - **Стоимость:** код под Apache-2.0, но всё, кроме демо, гоняет модели через **Vertex AI** (Google Cloud) и **платно**: «Model-backed runs incur API costs; start with a small task selection».

## Идея: обвязка важнее, чем кажется

**Harness** — всё вокруг модели, что делает её агентом: промпты, инструменты, память, скиллы, оркестрация. **Harnessing** — оптимизация этой обвязки. Авторы автоматизируют её на двух уровнях рекурсии при **замороженных весах**:

- **Рекурсия уровня задачи — шаг Propose–Probe–Compose:**
  1. **Propose** — редактор предлагает правки обвязки: «инвариантные» (общие) и предметные (domain).
  2. **Probe** — каждую кандидат-обвязку **реально прогоняют на той же задаче**.
  3. **Compose** — композитор собирает итоговую обвязку из **контраста между прогонами**: что изменилось в поведении агента от правки. Правильного ответа (ground truth) для этого **не нужно** — в этом главная новизна.
- **Рекурсия уровня обвязывания:** после задачи «рефлектор» сохраняет принятую обвязку и **подкреплённые фактами уроки** в библиотеку по предметной области — она направляет доработку на следующих задачах.

**Масштабирование (`--k`):**

| Режим | Что делает |
| :--- | :--- |
| `--k 1` | один шаг Propose–Probe–Compose |
| `--mode parallel --k K` | K общих + K предметных кандидатов, K композиций — «шире» |
| `--mode sequential --k K` | K шагов подряд, обвязка и улики переносятся дальше — «глубже» |

**Результаты из статьи:** один шаг улучшает **GLM-5** и **Gemini 3.5 Flash** относительно их базовых обвязок — до **+11,5 пункта** на WorkBuddy-Bench, **+4,5** на JobBench и **+11,8 п. п.** доли частично пройденных задач на LAB; больший бюджет `k` даёт дальнейший рост.

## Восемь компонентов обвязки

Обвязка — дерево файлов. Для исполнителя OpenCode:

| № | Путь | Что это | Когда в контексте |
| :--- | :--- | :--- | :--- |
| c1 | `systemprompt.md` | роль и порядок работы | **всегда** |
| c2 | `guardrails.md` | постоянные правила (ограничения) | **всегда** |
| c3 | `LongTermMEMORY.md` | долговременные факты предметной области | **всегда** |
| c4 | `tool_descriptions/tool_guidance.md` | как пользоваться инструментами | **всегда** |
| c5 | `sub_agents/<имя>/AGENT.md` | субагент (`mode: subagent`) | в **своём** контексте, возвращает текст |
| c6 | `skills/<имя>/SKILL.md` | переиспользуемый сценарий (`name:` = имя папки, `description:`) | **по требованию** |
| c7 | `scripts/<имя>.py` | детерминированный помощник | по требованию, через bash |
| c8 | `plugin/<имя>.ts` | плагин OpenCode | **всегда зарегистрирован, действует внутри цикла инструментов** |

Для **Codex** то же самое ложится на `AGENTS.md` (вшивается в каждый ход), `.agents/skills/`, `scripts/` и хуки в `.codex/hooks.json` — в формате хуков Claude Code; суммарный «всегда включённый» текст ограничен ~24 тыс. символов.

## Самое полезное: правила, по которым улучшатель правит обвязку

Это можно забрать себе без всякого фреймворка — инструкция модели-улучшателю из `harness2/core/prompts.py` — по сути **сжатый гайд по устройству обвязки** для Claude Code, OpenCode, Codex:

- **Всегда включённый текст — самый дорогой вариант.** Каждое его слово занимает контекст в каждом прогоне и конкурирует с бюджетом вывода агента; самый дорогой провал — агент рассуждает, пока бюджет не кончится, и не выдаёт ничего. Больше прозы делает его **вероятнее**. Компонент по требованию ничего не стоит, пока не вызван.
- **Порядок предпочтения при добавлении знаний:**
  1. **Скилл** — для всего, у чего есть узнаваемый триггер (тип документа, формат, повторяющаяся ситуация). Форма по умолчанию для новых инструкций.
  2. **Скрипт** — для детерминированной операции, которую агент делал руками неправильно или медленно.
  3. **Субагент** — ровно для одной формы задач: **большой вход, маленький ответ** (он не видит основной диалог и возвращает текст). Если ответ размером со вход — плохая сделка.
  4. **Плагин/хук** — для повторяющихся механических проблем **внутри цикла инструментов**: обрезать шумный или огромный вывод инструмента; добавлять подсказку после повторяющейся сигнатуры ошибки; ограничивать «убегающий» инструмент; проверять запись сразу после неё. «Прозу можно не дочитать, хук — нельзя», и в контексте он не стоит ничего.
  5. **Всегда включённый текст** — последним и только для короткого правила, которое действительно касается каждого прогона. Добавили — вырежьте что-то другое.
- **У каждого скилла должна быть строка-триггер** в всегда включённом тексте: «When <ситуация>, load the `<имя>` skill». Безымянный скилл никогда не открывается — «строка и делает его существующим». (Самое частое нарушение у модели.)
- **Каждый упомянутый скрипт должен существовать** и лежать рядом со скиллом (`skills/<имя>/scripts/…`), иначе его молча отбросят.
- **Обвязка меняет, КАК агент работает, но не ФОРМУ результата.** Если задача задала поля, колонки, разделы, порядок — нельзя добавлять «поясняющие колонки» или переименовывать заголовки для наглядности: следующий потребитель завязан на точные имена. Значение сдавать **значением**, а не формулой или описанием расчёта.
- **«Ничего не менять» — законный ответ** (`KEEP_BASE`), если улики не требуют правок: адаптация без оснований тратит контекст и ничего не даёт.

Эти принципы совпадают с тем, как устроены скиллы и хуки в Claude Code: описание скилла — его триггер, хук нельзя проигнорировать, субагент нужен для дорогого поиска с коротким ответом.

## Как устроен запуск

- **Исполнитель (solver):** **OpenCode** (по умолчанию) или **Codex** (`--substrate cx`) с Gemini на Vertex AI; для Codex в комплекте `harness2-bridge` — локальный LiteLLM-прокси с Responses API.
- **Улучшатель (improver):** Gemini или **Claude на Vertex**; в коде есть канал через **Claude Code CLI** — `claude -p --dangerously-skip-permissions --append-system-prompt …`.
- **Судья (judge):** отдельная модель оценивает результат по рубрикам бенчмарка.
- **Безопасность:** у исполнителя **неограниченный доступ в сеть, а Codex запускается с выключенной песочницей**. В документации отмечено: при проверке релиза агент Codex на JobBench **сам скачал рубрику оценки своей задачи** с Hugging Face. Перед оценкой нужно закрыть хосты `huggingface.co`, `hf.co`, `github.com`, `raw.githubusercontent.com`; `harness2-bridge --host 0.0.0.0` слушает все интерфейсы.

## Установка и проба

Требования: **Linux, Python 3.12** (пакет поддерживает 3.12–3.13), **uv**; для бенчмарков с моделями — **Node.js 20+**, **Google Cloud CLI** с доступом к моделям в Vertex AI, для LAB — Pandoc и Poppler, для WorkBuddy — Docker.

```bash
git clone https://github.com/google-research/harness2 && cd harness2
uv venv --python 3.12 .venv && source .venv/bin/activate
uv pip install -e '.[render]'

# демо без ключей: обе схемы рекурсии на детерминированных «редакторах»
harness2-demo --output runs/demo --k 2

# дальше — уже платно (Vertex AI)
cp .env.example .env          # GOOGLE_CLOUD_PROJECT, HARNESS2_SOLVER/IMPROVER/JUDGE_MODEL
gcloud auth application-default login
harness2-setup lab && harness2-check --bench lab
harness2 --bench lab --k 1 --mode parallel --only-domains antitrust-competition --max-tasks 1 --dry-run
```

| Система | Python 3.12 / uv | Node.js 20+ | Pandoc, Poppler (LAB) | Docker (WorkBuddy) | gcloud |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Gentoo** (OpenRC) | `dev-python/uv`; Python 3.12 uv скачает сам | `net-libs/nodejs` | `app-text/pandoc-bin`, `app-text/poppler[utils]` | `app-containers/docker` + `rc-update add docker default` | в основном дереве нет — архив `google-cloud-cli` от Google или оверлей |
| **Debian / Ubuntu** | инсталлятор astral | NodeSource/`nvm` (в Debian 13 — 20.x, хватает) | `apt install pandoc poppler-utils` | `docker.io` или репозиторий Docker | репозиторий `packages.cloud.google.com` |
| **Arch** | `pacman -S uv` | `pacman -S nodejs npm` | `pacman -S pandoc-cli poppler` | `pacman -S docker` | AUR `google-cloud-cli` |
| **Entware** (роутер) | неприменимо: исследовательский стенд с Docker и облачными моделями роутеру не по силам | | | | |

## Кому это нужно

- **Исследователям агентов** и тем, кто строит свой агент поверх OpenCode/Codex и хочет **автоматически подбирать обвязку** под класс задач — с бюджетом на облачные модели.
- **Всем остальным** полезнее не запускать фреймворк, а **забрать правила из раздела выше** в свой `CLAUDE.md`/`AGENTS.md`-подход: скилл с триггером вместо простыни в системном промпте, хук вместо «пожалуйста, не забывай», субагент только для «большой вход — короткий ответ».
