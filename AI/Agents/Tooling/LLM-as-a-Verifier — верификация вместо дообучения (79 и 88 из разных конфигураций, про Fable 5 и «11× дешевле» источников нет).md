## 🧠 В чём на самом деле новизна

Пост описывает метод как «сгенерь несколько вариантов и выбери лучший». Это best-of-N — приём, известный годами, и сам по себе на статью не тянет. Настоящий вклад в другом. Из аннотации:

> *«Unlike standard LM judges that prompt LLMs to produce discrete scores for candidate solutions, LLM-as-a-Verifier computes the expectation over the distribution of scoring token logits to generate continuous scores.»*

То есть модель **не спрашивают** «поставь оценку от 1 до 10». Вместо этого берут распределение логитов по токенам-оценкам и считают по нему **матожидание** — получается непрерывная оценка вместо дискретной. Это даёт лучшую разделимость хороших и плохих решений и более калиброванное сравнение.

Дальше авторы масштабируют верификацию по трём осям:

1. **гранулярность оценки** — чем больше градаций, тем чище разделение;
2. **повторные прогоны** оценивания;
3. **декомпозиция критериев** — разбор решения по отдельным критериям.

Есть и алгоритмическая часть: вместо сравнения всех пар за `O(N²)` применяется **Probabilistic Pivot Tournament** — каждый кандидат сравнивается только с небольшим набором опорных, что даёт `O(Nk)`.

> [!note] Формулировка самих авторов
> Они позиционируют верификацию как **новую ось масштабирования** наряду с предобучением, постобучением и вычислениями на инференсе. Это заметно содержательнее, чем «тулза, которая выбирает лучший ответ».

## 📊 Числа: что в таблице на самом деле

Раздел README **Self-Verification (Terminal Bench 2.1)**: генерируется 5 траекторий `mini-swe-agent` на задачу моделью `deepseek-v4-flash`, и **та же модель** выступает верификатором собственных прогонов.

| Конфигурация | Pass@1 | LLM-as-a-Verifier | Oracle |
| :--- | ---: | ---: | ---: |
| Best-of-3 | 79,4 % | **86,5 % ± 1,1 %** | 92,1 % |
| Best-of-5 | 78,7 % | **88,0 % ± 0,6 %** | 96,6 % |

Пост взял «79» из первой строки, «88» — из второй. Правильные пары дают прирост **+7,1** или **+9,3** пункта.

> [!tip] Колонка, которую пост выкинул, — самая честная
> **Oracle** — это результат при идеальном выборе, то есть потолок метода. Считаем, какую долю доступного запаса верификатор реально забирает:
>
> - Best-of-3: +7,1 из возможных 12,7 → **56 %**
> - Best-of-5: +9,3 из возможных 17,9 → **52 %**
>
> То есть примерно половину. Это хороший результат для метода без дообучения, но это не «модель стала лучше», а «из уже сгенерированных вариантов удалось выбрать удачнее в половине случаев, когда выбор вообще был».
>
> Отброшены и погрешности: ±1,1 % и ±0,6 %.

## 🧾 Статья и README — это разные наборы результатов

Неочевидное, но важное расхождение:

| | В статье (06.07.2026) | В README (обновлён 20.08.2026) |
| :--- | :--- | :--- |
| Бенчмарк по терминалу | **Terminal-Bench V2** | **Terminal-Bench 2.1** |
| Верификатор | в основном Gemini 2.5 Flash | та же модель, что генерировала (self-verification) |
| DeepSeek | упоминается **2 раза** | основной герой эксперимента |

Проверил полный текст статьи: сочетания «Terminal-Bench 2.1» там **нет ни разу**, как нет «Fable», «cheaper», «11×» и «cost-effective».

Вывод: цифры, на которые опирается пост, — это **более поздний эксперимент из README**, не входящий в рецензируемую статью. Он не хуже автоматически, но статус у него другой, и подавать его как «доказано Стэнфордом» некорректно.

Из статьи, для сравнения, вот что заявлено с верификатором Gemini 2.5 Flash:

| Бенчмарк | Базовая модель | Pass@1 | С верификатором | Oracle |
| :--- | :--- | ---: | ---: | ---: |
| Terminal-Bench V2 | GPT-5.5 (Best-of-5) | 83,1 % | **86,5 %** | 92,1 % |
| SWE-Bench Verified | Opus 4.5 / 4.6 / Gemini 3 Flash (Best-of-3) | 76,1 % | **78,2 %** | 84,4 % |
| MedAgentBench | Claude Opus 4.8 (Best-of-5) | 70,2 % | **73,3 %** | 75,0 % |

Прирост скромнее: от **+2,1** до **+3,4** пункта. Именно эти числа прошли рецензирование.

## 💰 Про цену: чего пост не посчитал

Утверждения «в 11 раз дешевле Fable 5» я не нашёл нигде, зато арифметика метода очевидна и говорит об обратном по абсолютным затратам:

- сгенерировать **N решений** вместо одного — это N-кратная стоимость генерации;
- затем прогнать **верификацию**, причём с повторными оценками и декомпозицией критериев — ещё запросы сверху;
- PPT снижает число сравнений с `O(N²)` до `O(Nk)`, а префиксный кэш даёт, по README, **≈3,4× меньше некэшированных входных токенов**.

То есть оптимизации нацелены на то, чтобы верификация не стоила квадратично, а не на то, чтобы всё вместе вышло дешевле одного вызова сильной модели. Экономия возможна в сценарии «дешёвая модель × N + верификация вместо одного вызова дорогой» — но конкретной цифры «11×» в источниках проекта нет.

## ▶️ Что это на практике

Библиотека на Python, ставится из репозитория, есть плагин для Claude Code ([TurboAgent](https://github.com/llm-as-a-verifier/TurboAgent)). Сценарии из README:

```bash
python scripts/run.py                 # покажет список бенчмарков
python scripts/run.py swe_bench
python scripts/run.py swe_bench --pivots 2 --n-evaluations 8 --seed 0 --max-workers 50
python scripts/run_bo5.py             # воспроизведение self-verification
```

> [!warning] «Воспроизведение» здесь означает не то, что кажется
> Траектории агентов **лежат в репозитории готовыми** (`data/`). Скрипты только **оценивают** заранее сгенерированные прогоны, а не запускают агента с нуля. Для воспроизведения self-verification достаточно `DEEPSEEK_API_KEY`. Это законная методика, но это не «прогнал бенчмарк целиком».

Применимость к своим задачам — через API библиотеки: даёшь пул траекторий и задачу, получаешь выбор лучшей. Полезно там, где есть **готовый пул кандидатов** и внятные критерии оценки.

| Система | Установка |
| :--- | :--- |
| **Gentoo** (основная) | Python-пакет из репозитория в venv; нужен ключ к API модели-верификатора |
| **Debian / Ubuntu** | `pipx`/venv (PEP 668), далее установка из клона |
| **Arch** | venv либо `uv` |
| **Entware / RT-AX56U** | ❌ Неприменимо — это обвязка над облачными API и тяжёлые прогоны |

## 💡 Итог

- Работа серьёзная: сильный состав авторов, статья на arXiv, MIT, воспроизводимые скрипты. Идея «верификация как ось масштабирования» содержательна.
- Пост **обесценил метод**, сведя его к best-of-N. Реальная новизна — непрерывные оценки через матожидание по логитам плюс масштабирование по трём осям.
- **Числа склеены из разных конфигураций**, отброшены погрешности и колонка Oracle. Реально метод забирает около **половины** доступного запаса.
- **«Лучше Fable 5» и «в 11 раз дешевле» не подтверждаются ничем** — ни README, ни сайтом, ни документацией, ни статьёй.
- Цифры про DeepSeek — из README, а не из статьи; в рецензируемой части прирост скромнее: +2,1…+3,4 пункта.
