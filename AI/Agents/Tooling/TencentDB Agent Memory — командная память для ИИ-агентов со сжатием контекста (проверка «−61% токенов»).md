# TencentDB Agent Memory

> [!info] Коротко
> Реальный, крупный и живой опенсорс-проект Tencent Cloud (MIT, 20.6k ★): «память» для ИИ-агентов из четырёх активов — Chat Memory, Skill, Wiki, CodeGraph — плюс **сжиматель контекста**, который действительно есть в коде и сделан неглупо.
>
> Но заголовок «сокращаем расход токенов на 60%» — это **лучшее число из четырёх бенчмарков**, снятое на поисковом бенчмарке WideSearch. На кодинге (SWE-bench) заявлено −33%, и даже это число не сходится с собственной арифметикой проекта. А главное — экономия считается **только по основной модели**: сжатие работает за счёт второй LLM, которая жжёт свои токены и в таблице не учтена.

---

## Что это на самом деле

Ссылка из поста (`github.com/Tencent/TencentDB-Agent-Memory`) отдаёт **301 редирект** — проект живёт под организацией `TencentCloud`, а не `Tencent`. Забавно, что и сам README до сих пор предлагает клонировать старый URL, хотя ещё 24 июля 2026 был коммит `docs(install): fix repo URL to TencentCloud/`.

Это не библиотека и не плагин, а **стек из четырёх сервисов в Docker**:

| Сервис | Порт | Что делает |
| :--- | :---: | :--- |
| Memory Core | `8420` | хранение и обработка памяти, auth, data plane для skill/RAG |
| Panel UI (Memory Hub) | `8125` | веб-панель: команды, агенты, ревью и выдача активов |
| Knowledge | `8424` | Wiki и CodeGraph |
| Proxy | `8096` | прозрачный прокси LLM-запросов (Anthropic + OpenAI протоколы) |

Идея: агент (Claude Code, CodeBuddy, OpenClaw, Hermes) ходит не напрямую в модель, а через `MemoryProxy`. Тот на входе подмешивает в системный промпт нужные навыки и память, на выходе — асинхронно вытаскивает из диалога новые знания.

Память слоистая: **L0** (сырой диалог) → **L1** (факты, предпочтения, ограничения) → **L2** (сцены вокруг задачи) → **L3** (персона, долгосрочный профиль). Обычно в контекст едут L2/L3, а за конкретными фактами система падает в L1/L0 через BM25 + вектора + RRF.

> [!note] Что проект честно признаёт сам
> В разделе Acknowledgements прямо написано, что CodeGraph **использует код** проекта [colbymchenry/codegraph](https://github.com/colbymchenry/codegraph), управление скиллами — **часть кода Skill из Hermes Agent** (Nous Research), а идея Wiki взята из гиста Карпаты про «LLM Wiki». Это редкая для корпоративного релиза честность, и её стоит зачесть в плюс.

## Откуда взялся «−61%» и почему его трудно найти

Главная странность: **в README, который вы увидите на главной странице репозитория, этой таблицы нет.**

Дефолтная ветка репозитория — `feat/server_team` (сама по себе странность: фича-ветка как дефолтная, со сквошнутой историей в 10 коммитов против 107 в `main`). В её README в разделе Benchmark только PersonaMem. Таблица с токенами живёт в `main`:

| Способность | Бенчмарк | OpenClaw | + плагин | Δ успеха | Токенов было | Стало | Δ токенов |
| :--- | :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| Короткая память | WideSearch | 33% | **50%** | **+51.52%** | 221.31M | **85.64M** | **−61.38%** |
| Короткая память | SWE-bench | 58.4% | **64.2%** | **+9.93%** | 3474.1M | **2375.4M** | **−33.09%** |
| Короткая память | AA-LCR | 44.0% | **47.5%** | **+7.95%** | 112.0M | **77.3M** | **−30.98%** |
| Долгая память | PersonaMem | 48% | **76%** | **+59%** | — | — | — |

Все три бенчмарка — **настоящие и уважаемые**, это важно: [WideSearch](https://widesearch-seed.github.io/) (ICLR 2026, широкий сбор информации в таблицу), [AA-LCR](https://artificialanalysis.ai/articles/announcing-aa-lcr) (Artificial Analysis, рассуждения по 100k+ токенов документов), PersonaMem (COLM 2025, ~6000 вопросов по историям на 32k/128k/1M токенов). Проект не выдумывал себе удобные метрики — и это в его пользу.

### Почему именно WideSearch дал 61%

Это не случайность, а свойство механизма. Сжиматель работает **только с результатами вызова инструментов**. В поисковой задаче результаты инструментов — это выкачанные веб-страницы: огромные, шумные и прекрасно ужимающиеся в одну строчку. В кодинге результат инструмента — это чаще diff, вывод компилятора или содержимое файла, где выкидывать нечего. Отсюда и разрыв: −61% там, где мусора много, и −33% там, где мало.

**Для кодинг-агента ориентироваться надо на цифру SWE-bench, а не на заголовочную.**

### И даже −33.09% не сходится

Открытый [issue #813](https://github.com/TencentCloud/TencentDB-Agent-Memory/issues/813) (5 августа 2026, без ответа команды) — это чистая проверка таблицы на самосогласованность, без всяких прогонов:

```
(3474.1 − 2375.4) / 3474.1 = 31.63%   ← считается из напечатанных чисел
                             33.09%   ← опубликовано
                             −1.46 п.п.
```

Все остальные строки таблицы сходятся точно. Чтобы получить −33.09%, значение «до» должно было быть ≈3550.1M. Похоже, строку SWE-bench забыли обновить при правке бенчмарков 13 мая 2026 (коммит `3cc6d2a` «docs: fix benchmark data»), — и та правка, кстати, поменяла WideSearch очень сильно: было `8.5%→12%` при `174.31M→63.46M`, стало `33%→50%` при `221.31M→85.64M`.

> [!warning] Базовая линия — OpenClaw, а не Claude Code
> Вся таблица — это «OpenClaw против OpenClaw + плагин». Если вы подключаете память к Claude Code через `MemoryProxy`, это **другой путь интеграции**, для которого опубликованных замеров нет вообще.

## Как устроен сжиматель (по коду, а не по README)

Механика собрана из трёх частей, и она честно неплохая.

**1. Суммаризатор результатов инструментов** (`offload_server/prompts/l1-prompt.ts`). Каждая пара «вызов инструмента + результат» уходит отдельной LLM, которая возвращает JSON: краткое описание вызова, `summary` до 200 символов и — ключевое — **`score` от 0 до 10**, то есть «насколько summary способна заменить оригинал». Параметры обрезаются до 500 символов, результат — до 2000.

**2. Карта задачи в Mermaid** (`prompts/l2-prompt.ts`). Та самая «тезисная карта». Системный промпт (на китайском) требует от модели построить «когнитивный автомат состояний» в виде `flowchart TD`, где форма узла кодирует тип действия, а статус — `done|doing|paused|blocked`. Отдельно предусмотрены «когнитивные надгробия» — узлы для тупиковых решений, чтобы агент не наступал на те же грабли. Сверху метаданные: `taskGoal`, `progress` 0–100, таймстемпы. Размер файла велено держать **в пределах 4000 символов**.

**3. Четыре уровня сжатия** (`compact/compressor.ts`), выбираются по доле занятого окна контекста:

| Уровень | Порог | Что делает |
| :--- | :---: | :--- |
| `fastpath` | < 50% | переприменяет уже подтверждённые замены, ничего нового не сжимает |
| `mild` | ≥ 50% | сканирует **первые 70%** сообщений, меняет результаты инструментов на summary — по убыванию score и только пока `score ≥ 4` |
| `aggressive` | ≥ 85% | режет крупные результаты до 2000 символов и удаляет сообщения, защищая «хвост» после последнего сообщения пользователя (минимум 10 сообщений) |
| `emergency` | ≥ 95% | то же жёстче, но Mermaid-карты вынимаются и сохраняются в первую очередь |

Хорошая деталь: в `mild` есть проверка `if (summaryLen >= originalLen) continue` — если summary не короче оригинала, замена не делается. И токены считаются настоящим tiktoken, а не оценкой «символы делить на 4».

## Чем на самом деле платишь

> [!caution] Экономия считается только по основной модели
> В `.env.example` **две независимые группы настроек LLM**:
> - `MEMORY_LLM_BASE_URL` / `_API_KEY` / `_MODEL` — внутренняя модель: суммаризация, построение Mermaid-карт, ingest Wiki;
> - `PROXY_UPSTREAM_URL` / `_API_KEY` / `_MODEL` — та модель, с которой вы реально работаете.
>
> Каждый вызов инструмента вашего агента порождает **дополнительный вызов внутренней модели**. Столбец «токенов стало» в таблице бенчмарков — это расход основной модели. Расход второй модели там не показан.

Это не теория. [Issue #73](https://github.com/TencentCloud/TencentDB-Agent-Memory/issues/73) (22 мая 2026, 11 комментариев, **открыт до сих пор**): пользователь развернул локальную Qwen3.6-27B-FP8 и попытался воспроизвести «OpenClaw vs OpenClaw + плагин». Результат — **разницы в успешности нет, а токенов потрачено больше**.

Ответ мейнтейнера (`Maxwell-Code07`, в тот же день) стоит процитировать по сути: качество извлечения и вызова L1 **чувствительно к способностям модели**, маленькие модели плохо порождают качественные записи памяти, и выгода из-за этого падает. На просьбу опубликовать тестовые скрипты — «оценим внутри, ответим по мере прогресса».

**Прошло почти три месяца. Публичных скриптов бенчмарка нет.** Есть три отдельных обращения от сообщества с просьбой дать воспроизводимый харнесс — [#106](https://github.com/TencentCloud/TencentDB-Agent-Memory/issues/106), #204 и [#812](https://github.com/TencentCloud/TencentDB-Agent-Memory/issues/812), причём в #812 человек уже принёс готовый харнесс. Все открыты.

Практический вывод: если вы собираетесь ставить лёгкую или локальную модель на роль `MEMORY_LLM`, готовьтесь к тому, что экономии не будет вовсе. Механизм окупается только когда суммаризатор достаточно умён, чтобы его summary реально заменяла оригинал.

## Что сломано прямо сейчас

**Claude Code не пишет память.** [Issue #964](https://github.com/TencentCloud/TencentDB-Agent-Memory/issues/964) от 12 августа 2026 — то есть вчера. Полный стек по официальной инструкции, Claude Code через прокси: инъекция работает, авторизация и выбор агента работают, а вот захват диалога — нет. Все счётчики `pipelineWorker` в `/health` по нулям, в панели ноль записей на всех слоях. Память не накапливается вообще. Если вы, как и владелец этой базы знаний, живёте в Claude Code — это блокер, и перед установкой стоит проверить, закрыт ли он.

**Версии разъезжаются.** Релиз в репозитории — v2.0.0 (3 августа 2026), а команда быстрого старта тянет `agentmemory/memory-core:latest`, и на Docker Hub самый свежий тег — **1.0.0**. В npm пакет `@tencentdb-agent-memory/memory-tencentdb` тоже застрял на **1.0.1 от 14 июля**. То есть «поставь одной командой» ставит не то, что описано в README.

**556 открытых issues и PR.** Проект живой — за 12 августа прилетело больше десятка PR от сообщества, — но из сотни последних обращений открыто 83. Внешние патчи копятся быстрее, чем их разбирают.

## Безопасность: сеть и авторизация

> [!danger] Гейт авторизации по умолчанию выключен, а порт открыт наружу
> `start-memory-core.sh` публикует порт как `-p "${MEMORY_CORE_PORT}:8420"` — то есть на **все интерфейсы**, и внутри контейнера слушает `TDAI_GATEWAY_HOST=0.0.0.0`. То же самое у прокси.
>
> При этом `MEMORY_CORE_GATEWAY_API_KEY` в `.env.example` **пустой по умолчанию**, что отключает Bearer-проверку. И это не недосмотр — в комментарии рядом написано прямым текстом: если задать непустой ключ, **прокси перестанет работать**, потому что он этот заголовок не отправляет; «в продакшене ключ нужно будет включить после того, как починят на стороне прокси».
>
> Итог: выбрать между «работает» и «защищено» сейчас нельзя. Любой в вашей локальной сети, кто дотянется до `:8420`, читает и пишет всю командную память.

Более того, открытость наружу — задуманное поведение: в `.env.example` есть переменная `MEMORY_HUB_PROXY_PUBLIC_URL` с комментарием, что она подставляет LAN-адрес, «чтобы с чужого компьютера можно было просто скопировать URL из карточки и подключиться».

**Что делать:** привязывать порты только к петле (`-p 127.0.0.1:8420:8420` и так далее, поправив скрипты запуска) либо закрывать всё файрволом. Наружу — только через SSH-туннель или WireGuard.

Отдельно держите в голове, что через `MemoryProxy` проходит **весь** ваш диалог с моделью, включая содержимое файлов, а `PROXY_UPSTREAM_API_KEY` лежит в конфиге прокси. Это ещё один аргумент не выставлять его в сеть.

## Установка по системам

Основной путь — Docker, три образа под `linux/amd64` и `linux/arm64`. Суммарно **около 817 МБ** (memory-core 236 МБ, memory-hub 392 МБ, memory-proxy 189 МБ). Compose не нужен — скрипты используют обычный `docker run`.

> [!important] Расход ОЗУ я не замерял
> Размеры образов проверены по Docker Hub API, а вот потребление памяти тремя Node-сервисами под нагрузкой — нет. Не переносите сюда чужие цифры и померьте сами перед тем, как ставить на слабую машину.

### Gentoo (основная система)

```bash
# Docker: собирается из исходников, как и всё остальное
sudo emerge -av app-containers/docker app-containers/docker-cli

# OpenRC
sudo rc-update add docker default
sudo rc-service docker start
sudo usermod -aG docker "$USER"   # перелогиниться

git clone https://github.com/TencentCloud/TencentDB-Agent-Memory.git
cd TencentDB-Agent-Memory/deploy/global-images
cp .env.example .env
$EDITOR .env      # заполнить обе группы: MEMORY_LLM_* и PROXY_UPSTREAM_*
./start-all.sh
```

Ядро должно быть собрано с опциями для контейнеров — при сомнениях запустите `dockerd --validate` или проверьте `CONFIG_NAMESPACES`, `CONFIG_CGROUPS`, `CONFIG_OVERLAY_FS`.

Если захочется собирать сервисы из исходников без Docker — нужен `>=net-libs/nodejs-22.16` (в `package.json` стоит `"node": ">=22.16.0"`) и `pnpm`, проект собран как pnpm-workspace.

### Debian / Ubuntu

```bash
sudo apt update && sudo apt install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
```

Дальше — те же четыре команды из блока выше. Если нужен путь без Docker: штатный `nodejs` в Debian 13 и Ubuntu 24.04 **старее 22.16**, ставьте NodeSource или `nvm`.

### Arch

```bash
sudo pacman -S docker
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
```

Сборка из исходников проще всех: `sudo pacman -S nodejs pnpm` даёт свежий Node без плясок.

### Entware (ASUS RT-AX56U)

> [!danger] Не встанет — и даже пытаться не стоит
> Четыре причины, любой достаточно:
> - **Docker'а на Entware нет** в принципе, а проект распространяется образами;
> - **512 МБ ОЗУ** на роутере против трёх Node-сервисов, SQLite и векторного поиска;
> - **armv7**, а образы собраны под `amd64` и `arm64` — 32-битной сборки нет вообще;
> - в Entware Node версии 18, а требуется `>=22.16`.
>
> Роутер здесь может быть только клиентом: пробросить туннель до машины, где стек уже крутится.

## Стоит ли ставить

**Где смысл есть.** Если у вас команда с несколькими людьми и агентами, и вы реально страдаете от того, что каждый новый агент заново изучает проект — управление активами тут сделано серьёзно: владелец, версия, статус, видимость (`private` / `team` / `restricted` / `agent`), ACL, привязка к конкретному агенту. Это заметно взрослее, чем «свалить всё в вектора». Сама модель «памяти как инвентаря, который выдают агенту под роль» — хорошая, и её стоит подсмотреть, даже если сам стек не ставить.

**Где смысла мало.** Если вы один человек с Claude Code:

- заявленная экономия на кодинге — треть, а не 60%, и та не воспроизводится из собственных чисел проекта;
- вы платите токенами второй модели, которых в расчёте нет;
- захват диалога из Claude Code прямо сейчас сломан (#964);
- четыре сервиса и ~817 МБ образов ради этого — тяжёлая цена;
- гейт авторизации выключен и включить его нельзя без поломки прокси.

**Разумная позиция:** подождать, пока закроют #964 и опубликуют харнесс из #812, а пока — прочитать `l2-prompt.ts` и утащить идею Mermaid-карты задачи себе. Она хороша сама по себе и не требует ставить ничего.
