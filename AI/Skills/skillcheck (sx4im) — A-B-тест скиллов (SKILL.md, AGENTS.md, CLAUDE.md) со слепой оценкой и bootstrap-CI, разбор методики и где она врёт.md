# skillcheck — A/B-тест скиллов агента

**Что это.** CLI на Node.js, который берёт любой Markdown-файл-инструкцию (`SKILL.md`, `AGENTS.md`, `CLAUDE.md`, `.cursorrules`) и ставит на нём контролируемый эксперимент: генерирует задачи по заявленной теме скилла, решает каждую задачу **дважды** — с подсунутым скиллом и без него, — оценивает результаты **вслепую** и выдаёт вердикт `HELPS` / `PLACEBO` / `HARMS` с 95%-доверительным интервалом.

Идея правильная и, честно говоря, давно назревшая: скиллы пишут и публикуют пачками, а измеряет их эффект почти никто. Но между «идея правильная» и «цифре можно верить» здесь лежит несколько существенных оговорок — разбор ниже.

## 2. Как устроен прогон

Пять стадий, каждая — отдельный вызов модели:

```
normalize → generate → run → grade → score
```

1. **Normalize.** Файл парсится, из YAML-фронтматтера достаётся «заявленная тема» (`domain:`, `description:`, `when_to_use:`), иначе — первый заголовок, иначе — имя файла. Соседние файлы (`scripts/`, `references/`) **записываются в отчёт, но не исполняются и не подгружаются**.
2. **Generate.** Генератор задач видит **только тему**, никогда — тело скилла. Это защита от утечки инструкций в задания, и она честная. Просит `2N` задач, берёт `N`. Температура 0.4, потолок 8000 токенов, три попытки на невалидный JSON.
3. **Run.** Каждая задача × `K` испытаний × 2 плеча. Температура **0.7**, потолок ответа **2048 токенов**, рассуждения выключены (`enable_thinking: false`).
4. **Grade.** Все выходы перемешиваются и оцениваются по критерию задачи. Оценка — число 0..1, зачёт при **`score >= 0.5`**. Если грейдер проигнорировал JSON-режим, есть эвристический разбор текста с учётом отрицаний.
5. **Score.** Парный bootstrap на 1000 итераций (сид фиксирован — 1337), квантили 2.5% и 97.5% дают 95%-интервал. Вердикт: `helps`, если весь интервал выше нуля; `harms` — если весь ниже; `placebo` — если пересекает.

### Уровни усилий

| Уровень | Задач × испытаний | Наблюдений | Время | Шаг измеримого эффекта |
| :--- | :---: | :---: | :---: | :---: |
| Quick | 2 × 1 | 2 | ~30 с | **50 п.п.** |
| Standard | 3 × 2 | 6 | 1–2 мин | **16,7 п.п.** |
| Thorough | 5 × 3 | 15 | 3–4 мин | **6,7 п.п.** |
| Максимум вручную | 50 × 10 | 500 | долго и дорого | 0,2 п.п. |

> [!warning] Шаг измеримого эффекта — это не придирка
> Наблюдаемый эффект считается как разница долей: `mean(с_скиллом) − mean(без_скилла)`. При `N` наблюдениях он может принимать только значения, кратные `100/N`. На уровне **Quick** прибор физически способен показать только −100, −50, 0, +50 или +100 п.п. Любая «точная сводка» на двух наблюдениях — это шум.
> Дефолт `--trials` равен 3, и сама методичка проекта прямо пишет: *«single-trial results are not accepted as launch-quality evidence»*. То есть уровень Quick авторы сами не считают доказательством.

## 3. Команды

```bash
skillcheck                                   # интерактив: файловый пикер + выбор усилия
skillcheck check ./SKILL.md                  # прямой прогон
skillcheck check ./SKILL.md --tasks 5 --trials 3 --json
skillcheck check ./SKILL.md --explain        # разбор по задачам + контрастные примеры выводов
skillcheck check ./SKILL.md --output res.json
skillcheck eval ./SKILL.md                   # сырой JSON-оценщик
skillcheck verify res.json --sample 3        # независимо перемерить опубликованный результат
skillcheck corpus run --corpus corpus.json   # пачкой
skillcheck rot --results ./results           # найти скиллы, переставшие помогать
skillcheck matrix ./SKILL.md                 # сравнить скилл на нескольких моделях/провайдерах
skillcheck setup / logout                    # ключ
```

Ограничители: `--tasks` ≤ 50, `--trials` ≤ 10, опечатка в опции отвергается, а не игнорируется молча. Есть `--concurrency N` (появился в 0.9.0, ускоряет прогон на 60–75%).

> [!note] `matrix` и `--concurrency` в списке команд README отсутствуют
> Обе появились в 0.9.0 (23 июля 2026) и описаны только в `CHANGELOG.md` и в `--help`. Если читать один README, о них не узнаешь.

Флаг `--explain` ничего не стоит дополнительно: он переиспользует уже полученные выводы, а не делает новые вызовы.

## 4. Главное ограничение: это тест не агента, а чат-комплишена

Это не претензия автора-скептика — это написано в `METHODOLOGY.md` самого проекта, в разделе «Known Limitations», и стоит того, чтобы вынести в начало:

> [!danger] Что skillcheck не измеряет
> - **Срабатывание триггера.** Скилл всегда впихивается в системный промпт принудительно. Вопрос «сработает ли скилл, когда надо» — вне области видимости v1. А для Claude Code это ровно половина ценности скилла: поле `description` во фронтматтере и есть то, по чему агент решает подтянуть скилл.
> - **Ресурсы скилла.** `scripts/`, `references/`, вложенные `.md` — только фиксируются в отчёте, не исполняются. Скилл вроде `claude-video`, вся суть которого в `frames.py`, будет измерен по одному лишь тексту `SKILL.md`.
> - **Прогрессивное раскрытие.** Механика «сначала короткий фронтматтер, тело подгружается по требованию» не воспроизводится вообще: тело всегда целиком в контексте.
> - **Инструменты и файловая система.** Плечо `with_skill` — это один вызов chat-completion на 2048 токенов ответа. Ни Bash, ни Read, ни Edit, ни многошаговой петли. Скилл, который говорит агенту «сначала запусти тесты, потом правь», проверить нечем.
> - **Рассуждения.** `enable_thinking: false` — скиллы, рассчитанные на ризонинг-модели, тестируются в режиме без ризонинга.

Вывод простой: skillcheck честно отвечает на вопрос **«помогает ли этот текст модели, когда она его уже прочитала»**. Он не отвечает на вопрос **«помогает ли этот скилл моему агенту»**. Для чисто текстовых скиллов-инструкций (стиль кода, правила ревью, доменные памятки — вроде [Ponytail — скилл против «графомании» в коде](Ponytail%20%E2%80%94%20%D1%81%D0%BA%D0%B8%D0%BB%D0%BB%20%D0%BF%D1%80%D0%BE%D1%82%D0%B8%D0%B2%20%C2%AB%D0%B3%D1%80%D0%B0%D1%84%D0%BE%D0%BC%D0%B0%D0%BD%D0%B8%D0%B8%C2%BB%20AI-%D0%B0%D0%B3%D0%B5%D0%BD%D1%82%D0%BE%D0%B2%20%D0%B2%20%D0%BA%D0%BE%D0%B4%D0%B5.md) или [epstein.md](../Prompts/epstein.md%20%28Shipper%29%20%E2%80%94%20%D0%B3%D0%B8%D0%B3%D0%B0%D0%BD%D1%82%D1%81%D0%BA%D0%B8%D0%B9%20.md-%D1%84%D0%B0%D0%B9%D0%BB%20%D0%BF%D1%80%D0%BE%D1%82%D0%B8%D0%B2%20%C2%ABAI-%D1%81%D0%BB%D0%BE%D0%BF%D0%B0%C2%BB%20%D0%B2%20%D0%B4%D0%B8%D0%B7%D0%B0%D0%B9%D0%BD%D0%B5%20%28%D0%B3%D1%80%D0%B0%D0%B4%D0%B8%D0%B5%D0%BD%D1%82%D1%8B%2C%20%D1%82%D0%B5%D0%BD%D0%B8%2C%20%D1%8D%D0%BC%D0%BE%D0%B4%D0%B7%D0%B8%2C%20~350%20%D0%98%D0%98-%D1%81%D0%BB%D0%BE%D0%B2%29.md)) первое почти совпадает со вторым. Для скиллов-пайплайнов со скриптами — нет.

## 5. Разбор методики: три места, где цифре верить не стоит

### 5.1. Плечо «без скилла» вообще не имеет системного промпта

Из `packages/cli/src/run.ts`:

```ts
function messagesForArm(skill, task, withSkill) {
  if (!withSkill) {
    return [{ role: 'user', content: task.prompt }];   // ← системного промпта нет вовсе
  }
  return [
    { role: 'system',
      content: `You are completing an evaluation task. Apply the following skill instructions when relevant.\n\n${skill.instructions}` },
    { role: 'user', content: task.prompt }
  ];
}
```

То есть сравниваются не «скилл против пустоты», а **«системный промпт со скиллом против отсутствия системного промпта»**. В лечение попадает и обёртка `You are completing an evaluation task. Apply the following skill instructions when relevant.` — фраза, которая сама по себе способна сдвинуть поведение модели (она сообщает, что идёт оценка, и просит быть внимательнее).

Корректная контрольная группа должна была получить нейтральный системный промпт того же объёма и тональности. Как сделано сейчас — часть измеренного «эффекта скилла» на самом деле эффект того, что в одном плече системный промпт есть, а в другом нет.

### 5.2. Bootstrap считает испытания одной задачи независимыми

`scorePairedObservations` получает плоский список наблюдений, где ключ — `taskId:trial`, и ресэмплирует **его** с возвращением:

```ts
const sample = observations[Math.floor(random() * observations.length)]!;
```

Но `K` испытаний одной и той же задачи — не независимые единицы: у них общий промпт и общий критерий. Задача бывает просто лёгкой или просто неудобной, и все её испытания коррелированы. Классический приём для таких данных — **кластерный bootstrap**: ресэмплировать задачи целиком вместе с их испытаниями. Ресэмплирование отдельных наблюдений завышает эффективный объём выборки и делает доверительный интервал **уже, чем он должен быть**, — а значит, вердикты `HELPS`/`HARMS` выпадают чаще, чем оправдано.

Показательно, что механику автор понимает — вот его собственный комментарий там же, в `run.ts`, про баг с кэшированием испытаний:

> *«That collapses K independent stochastic samples into one replicated K times and makes the paired-bootstrap CI ~sqrt(K) too narrow (pseudo-replication).»*

Баг он починил (номер испытания добавлен в ключ кэша), но тот же по природе эффект в более мягкой форме остаётся в самой схеме ресэмплирования — и в «Known Limitations» он не упомянут.

### 5.3. «Satisfaction 0–100» — это не отдельная метрика

Сайт и README подают шкалу удовлетворённости как самостоятельную оценку качества со шкалой «Very bad → Excellent». В коде (`eval.ts`) она вычисляется так:

```ts
const satisfaction = Math.max(0, Math.min(100, Number((50 + score.meanEffectPp).toFixed(1))));
```

Это **линейный сдвиг эффекта на 50** и больше ничего. Новой информации ноль. Хуже того — формула **не учитывает доверительный интервал**: прогон с эффектом +25 п.п. и интервалом от −5 до +55 (то есть вердикт `PLACEBO`, эффект статистически не доказан) всё равно нарисует бодрое `75.0/100 GOOD` с заполненной полоской.

> [!caution] Практический вывод
> Смотрите на **вердикт и на ширину интервала**, а на «Satisfaction» — нет. Широкий интервал (например, ±20 п.п. и больше) означает, что прогон ничего не показал, независимо от того, как красиво заполнилась полоска.

## 6. Деньги и приватность

Пост про это не сказал ни слова, а вопрос практический.

| Параметр | Значение |
| :--- | :--- |
| Бесплатно | **10 прогонов**, автообновление 1-го числа каждого месяца |
| Pro | **$19 разово**, безлимит + корпус и rot-отчёты |
| Вход | Clerk (Google / GitHub) |
| Оплата | Stripe |
| Хранилище ключей на сервере | Upstash Redis, ключи хранятся хешированными с «перцем» |
| Модель по умолчанию в hosted-режиме | `openai/gpt-oss-120b` через **NVIDIA NIM** |
| Ключ на вашей машине | `~/.config/skillcheck/config.json`, права `0600` |

**Что уходит на сервер в hosted-режиме:** тело вашего скилла целиком (оно идёт в системный промпт каждого вызова), сгенерированные задачи и все выходы модели. Прокси `dashboard/api/chat/completions.js` пересылает их в NVIDIA NIM под серверным ключом. Если скилл содержит что-то внутреннее — тестируйте в BYOK-режиме.

**BYOK (свой ключ)** — семь провайдеров: OpenAI, Anthropic, Google Gemini, Groq, Mistral, OpenRouter, NVIDIA NIM. Задаётся переменной `<PROVIDER>_API_KEY`, при `skillcheck setup` список моделей подтягивается живьём с `/models` провайдера.

> [!warning] Дефолтные модели в BYOK устарели почти на два года
> В `packages/cli/src/adapters/providers.ts`:
> ```ts
> openai:     'gpt-4o'
> anthropic:  'claude-3-5-sonnet-20241022'
> gemini:     'gemini-1.5-pro'
> openrouter: 'anthropic/claude-3.5-sonnet'
> groq:       'llama-3.3-70b-versatile'
> ```
> Это модели 2024 года. Мерить на них эффект скилла в августе 2026 бессмысленно: скилл, который «помогает» gpt-4o, вполне может оказаться `PLACEBO` на актуальной модели — это ровно то «гниение», которое ловит команда `rot`. **Всегда задавайте модель явно** через `SKILLCHECK_MODEL` или через живой выбор в `skillcheck setup`.

То есть инструмент, чей главный тезис «почти никто не измеряет скиллы», сам не опубликовал ни одного измерения.

> [!important] Как это читать
> Это не «плохой проект» — это **ранний проект одного автора с аккуратной инженерией и без пользователей**. Код чистый, тесты есть, ограничения задокументированы честно (что редкость). Но версия 0.9.x, живой боевой обкатки не было, и полагаться на его вердикт как на арбитра в споре «нужен этот скилл или нет» пока рано. Использовать как **грубый детектор откровенного плацебо** — вполне можно.

## 8. Установка на четырёх системах

Требование одно: **Node.js ≥ 20**. Именно оно и решает всё.

| Система | Node в репозитории | Годится? |
| :--- | :--- | :---: |
| **Gentoo** | `net-libs/nodejs` стабильные 20.18.2 / 22.13.1 / 24.14.0 / 26.3.0 | ✅ |
| **Debian 13 (trixie)** | 20.19.2 | ✅ |
| **Debian 12 (bookworm)** | 18.20.4 | ❌ нужен NodeSource |
| **Ubuntu 24.04 (noble)** | 18.19.1 | ❌ нужен NodeSource |
| **Ubuntu 25.04+ (plucky/resolute)** | 20.18.1 / 22.22 | ✅ |
| **Arch** | `extra/nodejs` 26.7.0 | ✅ |
| **Entware (RT-AX56U, armv7)** | `node` **v18.20.2** — единственная версия в репозитории | ❌ **не заведётся** |

### Gentoo (основная)

```bash
# Node уже должен стоять; если нет:
sudo emerge --ask net-libs/nodejs
# USE-флаг npm нужен обязательно — без него нет самого npm
grep -r nodejs /etc/portage/package.use/ || \
  echo 'net-libs/nodejs npm' | sudo tee -a /etc/portage/package.use/nodejs

node --version   # должно быть >= v20
npm install -g @sx4im/skillcheck
```

Глобальная установка от root в `/usr/lib/node_modules` на Gentoo — рабочий, но не самый чистый путь. Аккуратнее без прав root:

```bash
npm config set prefix "$HOME/.local"
export PATH="$HOME/.local/bin:$PATH"   # в ~/.bashrc
npm install -g @sx4im/skillcheck
```

Либо вообще без установки — разово:

```bash
npx @sx4im/skillcheck check ./SKILL.md
```

### Debian / Ubuntu

На trixie и на Ubuntu 25.04+ хватает штатного пакета:

```bash
sudo apt update && sudo apt install -y nodejs npm
node --version
```

На **bookworm** и **noble** штатный Node — 18.x, этого мало. Нужен NodeSource:

```bash
sudo apt install -y curl ca-certificates gnupg
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
node --version    # v22.x
sudo npm install -g @sx4im/skillcheck
```

Альтернатива без сторонних репозиториев — `nvm` в домашнем каталоге:

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
exec $SHELL
nvm install 22 && nvm use 22
npm install -g @sx4im/skillcheck
```

### Arch

```bash
sudo pacman -S nodejs npm
npm install -g @sx4im/skillcheck
```

Пакета в AUR под сам skillcheck нет — только через npm.

### Entware (ASUS RT-AX56U)

```bash
opkg update
opkg info node
# Version: v18.20.2-2   ← ниже требуемых 20
```

> [!caution] На роутере не поедет
> В репозитории Entware для `armv7sf-k3.2` лежит **только Node v18.20.2**, а `package.json` проекта требует `"node": ">=20"`. Собирать Node 20+ под armv7 вручную ради этого — путь в никуда: 512 МБ ОЗУ и 256 МБ flash, а сам инструмент не даёт на роутере ничего, чего не даст на десктопе.
>
> Если очень нужно гонять проверки «с роутера» — это делается по SSH к машине, где Node 20+ уже стоит:
> ```bash
> ssh desktop 'cd ~/skills && npx @sx4im/skillcheck check ./SKILL.md --json' > result.json
> ```
> Практического смысла в этом мало: сетевые вызовы всё равно уходят к провайдеру модели, а не к роутеру.

## 9. Практический сценарий: проверить свои скиллы

Ниже — реальный порядок действий на Gentoo, если хочется прогнать то, что уже лежит в `~/.claude/skills/`.

```bash
# 1. Установка и ключ
npm install -g @sx4im/skillcheck
skillcheck setup          # выбрать BYOK и указать актуальную модель

# 2. Один скилл, нормальный объём выборки, с разбором
skillcheck check ~/.claude/skills/ponytail/SKILL.md \
  --tasks 5 --trials 3 --explain --output ponytail.json

# 3. Пачкой — собрать манифест корпуса
cat > corpus.json <<'JSON'
{
  "name": "my-skills",
  "skills": [
    { "id": "ponytail",  "path": "/home/user/.claude/skills/ponytail/SKILL.md" },
    { "id": "watch",     "path": "/home/user/.claude/skills/watch/SKILL.md" }
  ]
}
JSON
skillcheck corpus run --corpus corpus.json --results ./results

# 4. Через месяц-другой, после смены модели — проверить, не «сгнило» ли
skillcheck rot --results ./results --output rot.json
```

> [!tip] Как читать результат, чтобы не обмануться
> 1. **Вердикт `PLACEBO` при узком интервале** (скажем, −3…+4 п.п.) — это содержательный результат: скилл действительно не работает, при том что вы платите за него токенами каждый запрос.
> 2. **Вердикт `PLACEBO` при широком интервале** (−20…+30 п.п.) — это не результат вообще, прогон слишком мал. Поднимайте `--tasks`/`--trials` и повторяйте.
> 3. **`HELPS` на 15 наблюдениях** — сигнал «похоже, помогает», а не доказательство. С учётом раздела 5.2 интервал ещё и оптимистично узкий.
> 4. **Смотрите на `Token cost`.** Скилл на +2000 токенов ради +5 п.п. на каждом запросе — сомнительная сделка; проект для этого считает «ценность на 1000 лишних токенов промпта».
> 5. **Один и тот же скилл на одной и той же модели даёт разные числа от прогона к прогону** — задачи генерируются заново каждый раз. Это заявлено как фича («независимое измерение»), но означает, что одиночный прогон нельзя цитировать как «результат».

### Что стоит проверять этим инструментом, а что нет

| Тип скилла | Имеет смысл? | Почему |
| :--- | :---: | :--- |
| Текстовые правила стиля/кода (`ponytail`, анти-слоп-промпты) | ✅ | Ровно тот случай, для которого метод и придуман |
| Доменные памятки и чеклисты в `CLAUDE.md` | ✅ | Тестируется тот самый текст, который агент и получает |
| Системные промпты и шаблоны | ✅ | По сути A/B-тест промпта |
| Скиллы со скриптами (`claude-video`, генераторы файлов) | ❌ | `scripts/` не исполняются — измерите только сопроводительный текст |
| Скиллы-пайплайны на много шагов (`Hyper Research`) | ❌ | Один вызов на 2048 токенов, петли и инструментов нет |
| Скиллы, у которых главное — момент срабатывания | ❌ | Триггер принудительно обойдён, `description` не проверяется |

## 10. Итог

**Что действительно хорошо:**
- Правильно поставленный вопрос: скиллы надо мерить, а не «чувствовать».
- Слепая оценка сделана честно — перемешивание, отсутствие метки плеча, генератор не видит тело скилла.
- Ограничения задокументированы автором сами, без принуждения. Это заметно лучше среднего по рынку.
- Инженерия аккуратная: 131 тест, оффлайн-прогон всего пайплайна с замоканным адаптером, CI на двух версиях Node.
- MIT, self-hosting дашборда предусмотрен, BYOK на семь провайдеров.

**Что нужно держать в голове:**
- Это измерение **текста в контексте**, а не работы агента. Триггер, скрипты и многошаговость — вне охвата.
- Контрольное плечо без системного промпта — конфаунд.
- Доверительный интервал систематически уже, чем следует, из-за ресэмплирования испытаний вместо задач.
- «Satisfaction» — декоративная перепаковка эффекта, игнорирующая неопределённость.
- Дефолтные модели BYOK — 2024 года, задавайте модель явно.
- Проект без пользователей: 23 звезды, 0 подписчиков, 0 внешних багрепортов, версия 0.9.7.
- На роутере с Entware не запустится — Node 18.

**Кому пригодится:** тому, у кого набралось много скачанных `SKILL.md` и есть подозрение, что половина из них — украшение. Как грубое сито от явного плацебо — годится уже сейчас, особенно в BYOK-режиме на своей актуальной модели. Как аргумент в техническом споре — пока нет.
