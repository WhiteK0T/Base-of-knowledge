# 🧹 ub-mode — скилл «чистого кода» от Роберта Мартина

[**ub-mode**](https://github.com/unclebob/ub-mode) — скилл для ИИ-агентов от Роберта Мартина (Uncle Bob), автора «Чистого кода». Это один файл `SKILL.md` в общем формате Agent Skills: правила дисциплинированной разработки, которые агент выполняет при каждой правке кода. Скилл вызывается командой `/ub-mode`. Заметка по посту [«Не баг, а фича»](https://t.me/bugnotfeature/28642) от 27 октября 2026 года, сверена с репозиторием.

## 1. Что внутри

Каждая правка проходит три этапа.

### Сначала заставить работать (First Make it Work)

- **Лень как принцип.** Одно решение живёт в одном месте; делается самая маленькая правка, которая решает задачу.
- **Фундамент.** Сначала правильная форма данных, потом логика. Если важен параллельный писатель — не делить состояние.
- **TDD.** Сначала падающий тест, причём падающий по ожидаемой причине. Потом минимальная правка до зелёного. Если честный тест написать нельзя — не писать плохой.
- **Перепроектировать, а не прикручивать.** Новое требование не приклеивают к старому дизайну: спрашивают, что построили бы, будь оно с самого начала, и доставляют частями.
- **Атаковать предпосылку.** Если две правки, исходящие из одной посылки, проваливают одну и ту же проверку, посылку записывают одной фразой и устраняют, а не пробуют третью правку.
- **Сначала убрать, потом добавить.** Сложность вычитают раньше, чем что-то добавляют.
- **Цель — проверяемое конечное состояние.** Промежуточная поломка допустима, только если она запланирована и обратима.
- **Сделать рычаг.** Неочевидную повторяющуюся работу автоматизируют: одну единицу делают руками, потом пишут инструмент, который повторяет её.
- **Архитектура:**
  - модель предметной области, в которой недопустимые состояния невозможны, и глоссарий терминов;
  - данные проверяются на границе, внутри им доверяют, бизнес-логика — чистые функции;
  - типы не дают записать недопустимое значение, внешние данные разбираются один раз, предупреждения компилятора не глушат;
  - операции идемпотентны, в том числе после падения на середине;
  - общее изменяемое состояние — только с одним писателем, закреплённым в структуре кода.

### Потом сделать правильно (Then Make it Right)

- **Чинить причину.** Воспроизвести, исправить причину. Проверка, которая лишь прячет падение, — не исправление.
- **Работа малыми проверяемыми кусками:** закончил кусок, проверил, только потом следующий.
- **Тестировать поведение, а не реализацию.** Тест вызывает код так, как его вызывает пользователь. Тест, который прошёл бы, даже если бы все функции ничего не возвращали, выбрасывают.
- **Метрики — внешними инструментами:**
  - `crapper` — у каждой функции CRAP меньше 10;
  - `dryer` — убрать дубли со сходством от 0,8;
  - `mutator` — покрыть непокрытое, убить выжившие мутанты, удалить мёртвый код.
- **Рефакторинг:** зафиксировать поведение, поменять структуру, доказать, что поведение не изменилось.

### Практика (Practice)

- **Журнал.** Записывать каждое действие и его причину, в конце отчитаться журналом.
- **Беречь контекстное окно.** Основная ветка разговора маленькая, объёмную работу отдавать в другое место — на практике субагентам — и держать только выжимку.
- **Уборка рабочих деревьев.** Удалять то, что точно не используется. Незакоммиченная работа ждёт решения человека.
- **Коммиты** — частые, маленькие, по порядку. В каждом: зачем, что изменилось и чем это доказано. В конце — push в основную ветку.

## 2. Что за словами поста

- **«Бесплатный»** — да, MIT.
- **«Без повторов и мусора».** Это пункты про дубли и мёртвый код, а их выполняют внешние инструменты Мартина. Сам `SKILL.md` пишет лишь «используй инструмент» и не объясняет, где его взять и как запустить. Без установленных `crapper`, `dryer` и `mutator` эти шаги агенту выполнить нечем (раздел 3).
- **«Найдут причины своих ошибок, наведут порядок рефакторингом»** — это пункты «Чинить причину» и «Рефакторинг».
- **«Как пишет Роберт Мартин».** Правила — сокращённая переработка чужого набора (`poteto-mode`), что Мартин и указывает в README. Его собственный вклад — отбор правил и инструменты-метрики.
- **«Автор уже вовсю использует со своими агентами»** — в репозитории об этом ничего нет.

## 3. Установка

Скилл — копия `SKILL.md` в каталог скиллов агента. Пути из README:

```bash
# Claude Code (для Cursor — ~/.cursor/skills/ub-mode/, для Grok — ~/.grok/skills/ub-mode/)
mkdir -p ~/.claude/skills/ub-mode
curl -fsSL https://raw.githubusercontent.com/unclebob/ub-mode/master/SKILL.md -o ~/.claude/skills/ub-mode/SKILL.md
```

Затем в сессии — `/ub-mode`. Скилл не включается сам по себе: в его описании сказано, что он для случая, когда пользователь запускает `/ub-mode` или просит эти принципы.

### Инструменты для метрик

`crapper`, `dryer` и `mutator` — Python-утилиты (0BSD), поддерживают Clojure, Java, Go, TypeScript и JavaScript, Rust и Python. На PyPI их нет: каждую клонируют, а при первом запуске она создаёт себе `.venv`. `mutator` ищет `crapper` рядом с собой (`../crapper`), поэтому клонировать их нужно в один каталог.

| Система | Что нужно для `.venv` |
| :--- | :--- |
| Gentoo | `dev-lang/python` — `venv` в нём есть |
| Debian / Ubuntu | `sudo apt install python3-venv git` — без `python3-venv` создать `.venv` не получится |
| Arch | `sudo pacman -S python git` |

```bash
mkdir -p ~/tools && cd ~/tools
git clone https://github.com/unclebob/crapper
git clone https://github.com/unclebob/dryer
git clone https://github.com/unclebob/mutator

cd ~/my-project                    # запускать из корня проекта
~/tools/crapper/crapper --changed  # CRAP по изменённым файлам
~/tools/dryer/dryer --changed      # дубли
~/tools/mutator/mutator --changed  # мутационное тестирование
```

- **Покрытие.** Для CRAP нужно покрытие тестами. `crapper` берёт его штатными средствами языка: JaCoCo для Java, `go test -coverprofile`, `cargo llvm-cov` или `cargo tarpaulin` для Rust, LCOV для Python и TypeScript и т. д. Готовые отчёты подхватывает с `--use-existing-coverage`. Без покрытия есть `--no-coverage` — только сложность.
- **Формула:** CRAP = CC² × (1 − покрытие)³ + CC, где CC — цикломатическая сложность. До 5 — низкий риск, 5–30 — стоит посмотреть, больше 30 — сложно и плохо покрыто тестами. Порог ub-mode — 10.
- **Визуализация.** Результаты все три пишут в формате, который показывает [uml-viewer](https://github.com/unclebob/uml-viewer). Это отдельное приложение на Clojure, нужны Java 21+ и Clojure CLI; лицензии у него нет.

## 4. На что обратить внимание

- **Push в основную ветку.** Последний пункт практики велит в конце пушить в основную ветку. При работе через pull request или с защищённой `main` эту строку стоит поправить в своей копии `SKILL.md`. Claude Code всё равно спросит разрешение на `git push`, если не стоит автоматический режим.
- **Журнал в конце** — полезно для разбора, но это лишние выходные токены на каждую задачу.
- **TDD на каждую правку** замедляет мелкие изменения. Сам скилл оговаривается: если честный тест невозможен, плохой не писать.
- **Скилл короткий**, около 150 строк, и в фоне почти ничего не стоит: до вызова агент видит только `name` и `description`.
