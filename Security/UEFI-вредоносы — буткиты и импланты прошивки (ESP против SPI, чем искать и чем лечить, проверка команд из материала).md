# 👻 UEFI-вредоносы — буткиты и импланты прошивки

Конспект по [материалу SecurityLab от 21.08.2025](https://www.securitylab.ru/analytics/562655.php) с проверкой команд и дополнением за прошедший год. **Фактура в статье в целом верная** — случаи, CVE и логика лечения совпадают с первоисточниками. Но три вещи стоит поправить, и они меняют практику:

1. **Статья валит в одну кучу два разных класса угроз.** Буткит на ESP и имплант в SPI-флеше живучи по-разному и лечатся по-разному. Тезис «даже замена диска не помогает» верен только для второго; BlackLotus, которым статья иллюстрирует проблему, **живёт на разделе диска** и форматированием как раз снимается.
2. **Часть команд в том виде, как они приведены, не отработает.** `Get-SecureBootUEFI` не принимает список имён, у `chipsec_main -i` совсем другой смысл, а подкоманды `chipsec_util uefi scan` не существует. Рабочие варианты — ниже.
3. **За год ситуация заметно изменилась.** Главное: сертификаты Secure Boot 2011 года **истекли в июне 2026**, а третий истекает в октябре. На 20.09.2026 это самый актуальный пункт во всей теме, и статья августа 2025 его, естественно, не знает.

Проверено 20.09.2026 по NVD, исходникам CHIPSEC, документации Microsoft и fwupd, репозиториям Gentoo, Arch, Debian и Entware.

## ⚠️ Два класса угроз — не путать

Это главное различие во всей теме. От него зависит и способ поиска, и способ лечения.

| | **Буткит на ESP** | **Имплант в прошивке (SPI-флеш)** |
| :--- | :--- | :--- |
| Где лежит | файлы `.efi` на EFI System Partition — обычный раздел диска | микросхема SPI-флеша на материнской плате |
| Примеры | **BlackLotus**, **Bootkitty**, буткит-часть **HybridPetya** | **LoJax**, **MosaicRegressor**, **MoonBounce**, **CosmicStrand** |
| Переживает переустановку ОС | ⚠️ только если ESP не затёрли или заражение повторилось | ✅ да |
| Переживает **замену диска** | ❌ **нет** | ✅ **да** |
| Как попадает | эксплуатация подписанного уязвимого загрузчика, свои ключи в MOK, физический доступ | уязвимость SMM/прошивальщика, незалоченный SPI, физический доступ к программатору |
| Чем снимается | затиранием ESP + обновлением **dbx** (иначе уязвимый загрузчик по-прежнему доверенный) | **только перепрошивкой SPI**, часто внешним программатором |
| Насколько распространён | редко, но встречается у обычных пользователей | очень редко, почти всегда целевые атаки |

> [!important] Почему формулировка «формат диска — не лекарство» требует оговорки
> Для имплантов в SPI она абсолютно верна. Для BlackLotus — нет: он ставит свои `.efi` на ESP и не пишет во флеш. Затирание ESP его убирает. Настоящая проблема другая — **уязвимый, но подписанный Microsoft загрузчик остаётся доверенным**, пока не обновлён список отзывов `dbx`. То есть чистая система снова заражается тем же способом. Именно поэтому отзывы (CVE-2023-24932 и последующие) важнее, чем сама переустановка.

## ⏰ Самое актуальное: сертификаты 2011 года истекли

Это не гипотетика и не будущее — на дату заметки два из трёх сертификатов уже мертвы.

| Сертификат | Истекает | Чем был | Замена |
| :--- | :--- | :--- | :--- |
| **Microsoft Corporation KEK CA 2011** | **24.06.2026** | тот самый ключ, которым Windows Update дописывает новые записи в `db` и `dbx` | KEK CA 2023 |
| **Microsoft Corporation UEFI CA 2011** | **27.06.2026** | сторонний CA — им подписан **shim**, то есть загрузка почти всех дистрибутивов Linux | Microsoft UEFI CA 2023 |
| **Microsoft Windows Production PCA 2011** | **19.10.2026** | подпись загрузчика самой Windows | Windows UEFI CA 2023 |

> [!danger] Что это значит практически
> - **Без обновлённого KEK машина перестаёт получать новые отзывы `dbx`.** То есть каждая следующая дыра уровня BlackLotus остаётся неотозванной на этой машине навсегда. Для темы «UEFI-вредоносы» это прямой удар по единственному работающему механизму защиты.
> - **Для Linux ломается цепочка shim.** Новые shim подписываются сертификатом 2023 года, и прошивка без него в `db` их не примет. Дистрибутивы какое-то время выпускали shim с **двойной подписью** (2011 + 2023), но это переходная мера, а не навсегда.
> - Машины, выпущенные примерно с 2024 года, часто уже приехали с сертификатами 2023 с завода. Всё, что старше, надо обновлять руками или через обновления ОС.

Проверить и обновить:

```bash
# Linux: посмотреть, что лежит в db/KEK — ищем строки "2023"
sudo efi-readvar -v db  | grep -i '2023\|2011'
sudo efi-readvar -v KEK | grep -i '2023\|2011'

# обновление db/KEK и dbx приезжает через LVFS (поддержка db/KEK — с fwupd 2.0.8)
sudo fwupdmgr refresh
sudo fwupdmgr get-devices | grep -iA3 'dbx\|UEFI'
sudo fwupdmgr update
```

```powershell
# Windows (PowerShell от администратора)
Confirm-SecureBootUEFI           # включён ли Secure Boot вообще
Get-SecureBootUEFI -Name KEK -OutputFilePath kek.bin
```

## 🔑 Почему Secure Boot — не гарантия

Полезно держать в голове три независимых способа его обойти, все три реализованы на практике:

- **Подписанный, но уязвимый загрузчик.** Подпись Microsoft проверена, а внутри — свой PE-загрузчик или баг парсинга. Так работали `CVE-2022-21894` (BlackLotus) и `CVE-2024-7344` (HybridPetya). Лечится **только отзывом в `dbx`**, и потому просроченный KEK — это катастрофа в рассрочку.
- **Код выполняется раньше проверки.** LogoFAIL запускался на этапе DXE, при разборе картинки логотипа, то есть до того, как Secure Boot вообще начинает что-то проверять.
- **Корень доверия скомпрометирован изначально.** PKfail: платформенный ключ — тестовый, его приватная часть публично известна. Проверка формально проходит, смысла в ней ноль.

> [!tip] Проверка на PKfail занимает одну команду
> Сертификат платформенного ключа на задетых машинах содержит в полях subject/issuer строку `DO NOT TRUST` или `DO NOT SHIP`:
> ```bash
> sudo efi-readvar -v PK | grep -i 'do not trust\|do not ship\|DO NOT'
> ```
> Если совпало — Secure Boot на этой машине декоративный, пока не обновишь прошивку у вендора или не сгенерируешь свой PK.

## 🔍 Диагностика

### Windows — рабочие команды

> [!warning] Команда из материала в таком виде не отработает
> `Get-SecureBootUEFI -Name SecureBoot,db,dbx,KEK,PK` — параметр `-Name` объявлен как **одиночная строка** (`[String]`, позиция 1). Список через запятую PowerShell сначала превратит в массив, потом склеит в одну строку `"SecureBoot db dbx KEK PK"` — такой переменной не существует, ответом будет `Variable is currently undefined`. Плюс консоль нужна **с правами администратора**, иначе `Unable to set proper privileges. Access was denied.`

```powershell
# включён ли Secure Boot — самый короткий ответ
Confirm-SecureBootUEFI

# перебрать переменные по одной (вот так — работает)
'PK','KEK','db','dbx','SecureBoot','SetupMode' | ForEach-Object {
    [PSCustomObject]@{ Name = $_; Value = (Get-SecureBootUEFI -Name $_ -ErrorAction SilentlyContinue) }
} | Format-Table -Auto

# выгрузить dbx на диск для сравнения с эталоном от Microsoft
Get-SecureBootUEFI -Name dbx -OutputFilePath .\dbx.bin

# записи загрузки в прошивке — ищем незнакомые
bcdedit /enum firmware

# смонтировать ESP и посмотреть, что там лежит
mountvol S: /S
dir S:\EFI\ /s /a
```

На что смотреть в `S:\EFI\`: штатно там `Boot`, `Microsoft` и каталоги вендора. Лишние каталоги, свежие даты у `bootmgfw.efi`, незнакомые `.efi` — повод копать. Косвенный признак буткит-заражения — **внезапно отключившиеся BitLocker, HVCI или Defender**: BlackLotus именно это и делал.

### Linux

```bash
# состояние Secure Boot
mokutil --sb-state
bootctl status                       # systemd: Secure Boot, TPM, прошивка, ESP — одной командой

# ключи и отзывы
sudo efi-readvar -v PK ; sudo efi-readvar -v KEK
sudo efi-readvar -v db ; sudo efi-readvar -v dbx      # пакет efitools

# что пользователь сам добавил в доверенные (MOK) — частый способ легализовать чужой модуль
mokutil --list-enrolled

# записи загрузки
efibootmgr -v

# оценка защищённости платформы: уровень HSI (Host Security ID)
fwupdmgr security

# содержимое ESP
sudo ls -laR /boot/efi/EFI/
```

Отдельный сильный приём — **сверка PCR в TPM**. Регистры 0–7 покрывают прошивку, конфигурацию и состояние Secure Boot; если прошивку подменили, значения уедут:

```bash
sudo tpm2_pcrread sha256:0,1,2,3,4,5,6,7
```

Смысл не в абсолютных значениях, а в том, что они **меняются без причины**. Поэтому снимать эталон нужно на заведомо чистой системе — задним числом этот метод бесполезен.

### CHIPSEC — глубокий уровень

> [!warning] Здесь в материале две ошибки
> - **`chipsec_main -i` — это не «инвентаризация защит платформы».** Флаг `-i` = `--ignore_platform`: «выполнять проверки, даже если платформа не опознана». Инвентаризацию даёт `chipsec_main` **вообще без аргументов** — он прогоняет все модули.
> - **Подкоманды `chipsec_util uefi scan` не существует.** У `chipsec_util uefi` есть `types`, `var-list`, `var-read`, `var-write`, `var-delete`, `var-find`, `var-list-spi`, `nvram`, `nvram-auth`, `decode`, `keys`, `tables`, `s3bootscript`, `assemble`, `insert-before`, `insert-after`, `replace`, `remove`. Поиск известных вредоносных модулей делают **модули** `tools.uefi.scan_blocked` и `tools.uefi.scan_image`.

```bash
# все проверки платформы (нужны root и загруженный драйвер ядра)
sudo chipsec_main

# точечно: защищён ли SPI-флеш от записи — ключевой вопрос всей темы
sudo chipsec_main -m common.bios_wp
sudo chipsec_main -m common.spi_lock
sudo chipsec_main -m common.spi_desc
sudo chipsec_main -m common.secureboot.variables

# параметры SPI-контроллера и снятие дампа прошивки
sudo chipsec_util spi info
sudo chipsec_util spi dump rom.bin

# проверка дампа по списку известных вредоносных EFI-модулей
sudo chipsec_main -m tools.uefi.scan_blocked -a rom.bin,blockedlist.json

# сравнение дампа с эталонным образом
sudo chipsec_main -m tools.uefi.scan_image -a rom.bin

# разобрать дамп на тома и модули для ручного анализа
chipsec_util uefi decode rom.bin
```

> [!note] Честная оговорка от самих авторов
> В документации `scan_blocked` написано прямым текстом: *«модуль может обнаружить только то, о чём знает из своего конфига»*. Это не антивирус — это сверка со списком. Неизвестный имплант он не найдёт.
>
> И главное: **`common.bios_wp` полезен даже на чистой машине.** Если он говорит `FAILED`, значит записать во флеш может любой процесс с правами root/админа — то есть имплант ставится в одно действие. Это предмет для обновления прошивки прямо сейчас, а не когда-нибудь.

> [!danger] Чего не делать
> У `chipsec_util spi` есть подкоманды `write`, `erase` и `disable-wp`. Это не диагностика. Ошибка здесь — кирпич из материнской платы, восстанавливаемый только программатором.

## 🧯 Лечение — по возрастанию тяжести

Порядок из материала разумный, привожу с уточнениями:

1. **Обновить прошивку и отзывы.** UEFI до актуальной версии от вендора + `dbx`. На Linux — `fwupdmgr refresh && fwupdmgr update`; на Windows отзывы приезжают через Windows Update. **С этого начинать всегда** — без свежего `dbx` остальное бессмысленно, машина заразится повторно.
2. **Вычистить ESP.** Удалить лишние каталоги и `.efi`, восстановить загрузчик штатными средствами (`bcdboot` на Windows, переустановка `grub`/`systemd-boot` на Linux). Для ESP-буткитов этого шага обычно достаточно.
3. **Сбросить NVRAM и восстановить ключи Secure Boot** (PK/KEK/db) — обычно пункт «Restore Factory Keys» в настройках прошивки. Заодно убрать чужое из MOK: `mokutil --list-enrolled`, лишнее — `mokutil --delete`.
4. **Полная перепрошивка SPI** — если подозрение на имплант во флеше. Внутренняя перепрошивка из-под ОС тут **не годится**: если имплант активен, он может перехватить запись. Нужен внешний программатор (CH341A, Raspberry Pi + `flashrom`) и прищепка SOIC-8. Это уже сервисная операция.
5. **Ротировать всё, до чего вредонос мог дотянуться:** ключ восстановления BitLocker или LUKS, пароли, токены. Заново включить HVCI и Defender / проверить, что модули ядра снова требуют подписи.

> [!important] Когда останавливаться и звать людей
> Если `common.bios_wp` показывает `FAILED`, PCR разошлись, а дамп флеша отличается от эталона вендора — дальше самодеятельность вредна. Дамп надо сохранить как улику (он же понадобится для сравнения), машину — изолировать. Для целевых имплантов важнее не «вылечить», а понять, как попало.

## 🛡️ Профилактика

- **Держать прошивку свежей.** Скучно, но это единственное, что закрывает классы вроде SMM-багов Gigabyte.
- **Не пропускать обновления `dbx`** — и, начиная с 2026 года, убедиться, что на машине сертификаты 2023, а не только 2011.
- **Отключить CSM/Legacy Boot**, если он не нужен: совместимостный режим выключает часть проверок.
- **Пароль на настройки UEFI** и, если поддерживается, запрет загрузки со сменных носителей — большинство сценариев требуют физического доступа или перезагрузки в чужой носитель.
- **Ограничить MOK.** Каждый добавленный ключ — расширение круга доверия. Проприетарные драйверы этим пользуются легитимно, но список надо периодически смотреть.
- **Снять эталоны заранее:** дамп прошивки (`chipsec_util spi dump`), значения PCR, список содержимого ESP. Без эталона сравнивать не с чем, а собрать его после заражения уже нельзя.
- **Гентушный вариант — свои ключи.** Если ядро всё равно собирается руками, логичнее не доверять чужому CA, а сгенерировать свои PK/KEK/db через `sbctl` и подписывать свой загрузчик и ядро самому. Побочный бонус: истечение сертификатов Microsoft такую конфигурацию не задевает.

## 💡 Итог

- **Тема реальная, но пропорции важны.** Импланты во флеше — это почти всегда целевые атаки уровня APT. Обычному пользователю на порядок вероятнее встретить ESP-буткит, а тому нужен либо уязвимый подписанный загрузчик, либо физический доступ.
- **Два класса угроз — два разных ответа.** Замена диска не спасает только от имплантов в SPI; ESP-буткит снимается затиранием раздела, но **вернётся, если не обновить `dbx`**.
- **Secure Boot ломали тремя принципиально разными способами:** подписанным уязвимым загрузчиком, выполнением кода до проверки (LogoFAIL) и компрометацией самого корня доверия (PKfail). Считать его гарантией нельзя ни в одном из случаев.
- **Самое срочное на сегодня — сертификаты.** KEK CA 2011 истёк 24.06.2026, UEFI CA 2011 — 27.06.2026, Windows Production PCA 2011 истекает 19.10.2026. Без обновлённого KEK машина больше **не получает новых отзывов `dbx`**, то есть остаётся беззащитной перед следующим BlackLotus.
- **Команды из исходного материала перед применением стоит сверить** — `Get-SecureBootUEFI` со списком имён, `chipsec_main -i` как «инвентаризация» и `chipsec_util uefi scan` работать не будут.
- **Самая полезная проверка занимает минуту:** `chipsec_main -m common.bios_wp`. Если `FAILED` — флеш открыт на запись из-под ОС, и это чинится обновлением прошивки, а не антивирусом.
- **Эталоны снимают заранее.** Дамп прошивки, PCR, содержимое ESP на чистой системе. После заражения собирать их поздно.
