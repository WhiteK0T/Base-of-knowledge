# 🖱️ Click2Shell — WordPress Core RCE-цепочка через инъекцию в jQuery-селектор

> [!danger] TL;DR
> **Click2Shell** — цепочка в **ядре WordPress** (не в плагине), приводящая к выполнению кода на сервере. Ядровая часть — **инъекция в jQuery-селектор** на странице установки тем: один и тот же параметр URL по-разному обрабатывается на бэкенде и во фронтенд-JS.
> - Уязвимы: **все версии WordPress до 7.1.1**. Исправлено в **7.1.1** (17.09.2026, changeset 63664).
> - Сама ядровая ошибка — **CVSS ~7.1** (принудительная установка темы, кода ещё нет). Полная цепочка с RCE — **CVSS 9.3–9.6**.
> - Нашла команда **[pwn.ai](https://pwn.ai/)** (Paulos Yibelo), сообщила 22.08.2026. **Обновиться до ≥ 7.1.1.** Автообновления ядра WordPress обычно уже подтянули патч.

> [!warning] «Pre-auth» — с оговоркой
> Пост и README PoC называют цепочку «pre-auth». Это условно: атакующему не нужна **своя** учётка, но нужно, чтобы **залогиненный администратор** открыл подготовленную ссылку (или чтобы на сайте была XSS, которая откроет её сама). То есть требуется взаимодействие с жертвой-админом (`UI:R` в векторе CVSS). Полностью без участия администратора цепочка не срабатывает.

## 🧬 Ядровая ошибка: один URL, две разные обработки

Ошибка — классический **рассинхрон санитизации** между сервером и клиентом:

- **Бэкенд (Themes API на WordPress.org)** канонизирует параметр `theme` в корректный slug: из значения извлекается только имя темы.
- **Фронтенд (`wp-admin/js/theme.js`)** берёт **исходное, неэкранированное** значение из URL и подставляет его прямо в **jQuery-селектор**:

```javascript
// было (уязвимо):
$( 'div[data-slug="' + slug + '"]' ).trigger( 'click' );
```

Так как `slug` попадает в селектор без экранирования, специально сконструированное значение превращается в **инъекцию CSS-селектора**: селектор перестаёт указывать на карточку одной темы и «дотягивается» до кнопки «Установить» нужной атакующему темы. `.trigger('click')` нажимает её от имени администратора.

**Почему установка проходит без запроса прав:** скрипт работает на уже аутентифицированной странице `wp-admin`. Nonce на установку и право `install_themes` там уже есть — атакующему не нужно ничего подделывать, он переиспользует активную сессию админа.

**Патч (WordPress 7.1.1, changeset 63664):**

```javascript
// стало:
$( 'div.theme[data-slug="' + $.escapeSelector( slug ) + '"]' ).trigger( 'click' );
```

Два изменения: slug пропускается через `$.escapeSelector()`, а селектор сужен до реальных карточек тем (`div.theme`).

## 🔗 Как ядровая ошибка становится RCE

Сама по себе принудительная установка темы кода не выполняет: тема ставится, но остаётся неактивной. RCE получается в связке ещё с двумя звеньями (демонстрация pwn.ai):

1. **Принудительная установка темы из каталога** — ядровая инъекция выше. В демонстрации ставилась реальная тема из каталога WordPress.org — **Mobile Repair Zone 2.5.4**.
2. **Загрузка PHP темы до активации через Customizer.** Код темы подгружается в жизненный цикл запроса ещё до того, как тему активировали.
3. **Незащищённый AJAX-установщик в самой теме.** У Mobile Repair Zone 2.5.4 есть AJAX-обработчик, который по присланному URL скачивает и ставит произвольный плагин **без проверки прав и nonce**. Установленный плагин выполняется как пользователь веб-сервера — это и есть RCE.

То есть ядро даёт возможность **навязать установку любой темы из официального каталога**, а дырявая тема из этого же каталога замыкает цепочку до выполнения кода. Ядровый патч рвёт первое звено — навязать установку больше нельзя.

> [!note] Публичный PoC существует, но с оговорками
> В открытом доступе есть Python-PoC (репозиторий `HackfutSecRoot/click2shell`, создан 19.09.2026). По собственному README это **реконструкции для лабораторий**, а не готовый рабочий эксплойт: точные строки инъекции и имена AJAX-действий в скриптах оставлены заглушками (`SELECTOR_PAYLOAD`, `AJAX_ACTION`), потому что в исходной статье блоки кода не отрендерились. Так что «уже есть публичный эксплойт» из поста — правда лишь наполовину: каркас опубликован, но боевые строки в нём не заполнены. Репозиторий на 27.09.2026 — 4 звезды, автору-аккаунту около месяца; в README много ссылок на приватные Telegram-каналы автора.

## 🩹 Исправление и смягчение

1. **Обновить ядро до ≥ 7.1.1.** Проверка и обновление через WP-CLI:
   ```bash
   wp core version
   wp core update --minor    # для веток < 7.1 подтянет доступный патч ветки
   ```
   Ядро WordPress по умолчанию обновляет минорные/security-релизы автоматически — многие сайты получили 7.1.1 без ручного вмешательства.
2. **`DISALLOW_FILE_MODS`.** По Patchstack, сайты с `define('DISALLOW_FILE_MODS', true);` в `wp-config.php` **не** компрометируются этой цепочкой полностью: запрещены установка/обновление тем и плагинов из админки. Разумная мера хардненинга для продакшена и без Click2Shell.
3. **Удалить/обновить уязвимую тему.** Mobile Repair Zone 2.5.4 с незащищённым AJAX-установщиком — второе звено; такие темы лучше не держать установленными.
4. **Гигиена сессии администратора.** Не открывать сторонние ссылки в браузере с активной сессией `wp-admin`; держать админку за отдельным профилем/браузером. Ядровая ошибка требовала именно клика/захода залогиненного админа.

> [!tip] Что искать в логах (IOC не публиковались, это по механике)
> Признаков компрометации в разборе pwn.ai нет. По логике цепочки настораживают: неожиданно появившиеся темы из каталога (`wp-content/themes/…`), вызовы `admin-ajax.php` с параметром-URL пакета от внешнего адреса, новые плагины и файлы в `wp-content/plugins/`, дочерние `sh`/`bash` у `php-fpm`.

## 🖥️ Применимость на системах владельца

Уязвимость — в PHP/JS-коде ядра WordPress, от ОS сервера не зависит. Значима, только если где-то поднят WordPress.

| Система | Актуальность |
| :--- | :--- |
| **Gentoo** | ✅ если есть локальный WordPress (`www-apps/wordpress` или вручную) < 7.1.1. Ядро обновляется средствами самого WordPress / WP-CLI, а не через Portage |
| **Debian / Ubuntu** | ✅ то же самое; пакет `wordpress` из репозитория ядро до 7.1.1 не тянет автоматически |
| **Arch** | ✅ то же самое (`wordpress` в extra) |
| **Entware / RT-AX56U** | ➖ практически нерелевантно: полноценный WordPress на роутере с 512 МБ RAM — экзотика |

> [!tip] Общий урок
> Если один и тот же параметр разбирается **и на сервере, и в браузере**, санитизировать нужно **в обоих местах**. Санитизация только на бэкенде бесполезна, когда фронтенд берёт сырое значение из URL и подставляет его в селектор/DOM. И `$.escapeSelector()` для любых данных, попадающих в jQuery-селектор, — не опция, а необходимость.
