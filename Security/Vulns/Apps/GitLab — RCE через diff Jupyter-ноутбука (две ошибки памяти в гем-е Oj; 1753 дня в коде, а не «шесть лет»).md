# 📓 GitLab — RCE через diff Jupyter-ноутбука (две ошибки памяти в гем-е Oj)

Исследователи **depthfirst** (Yuhang Wu, опубликовано **24.07.2026**) взяли не GitLab, а его зависимость — Ruby-гем **Oj**, высокопроизводительный JSON-парсер с большой нативной C-частью. Автоматическая система анализа выдала **18 приоритетных находок, включая 7 нарушений memory safety**. Две из них — **запись за границей буфера** и **утечка кучи** — сложились в полноценную **RCE на дефолтной установке GitLab**, выполняемую от пользователя `git`.

> [!info] Почему Ruby и «безопасность памяти» здесь не спасли
> Ruby считается memory-safe языком. Но у множества гемов есть каталог `ext/` с сишным кодом: `String`, `Array` и `Hash` уезжают в нативные парсеры с указателями, буферами фиксированного размера, преобразованиями целых и ручным управлением временем жизни. Исследование началось именно с наблюдения, что в этих `ext/` полно находок memory corruption.

## ❗ Поправка к посту: не «более шести лет», а 1753 дня

Пост утверждает, что одна из уязвимостей оставалась незамеченной **более шести лет**. По первоисточнику — **меньше пяти**:

> Two of them, an out-of-bounds write and a heap-pointer disclosure, had survived in Oj for **nearly five years**.

И точная цифра из их же таймлайна: уязвимый код прожил в парсере **1753 дня** (08.08.2021 → 27.05.2026), то есть **4 года 10 месяцев**. Проверил по rubygems: гем **Oj 3.13.0** — первый релиз с этим парсером — опубликован **09.08.2021**, а исправленный **3.17.3** вышел **04.06.2026**. Сходится.

## 🔗 Как цепочка добралась от JSON-парсера до GitLab

```
.ipynb в репозитории (обычный JSON)
   └─ открытие страницы diff коммита: GET /<project>/-/commit/<sha>/diffs_stream
        └─ Gitlab::Diff::Rendered::Notebook::DiffFile#notebook_diff
             └─ внутренний гем ipynbdiff → Transformer#validate_notebook
                  └─ Oj::Parser.usual.parse   ← вход в C
                       ├─ баг 1: непроверенный стек вложенности → запись за границей
                       └─ баг 2: сужение длины ключа до 16 бит → раскрытие указателя кучи
                            └─ выполнение команд в Puma-воркере от пользователя git
```

**Почему GitLab вообще парсит ноутбук.** `.ipynb` — это JSON, и «сырой» diff по нему нечитаем: одна правка в ячейке тонет среди экранированных переводов строк, счётчиков выполнения и сохранённых выводов. Поэтому GitLab делает «человеческий» diff ноутбуков: внутренний гем `ipynbdiff` разбирает обе ревизии, обходит массив `cells` и превращает их в упорядоченные текстовые блоки. Разбор файла — первый шаг, и именно так туда попал вызов Oj.

**Что нужно атакующему.** Обычная авторизованная учётка, которая может пушить в **свой собственный** проект. Коммитишь одну версию ноутбука, во втором коммите меняешь её, открываешь страницу diff — обе стороны diff под твоим контролем. **Не нужны** ни права администратора, ни CI/раннеры, ни взаимодействие с другими пользователями, ни чужие проекты.

**Что получает.** Выполнение команд от `git` — пользователя, под которым работают Puma-воркеры GitLab. Оттуда доступны данные репозиториев, секреты Rails, учётные данные сервисов и внутренние сервисы приложения.

> [!note] Про «утечку кучи» — без преувеличений
> Второй баг — это **фиксированное раскрытие 29 байт**, а не произвольное чтение по адресу: наружу попадают байты, уже лежавшие в структуре записи ключа. Этого хватило, чтобы узнать раскладку объектов в памяти и превратить узкий примитив записи в управляемый.

## 🩹 Затронутые и исправленные версии

| Компонент | Уязвимые версии | Первый исправленный релиз |
| :--- | :--- | :--- |
| GitLab CE/EE | 15.2.0 – 18.10.7 | **18.10.8** |
| GitLab CE/EE | 18.11.0 – 18.11.4 | **18.11.5** |
| GitLab CE/EE | 19.0.0 – 19.0.1 | **19.0.2** |
| Гем Oj | 3.13.0 – 3.17.1 | **3.17.3** |

- **GitLab 15.1 и старше не затронуты** — там в этом пути использовался `JSON.parse`.
- Релизы **15.2–18.9 бэкпортов не получили**: они уже вне поддерживаемых веток безопасности, оттуда нужно переезжать на поддерживаемую версию.
- Те же диапазоны применимы к Linux-пакетам, Docker-образам, установкам из исходников, Geo и cloud-native. Для Helm/Operator ориентир — версия GitLab в образе Webservice, где крутится Puma; первые исправленные чарты — **9.10.8, 9.11.6, 10.0.2**.
- **GitLab.com был пропатчен заранее**, клиентам Dedicated делать ничего не требовалось.

Условие уязвимости точнее версии: сборка затронута, если в ней есть путь `Oj::Parser.usual.parse` в рендере ноутбуков **и** поставляется Oj 3.13.0–3.17.1. Для форков, RC и downstream-пакетов проверять надо именно это, а не ярлык версии.

## 🧾 CVE: девять есть, а у самой цепочки — нет

Широкий аудит Oj дал **девять опубликованных advisory**, все — на другие части гема:

| CVE | Что это |
| :--- | :--- |
| CVE-2026-54502 | переполнение стекового буфера в `Oj.dump` при большом отступе |
| CVE-2026-54896 | переполнение кучи при сериализации исключения с большим отступом |
| CVE-2026-54897 | use-after-free в итераторах `Oj::Doc` при реентрантном закрытии |
| CVE-2026-54898 | use-after-free в SAJ-колбэке после мутации входных данных |
| CVE-2026-54899 | use-after-free при переключении кэша символьных ключей парсера |
| CVE-2026-54900 | `memcpy` с отрицательным размером в обработке атрибута `create_id` |
| CVE-2026-54901 | use-after-free из-за отсутствия GC-маркировки `array_class` и `hash_class` |
| CVE-2026-54902 | use-after-free в SAJ-колбэке длинного ключа |
| CVE-2026-54903 | переполнение целого при загрузке JSON-строки больше 2 ГиБ |

А вот **двум багам, из которых собрана RCE-цепочка, отдельные CVE в статье не названы** — GitLab закрыл вопрос просто подняв Oj до 3.17.3 в патч-релизе 10.06.2026. Так что искать эту историю по CVE-идентификатору бесполезно; ориентир — версия GitLab и версия гема.

## 🎯 Что из этого стоит унести

- **Мелкая зависимость — это тоже поверхность атаки.** Oj — это 298 версий и ~305 млн загрузок с rubygems. Библиотека «просто парсит JSON», а закончилось выполнением команд от `git` в GitLab.
- **Memory-safe язык не отменяет C внутри гемов.** Если у зависимости есть `ext/` — она наследует все классические проблемы C, просто прячет их за красивым Ruby-API.
- **Триггер может быть в самой безобидной фиче.** Красивый diff ноутбуков — удобство для дата-сайентистов, а оказалось входом в парсер, доступным любому пользователю через собственный проект.
- **Пропущенное окно опаснее самой уязвимости.** С 10.06.2026 патч есть; всё, что не обновилось, уязвимо до сих пор, а PoC с 24.07.2026 публичный.

## 💻 Что проверить у себя

Владельцу актуально только если где-то поднят **self-managed GitLab** — на gitlab.com и Dedicated делать нечего.

```bash
# версия GitLab
gitlab-rake gitlab:env:info | head -20
# или из контейнера:
docker exec -it gitlab cat /opt/gitlab/version-manifest.txt | grep -i '^gitlab-ce\|^gitlab-ee'

# версия гема Oj внутри инсталляции (главный критерий)
gitlab-rails runner 'require "oj"; puts Oj::VERSION'
```

Нужно: **Oj ≥ 3.17.3** и GitLab ≥ 18.10.8 / 18.11.5 / 19.0.2.

| Система | Что делать |
| :--- | :--- |
| **Gentoo** (основная) | Официального ebuild GitLab в ::gentoo нет — обычно это Omnibus-пакет или контейнер. Обновлять источником установки, а не портежем |
| **Debian / Ubuntu** | `sudo apt update && sudo apt install gitlab-ce` (или `-ee`) из репозитория GitLab |
| **Arch** (с июня 2026) | `gitlab` есть в AUR; после обновления проверить версию Oj командой выше |
| **Entware / RT-AX56U** | ➖ нерелевантно: GitLab на armv7 с 512 МБ RAM не живёт |

Если обновиться прямо сейчас нельзя — как временная мера годится отключение рендеринга diff для `.ipynb` в затронутых инстансах, но это именно временная мера: уязвим сам парсер, а не только этот путь.
