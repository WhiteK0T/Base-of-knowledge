# 🚀 73 ток/с из Qwen3.6-27B в llama.cpp без потери качества (johenews)

Конспект ролика [«Тебе врут про скорость локальных LLM. Как я выжал 73 токен/с из Qwen3.6, не теряя качество»](https://www.youtube.com/watch?v=w178rnvn2RQ) канала [**johenews**](https://www.youtube.com/@johenews21) (02.06.2026, ~23 минуты). Видео расшифровано whisper, команда снята с экрана. Значения по умолчанию и рекомендации сверены с [карточкой Qwen3.6-27B](https://huggingface.co/Qwen/Qwen3.6-27B), [документацией llama-server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) и [гайдом Unsloth](https://unsloth.ai/docs/models/tutorials/qwen3.6). Те же настройки автор раньше выкладывал постом, по нему есть заметка [MTP-ускорение в llama.cpp](../../../AI/Local-LLM/MTP-%D1%83%D1%81%D0%BA%D0%BE%D1%80%D0%B5%D0%BD%D0%B8%D0%B5%20%D0%B2%20llama.cpp%20%28Qwen3.6%2027B%29%20%E2%80%94%20%D1%82%D1%8E%D0%BD%D0%B8%D0%BD%D0%B3%20%D0%BB%D0%BE%D0%BA%D0%B0%D0%BB%D1%8C%D0%BD%D0%BE%D0%B3%D0%BE%20%D0%B0%D0%B3%D0%B5%D0%BD%D1%82%D0%BD%D0%BE%D0%B3%D0%BE%20%D0%B8%D0%BD%D1%84%D0%B5%D1%80%D0%B5%D0%BD%D1%81%D0%B0%20%28--fit%2C%20vLLM%2C%20%D1%88%D0%B0%D0%B1%D0%BB%D0%BE%D0%BD%D1%8B%29.md).

**Главная мысль:** цифра «столько-то токенов в секунду» без условий ничего не значит. Она зависит от кванта, размера контекста и десятка других параметров. Красивый бенчмарк на самом мелком кванте с минимальным контекстом бесполезен для работы. Настраивать нужно сразу по четырём осям: **скорость, качество, стабильность и удобство**. Автор пишет код на TypeScript и Go и считает, что локальные модели уже близко подошли к платным вроде Claude. По его словам, «не дотягивают» обычно не модели, а настройки.

## Модель, движок, результат

- **Модель:** **Qwen3.6-27B** (dense), квант **UD-Q8_K_XL** от Unsloth, на **двух видеокартах**.
  - Qwen3.5 плохо работала с инструментами, и в агентном режиме её было трудно использовать. Qwen2.5 заметно слабее.
  - Если сидите на Qwen3, 3.5 или 2.5, автор советует попробовать 3.6.
- **Dense против MoE:** dense-модель 27B по тестам лучше MoE-модели **35B-A3B** почти во всём. MoE быстрее, потому что на каждом шаге работают не все параметры, но обычно отвечает хуже.
- **Движок:** автор советует **llama.cpp** или **vLLM**, а не Ollama и LM Studio. Сам он выбрал llama.cpp.
- **Форматы под конкретное железо:** на Mac — **MLX**. На Blackwell — **NVFP4**, но у автора он в vLLM не завёлся.
- **MTP (Multi-Token Prediction):**

| Движок | Без MTP | С MTP | Принятие черновика (draft acceptance) |
| :--- | :--- | :--- | :--- |
| vLLM | ~45 ток/с | ~50 ток/с | ~5 % — MTP почти не работал |
| **llama.cpp** | — | **~73–75 ток/с** | **~0,74** |

- **Скорость обработки промпта (PP)** у автора — ~2800 ток/с.

## PP и TG — что именно мерить

| Метрика | Что это | От чего зависит |
| :--- | :--- | :--- |
| **PP** (prompt processing) | скорость, с которой модель «читает» промпт | вычислительная мощность GPU. На видеокарте почти мгновенно. На CPU с обычной RAM — порядка десятков ток/с, и задержка сильно ощущается |
| **TG** (token generation) | скорость, с которой идёт ответ. Именно её чувствует пользователь | **пропускная способность видеопамяти**: на каждый токен надо прочитать все (активные) веса. Плюс размер модели и квант. TG всегда медленнее PP, потому что токены генерируются строго по одному |

- **Квант:** чем сильнее сжата модель, тем она быстрее и тем глупее.
- **KV-кэш:** чем длиннее диалог, тем медленнее генерация, потому что модели приходится учитывать весь предыдущий контекст. Слишком маленький контекст тоже плох: работа просто не помещается.

## Четыре оси настройки

| Ось | От чего зависит в первую очередь |
| :--- | :--- |
| **Качество** | квант модели и сэмплинг (температура, top-k, top-p, штрафы) |
| **Стабильность** | `--batch-size` и `--ubatch-size`. Слишком агрессивные значения роняют процесс |
| **Удобство** | размер контекста |
| **Скорость** | MTP, flash attention, распределение по картам, число слотов |

## Команда автора

```bash
pm2 start bash --name llama-server -- -c "/путь/к/llama.cpp/build/bin/llama-server \
  -m /путь/к/моделям/Qwen3.6-27B-UD-Q8_K_XL.gguf \
  --host 0.0.0.0 --port 8080 \
  -ngl 999 \
  -ts 0,0 \
  --ctx-size 262144 \
  --batch-size 512 --ubatch-size 256 \
  --flash-attn on \
  --parallel 1 \
  --temp 0.6 --top-p 0.95 \
  --reasoning-budget 0 \
  --spec-type draft-mtp --spec-draft-n-max 2"
```

- **`pm2`:** менеджер процессов из мира Node.js, держит сервер в фоне и перезапускает при падении. На своих системах проще завести обычную службу, примеры ниже.
- **`--host 0.0.0.0`:** сервер открыт всей сети. Без `--api-key` и файрвола так делать не стоит.

## Параметры по порядку

### Контекст: `--ctx-size 262144`

- **Почему максимум:** 262 144 — родное окно модели. Это **главный параметр для удобства**: длинная беседа не переполняет контекст, модель помнит, о чём её спрашивали раньше.
- **Цена:** чем больше контекст, тем больше нужно VRAM под KV-кэш и тем ниже скорость. Автор всегда выбирает удобство.
- **Если не влезает:** уменьшите вдвое, до ~131 тыс. Этого хватает для большинства задач, но зависит от размера проекта.
- **Нижняя граница от Qwen:** окно не меньше **128K**, иначе страдает режим рассуждений (thinking).

### Сэмплинг для кода: температура, top-k, top-p, штрафы

- **Температура:** чем выше, тем модель «креативнее», чем ниже — тем строже. Для кода её снижают. Автор ставит **`--temp 0.6`**: по его словам, этот параметр мало кто задаёт, а влияет он сильно, и не только у Qwen.
- **top-k:** модель выбирает следующий токен только из k самых вероятных. Для кода Qwen рекомендует **20**.
- **top-p:** берётся минимальный набор самых вероятных токенов с суммарной вероятностью ≥ p. Для кода — **0,95**, баланс между качеством и разнообразием. Чем больше p, тем больше вариативности и выше риск ошибок.
- **presence penalty и repetition penalty:** штрафы за уже использованные токены. В обычном тексте повторы режут слух, а в коде повторяться — норма. Поэтому для кода автор советует штрафы **выключать**: `--presence-penalty 0`.

Как это сходится с первоисточниками:

| | Значение по умолчанию в `llama-server` | Qwen: thinking, точный кодинг | Qwen: thinking, общие задачи | Qwen: без thinking |
| :--- | :--- | :--- | :--- | :--- |
| `--temp` | 0,8 | **0,6** | 1,0 | 0,7 |
| `--top-k` | **40** | 20 | 20 | 20 |
| `--top-p` | 0,95 | 0,95 | 0,95 | 0,8 |
| `--min-p` | 0,05 | 0 | 0 | 0 |
| `--presence-penalty` | 0 | 0 | 0 | **1,5** |
| `--repeat-penalty` | 1,0 (выкл.) | 1,0 | 1,0 | 1,0 |

Что из таблицы стоит учесть:

- **Шпаргалка автора** (0,6 / 0,95 / presence 0) совпадает с рекомендацией Qwen **для режима рассуждений и точного кодинга**.
- **`--top-k 20` в его команде нет.** Без флага `llama-server` берёт свои 40, так что для рекомендованного набора его нужно добавить явно. То же касается `--min-p 0`.
- **В `llama-server` presence penalty по умолчанию и так 0.** Значение 1,5, о котором говорит автор, — это рекомендация Qwen для режима без рассуждений.
- **В команде стоит `--reasoning-budget 0`**, то есть рассуждения отключены сразу. Для такого режима Qwen рекомендует другой набор: 0,7 / 0,8 / presence 1,5. Есть два согласованных варианта:
  - **режим с рассуждениями** (`--reasoning-budget -1`, по умолчанию) и набор 0,6 / 0,95 / top-k 20 / presence 0 — он точнее;
  - **режим без рассуждений**, если нужна скорость ответа, и набор 0,7 / 0,8 / top-k 20 / presence 1,5.

  Какой из них лучше для ваших задач, проверяйте сами. В шпаргалке автора смешаны оба.
- **Клиент может перебить настройки сервера:** параметры, переданные в запросе к API (например, агентом или IDE), имеют приоритет над флагами сервера.

### Стабильность: `--batch-size` и `--ubatch-size`

- **Что это:** промпт обрабатывается пачками. `batch` — сколько токенов за один логический шаг, `ubatch` — на какие физические куски пачка делится внутри GPU.
- **Когда менять:** на мощной карте с запасом памяти их можно увеличивать (`-b 1024`/`2048`), и обработка промпта станет быстрее. Но **если сервер падает, первым делом уменьшайте именно их**.
- **Значения по умолчанию:** в `llama-server` это **2048 / 512**. Автор не повышает их, а наоборот **занижает до 512 / 256**, жертвуя скоростью PP ради стабильности и экономии памяти.

### MTP: `--spec-type draft-mtp --spec-draft-n-max 2`

- **Как работает:** встроенные MTP-головы модели предсказывают несколько токенов вперёд, основная сеть проверяет их за один проход. Подробно — в [заметке про MTP](../../../AI/Local-LLM/MTP-%D1%83%D1%81%D0%BA%D0%BE%D1%80%D0%B5%D0%BD%D0%B8%D0%B5%20%D0%B2%20llama.cpp%20%28Qwen3.6%2027B%29%20%E2%80%94%20%D1%82%D1%8E%D0%BD%D0%B8%D0%BD%D0%B3%20%D0%BB%D0%BE%D0%BA%D0%B0%D0%BB%D1%8C%D0%BD%D0%BE%D0%B3%D0%BE%20%D0%B0%D0%B3%D0%B5%D0%BD%D1%82%D0%BD%D0%BE%D0%B3%D0%BE%20%D0%B8%D0%BD%D1%84%D0%B5%D1%80%D0%B5%D0%BD%D1%81%D0%B0%20%28--fit%2C%20vLLM%2C%20%D1%88%D0%B0%D0%B1%D0%BB%D0%BE%D0%BD%D1%8B%29.md).
- **Нужна GGUF-сборка с MTP-головами:** у Unsloth это отдельный репозиторий `Qwen3.6-27B-MTP-GGUF`.
- **Главная метрика — `draft acceptance` в логе сервера** после запроса. Это доля черновых токенов, которые основная модель приняла. Шкала автора:

| Принятие | Оценка |
| :--- | :--- |
| < 50 % | плохо: MTP ест память и вычисления, а пользы почти нет (у автора в vLLM было ~5 %) |
| 60–75 % | нормально (у автора 0,74) |
| > 80 % | отлично: можно поднимать `--spec-draft-n-max` до 3–4 |

- **Значение `--spec-draft-n-max` по умолчанию** в `llama-server` — 3. Автор ставит **2**: чем длиннее черновик, тем ниже доля принятых токенов.

### CUDA для MTP

- **Версия:** для MTP автор советует свежую **CUDA 13**. В репозиториях Ubuntu лежит 12.x, 13-ю ставят из репозитория NVIDIA.
- **Только не 13.2:** Unsloth предупреждает, что с CUDA 13.2 Qwen3.6 может выдавать мусор. Используйте **версию ниже 13.2 или 13.3+**. У автора на 13.3 всё работает без проблем.
- **Старые карты:** CUDA 13 больше не собирает код под карты с compute capability ниже 7.5 (Pascal, Volta — например, GTX 10xx, V100). Для них остаётся CUDA 12.x, подробности — в [заметке про 4×V100](../%D0%9A%D0%B8%D0%B1%D0%B5%D1%80%20%D0%9A%D1%83%D0%B7%D0%BD%D0%B8%D1%86%D0%B0/4%C3%97Tesla%20V100%20SXM2%20%D1%81%20NVLink%20%D0%BF%D1%80%D0%BE%D1%82%D0%B8%D0%B2%202%C3%97RTX%203090%20%E2%80%94%20%D0%B1%D0%BE%D0%BB%D1%8C%D1%88%D0%BE%D0%B9%20%D1%82%D0%B5%D1%81%D1%82%20%28%D0%BA%D0%BE%D0%BD%D1%82%D0%B5%D0%BA%D1%81%D1%82%20%D0%B2%D0%BC%D0%B5%D1%81%D1%82%D0%BE%20%D1%81%D0%BA%D0%BE%D1%80%D0%BE%D1%81%D1%82%D0%B8%2C%20%D1%84%D0%BE%D1%80%D0%BA%20vLLM%2C%20%D0%BA%D0%B0%D1%80%D1%82%D0%B8%D0%BD%D0%BA%D0%B8%2C%20%D0%B2%D0%B8%D0%B4%D0%B5%D0%BE%2C%20%D1%81%D0%BC%D0%B5%D1%82%D0%B0%29.md).

### Несколько видеокарт: `-ts` (tensor split)

- **Что задаёт:** пропорции, в которых слои модели раскладываются по картам. `-ts 1,1` — поровну (то же самое, что `100,100`). **`-ts 0,0` — автоматически**: при всех нулях llama.cpp делит пропорционально свободной памяти, как и без флага.
- **Если карты разные** (например, 8, 12, 16 и 24 ГБ):
  1. Узнайте порядок карт: `nvidia-smi -L` выводит GPU 0, 1, 2, 3.
  2. Задайте пропорции **в этом порядке** под объём памяти, например `-ts 24,12,8,16`.
- **Проверка:** смотрите по логам и `nvidia-smi`, насколько загружена каждая карта. Иногда без явного `-ts` одна карта забита, а вторая почти пустая.

### Flash attention и слоты

- **`--flash-attn on`:** заметно ускоряет внимание и экономит память. В текущем `llama-server` по умолчанию стоит `auto`, но лучше проверить, что он не выключен.
- **`--parallel 1`:** число слотов — одновременных запросов. Если моделью пользуетесь вы один, ставьте **1**: контекст не делится между слотами, и весь объём достаётся одной сессии. Значение по умолчанию в `llama-server` — `-1` (авто).

## Итоговая шпаргалка (с поправками)

Вариант **с рассуждениями** — рекомендованный Qwen для точного кода:

```bash
llama-server -m Qwen3.6-27B-UD-Q8_K_XL.gguf \
  --host 127.0.0.1 --port 8080 \
  -ngl 999 --ctx-size 262144 \
  -b 512 -ub 256 -fa on -np 1 \
  --temp 0.6 --top-k 20 --top-p 0.95 --min-p 0 --presence-penalty 0 \
  --spec-type draft-mtp --spec-draft-n-max 2
```

- **Без рассуждений:** добавьте `--reasoning-budget 0` и смените сэмплинг на `--temp 0.7 --top-p 0.8 --presence-penalty 1.5`.
- **Наружу:** `--host 0.0.0.0` используйте только вместе с `--api-key` или файрволом.

## 🐧 Запуск службой вместо pm2

Сборка и установка llama.cpp по системам описаны в отдельной заметке: [llama.cpp — движок локального инференса GGUF](../../../AI/Local-LLM/llama.cpp%20%E2%80%94%20%D0%B4%D0%B2%D0%B8%D0%B6%D0%BE%D0%BA%20%D0%BB%D0%BE%D0%BA%D0%B0%D0%BB%D1%8C%D0%BD%D0%BE%D0%B3%D0%BE%20%D0%B8%D0%BD%D1%84%D0%B5%D1%80%D0%B5%D0%BD%D1%81%D0%B0%20GGUF.md). Если llama.cpp собираете сами, понадобится CUDA:

| Система | CUDA | Служба |
| :--- | :--- | :--- |
| **Gentoo** (OpenRC) | `dev-util/nvidia-cuda-toolkit` (в дереве 13.4.x, а для старых карт 12.9.x) | init-скрипт OpenRC (ниже) |
| **Debian / Ubuntu** | репозиторий NVIDIA → `cuda-toolkit-13-3` или новее (не 13.2) | unit systemd (ниже) |
| **Arch** | `pacman -S cuda` (13.x); llama.cpp — AUR `llama.cpp-cuda-git` | unit systemd |
| **Entware** (RT-AX56U) | неприменимо: на роутере нет GPU, а 27B не влезет в 512 МБ RAM. Роутер может быть только клиентом OpenAI-совместимого API | — |

**systemd** (`/etc/systemd/system/llama-server.service`):

```ini
[Unit]
Description=llama.cpp server (Qwen3.6-27B)
After=network-online.target

[Service]
User=llm
EnvironmentFile=/etc/default/llama-server
ExecStart=/opt/llama.cpp/build/bin/llama-server $LLAMA_ARGS
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```bash
# /etc/default/llama-server
LLAMA_ARGS="-m /srv/models/Qwen3.6-27B-UD-Q8_K_XL.gguf --host 127.0.0.1 --port 8080 -ngl 999 -c 262144 -b 512 -ub 256 -fa on -np 1 --temp 0.6 --top-k 20 --top-p 0.95 --min-p 0 --spec-type draft-mtp --spec-draft-n-max 2"

systemctl daemon-reload && systemctl enable --now llama-server
journalctl -u llama-server -f | grep -i accept     # следить за draft acceptance
```

**OpenRC** (`/etc/init.d/llama-server`, `chmod +x`):

```sh
#!/sbin/openrc-run
description="llama.cpp server"
command="/opt/llama.cpp/build/bin/llama-server"
command_args="${LLAMA_ARGS}"
command_user="llm"
command_background=true
pidfile="/run/${RC_SVCNAME}.pid"
output_log="/var/log/llama-server.log"
error_log="/var/log/llama-server.log"
depend() { need net; }
```

```bash
# /etc/conf.d/llama-server — та же строка LLAMA_ARGS="…"
rc-update add llama-server default && rc-service llama-server start
tail -f /var/log/llama-server.log | grep -i accept
```
