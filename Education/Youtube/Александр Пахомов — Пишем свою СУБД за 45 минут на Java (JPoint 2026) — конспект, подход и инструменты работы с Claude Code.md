## 2. Подход по шагам

### 2.1. Сначала — как будешь мерить

До первой строки кода автор выбрал **критерий готовности**: бенчмарк **[ClickBench](https://github.com/ClickHouse/ClickBench)** от команды ClickHouse — одна таблица `hits` (~105 колонок, данные Яндекс.Метрики, ~75 ГБ TSV) и **43 аналитических запроса** (`COUNT`, `GROUP BY`, `LIKE '%google%'`, `AVG`…). Есть готовые результаты десятков БД для сравнения.

Затем — **картинка системы в голове** («квадратики со стрелочками»): Java-процесс JPointDB, на вход TSV, на старте грузит данные и отдаёт REST для CLI и веба.

### 2.2. «The Prompt» — первый промпт решает направление

Автор особенно тщательно пишет **первый промпт** (называет его *the prompt*): от него зависит, куда пойдёт система; если она с самого начала пойдёт не туда, дальше придётся постоянно «подгонять и откатывать». Сам промпт:

> Я хочу написать персонализированную базу данных узкого назначения для своих нужд. Название JPointDB. Я буду делать SQL запросы поверх TSV файла. Это будут аналитические запросы. **DoD: JPointDB проходит ClickBench.** JPointDB должна быть максимально производительной (быстрее большинства БД из ClickBench). Как я буду работать с JPointDB: запускаю сервер (java process), передаю путь к tsv файлу, делаю аналитические SQL запросы через REST интерфейс, используя один из клиентов (web, cli). Стек: java 25, gradle 9, JUnit. Используй как можно меньше сторонних библиотек. Мне нужен контроль над исходным кодом для максимальной производительности. Говори со мной на русском. **Сначала план.**

Из чего он состоит — и почему:

| Элемент | Зачем |
| :--- | :--- |
| **Имя системы** сразу | без него неудобно ссылаться на то, о чём идёт речь |

Перед промптом: `/status` (сколько лимита осталось), `/model` → Opus с **max effort** — «effort это трейд-офф время/качество, я всегда выбираю качество».

### 2.3. Ревью плана и ответы на вопросы агента

Claude выдал план с **ключевыми архитектурными решениями** и **вопросами перед стартом**:

- хранение — свой **колоночный формат** на диске, одноразовая конвертация TSV (mmap-friendly);
- исполнитель — **векторный** (батчи по 4096 строк, pull-based) + **SIMD через Java Vector API** (`jdk.incubator.vector`);
- память — **off-heap через FFM API** (`MemorySegment`), GC не трогает данные колонок;
- SQL — **ручной recursive-descent парсер** (без ANTLR, 500–1000 строк: ClickBench использует узкое подмножество, без JOIN и оконных функций);
- HTTP — `com.sun.net.httpserver` из JDK, свой JSON-сериализатор;
- параллелизм — платформенные потоки + `ForkJoinPool` (виртуальные не подходят для CPU-bound);
- единственная внешняя зависимость — JUnit 5;
- этапы 0–8: скелет → колоночное хранилище → SQL-парсер и AST → планировщик → векторный исполнитель → SIMD → REST и клиенты → ClickBench → «профилирование и тюнинг (бесконечно)».

Вопросы агента: формат on-disk? куда писать файлы (`--data-dir`)? словарное кодирование строк — глобальное или поблочное? **TDD сразу** или сначала прототип? Vector API (incubator) — ок?

Ответ автора одной строкой: `1) подтверждаю 2) --data-dir отдельный 3) что ты имеешь в виду под словарной кодировкой строк? поясни 4) TDD 5) ок, используй vector API`. Непонятное — **спрашивает у агента**, а не соглашается вслепую (Claude объяснил словарь на примере колонки браузеров: Chrome=0, Firefox=1…).

> [!tip] Recap
> Вернувшись после перерыва, автор увидел новую функцию Claude Code **recap** — краткое напоминание, на чём остановились. Отключается в `/config`.

### 2.4. Golden-тесты против эталонной БД — до SQL-движка

Ключевой ход доклада. Когда хранилище готово и агент рвётся писать SQL, автор **намеренно останавливается**:

> функциональные тесты крайне важны для корректной работы запросов. нужно сразу их написать. возьми подмножество данных из clickbench, возьми референсную БД, которая есть в clickbench, используй результаты выполнения этих запросов для референсной бд как **golden dataset** для JPointDB. в остальном согласен.

То есть **спецификация через поведение существующей системы**: SQL уже специфицирован, отличаться может только порядок строк. Claude сам выбрал **DuckDB** (он уже стоял на машине и это ровно тот же сценарий: файл → один процесс → аналитика) и собрал:

```
bench/
├── scripts/setup-golden.sh   # качает 100k строк, гоняет DuckDB, пишет эталоны
├── golden/
│   ├── create.sql            # схема hits (105 колонок)
│   ├── queries.sql           # 43 запроса ClickBench
│   └── results/q00…q42.tsv   # эталоны (176 КБ — коммитятся)
├── sample/hits.tsv           # 100k строк, 115 МБ — в .gitignore
└── src/test/java/…/ClickBenchGoldenTest.java   # параметризованный, @Disabled до появления движка
```

Это «трушное TDD»: тесты появились, когда парсера ещё не было. Дальше — «газ, газ»: параллельно через субагентов. Промежуточный отчёт: **209 тестов, 0 падений, 9 «осознанных skip»**, 34 из 43 запросов сходятся с DuckDB, причины skip перечислены (не реализованы `STRLEN`, `REGEXP_REPLACE`, `EXTRACT`, `DATE_TRUNC`, неоднозначный tie-break в `ORDER BY … LIMIT`).

### 2.5. Сначала доделать функциональность, потом скорость

Агент несколько раз предлагает перейти к производительности — автор отказывает: **«полностью доделываем функциональную часть, покрываем тестами, и только потом перформанс»**. Итог функциональной части — **43/43 на 100k строк за ~3 часа одного вечера**.

Попутно агент предложил сначала дать пользователю «пощупать руками» (REST + CLI + веб), а самому чинить skip — автор согласился. Мелочи, которые он поправил промптами: скрипты запуска `start-server.sh` / `cli.sh` вместо команд Gradle, история и автодополнение в CLI (появилась зависимость **JLine** — автор одобрил: «одна, 1 МБ»), тёмная тема веба с CodeMirror.

### 2.6. End-to-end тесты вместо ручного тестирования

Когда в CLI снова и снова что-то не работало (`\s`, история), автор сформулировал правило: пока ты сам тестируешь и носишь агенту баги — ты узкое место. **Настрой агенту обратную связь**:

> вот эти команды не работают, сделай end-to-end тесты, которые будут это валидировать.

### 2.7. Quality gates — до тюнинга производительности

Логика: «перформанс может сломать то, чего я не увижу» — значит, сначала **«строительные леса»** из анализаторов. Промпт: *«настраиваем quality gates. сделай анализ БД на Java, предложи инструменты для контроля качества кода: линтеры, чекстайлы, статические анализаторы»*. Claude предложил три уровня:

| Уровень | Инструменты | Решение автора |
| :--- | :--- | :--- |
| **Tier 1** — жёсткие гейты в `./gradlew check` | **Spotless** (форматирование), **ErrorProne** (падает компиляция на серьёзных предупреждениях), **Checkstyle** (~15 правил: без wildcard-импортов, строка ≤ 140, именование…), **JaCoCo** (порог покрытия 80% на `core`) | сделать |
| **Tier 2** | **SpotBugs**, **PIT** — мутационное тестирование (меняет `>` на `>=`, `+1` на `-1` и смотрит, ловят ли тесты; «отличная метрика качества тестов», медленно — локально/nightly) | сделать |
| **Tier 3** | **NullAway** (+JSpecify), **OWASP Dependency-Check**, **SonarCloud**, Checker Framework, JDepend/jQAssistant | в **`BACKLOG.md`** |

> [!tip] Лайфхак автора — BACKLOG.md в репозитории
> Агент часто предлагает разумные вещи, в которые прямо сейчас вкладываться не хочется. Вместо «нет» — **«отложи в BACKLOG.md»**: идеи не теряются и не отвлекают.

NullAway всё же включили («вчера был доклад про него»). Итоговый пайплайн:

```bash
./gradlew check                    # Spotless + Checkstyle + ErrorProne/NullAway + SpotBugs + тесты + JaCoCo — ~11 с
./gradlew pitest                   # мутационное тестирование — ~2,5 мин (~71% мутантов убито)
./gradlew dependencyCheckAnalyze   # CVE-скан зависимостей (долго — качает базу NVD)
./gradlew spotlessApply            # автоисправление форматирования
```

### 2.8. Производительность: сначала baseline, потом профилирование

Агент предлагал сразу профилировать — автор попросил **тот же приём, что и с корректностью**:

> хочу side-by-side сравнение перформанса с duckdb на запросах clickbench. сделай это сейчас, потом идём по твоему плану, а в конце снова сравнение с duckdb.

- На 100k строк: сумма 43 запросов — JPointDB **970 мс** против DuckDB **43 мс**. «100k для функциональных тестов нормально, для перформанса мало» → прогон на **1 млн** строк: **11,8 с против 137 мс (в 86 раз медленнее)**; DuckDB использует все ядра, JPointDB пока однопоточная.
- **async-profiler** показал раскладку CPU: `Pattern.compile()` в `LIKE` на **каждую строку** — 21,7%; `new String(bytes)` на каждую ячейку словаря — 15,5%; TimSort — 11,3%; GC — 6,9%; `HashMap` в `GROUP BY` — 6,3%.
- Автор **сам смотрит flame graph** конкретного запроса (Q21 `LIKE '%google%'`), просит агента сделать фикс и **показать flame graph после**. Фикс: кэш `Pattern`, а простые `%lit%`/`lit%`/`%lit` — через `String.contains/startsWith/endsWith`, которые HotSpot превращает в SIMD-интринсики. Q21: **621 → 103 мс (×6)**, сумма 43 запросов **−33,5%**.
- Затем просит агента **самого прочитать новый flame graph** и найти следующее узкое место — проверяет, видит ли агент то же, что и он (`new String` → кэш строк словаря).
- Дальше цикл «замер → анализ → оптимизация → замер» три вечера: SIMD-агрегаты, radix-партиционирование, кэши, нативные даты.

Итог на 1 млн строк (JIT прогрет, 6 прогонов × 15, минимум): **JPointDB 183 мс против DuckDB 55 мс — в 3,3 раза медленнее** суммарно, при этом **быстрее DuckDB** на однострочных агрегатах (`MIN/MAX`, `SUM+COUNT+AVG`, `COUNT(*)`, `LIKE`) и сильно медленнее на тяжёлых `GROUP BY` с миллионом групп и `REGEXP_REPLACE`. История сессии: 447 → 380 → 358 → 256 → 300 → 222 → 187 → **183 мс**.

Автор сам оговаривает: это **«вайберский перформанс»** — для честных замеров нужна отдельная контролируемая инфраструктура.

## 4. Технические идеи из JPointDB, которые стоит запомнить

| Идея | Суть |
| :--- | :--- |
| Колоночное хранение | каталог `*.jpdb/` на таблицу: `meta.json` со схемой + **по файлу на колонку**; числа — сырые массивы примитивов + bitmap NULL в стиле Arrow |
| Словарное кодирование строк | глобальный словарь на колонку + `int`-идентификаторы; при слишком большом числе уникальных значений — откат на сырые строки (offsets + bytes) |
| mmap + FFM | `MemorySegment` и `Arena.ofShared`: данные вне кучи, GC их не видит |
| Sniffing схемы | первый проход по TSV определяет типы (`i32/i64/f64/string`) — БД работает с любым TSV, не только `hits` |
| SQL без генераторов | `Tokenizer` → recursive descent → sealed AST → `Binder` → исполнитель; sealed-иерархии + exhaustive `switch` держат код честным |
| `LIKE` без regex | простые шаблоны → `String.contains/startsWith/endsWith` (SIMD-интринсики HotSpot) |
| Детерминированные эталоны | в запросах `ORDER BY COUNT(*) DESC LIMIT N` добавлен вторичный ключ, иначе порядок при равенстве не совпадает с DuckDB |

## 5. Повторить у себя

| Система | JDK 25 | DuckDB CLI (для эталонов) | async-profiler |

| **Gentoo** | `dev-java/openjdk:25` или `dev-java/openjdk-bin:25` | `dev-db/duckdb` | архив с [релизов GitHub](https://github.com/async-profiler/async-profiler/releases) |
| **Debian / Ubuntu** | `openjdk-25-jdk` (в Debian 13 — через обновления; иначе SDKMAN) | в Debian 13 пакета нет — `curl https://install.duckdb.org \| sh` | архив с релизов GitHub |
