Четвёртый ролик серии про собеседования. Видео расшифровано whisper, SQL сверен со слайдами. Рекламные вставки опущены.

**Главная мысль:** DevOps — не DBA, он не проектирует схемы и не оптимизирует запросы, но с базами работает постоянно, и блок про них на собеседовании бывает почти всегда. Ниже 10 самых частых вопросов **по убыванию популярности** — на примере PostgreSQL.

## 1. «База работает медленно — с чего начнёте?»

Варианты формулировки: «пользователи жалуются, что всё тормозит», «как найти медленный запрос?».

**Сначала — встречные вопросы, а не конфиг:** медленно всё или одна страница? Когда началось? Что перед этим менялось — выкатка, рост нагрузки, новый отчёт? **Половина оценки — здесь**: собеседующему важно, будешь ли ты крутить настройки наугад или сначала соберёшь факты.

Дальше — **сверху вниз**:

1. **Сервер:** CPU, память, диск, ожидание диска (iowait). Часто «медленная база» — это забитый диск.
2. **Соединения и долгие запросы** внутри базы.
3. **Блокировки:** одна транзакция держит строки, остальные ждут её.
4. **`idle in transaction`** — открытая и брошенная транзакция: держит блокировки и мешает **autovacuum** (фоновая уборка старых версий строк).
5. **Виновник среди запросов — `pg_stat_statements`:** показывает не самый медленный запрос, а **самый дорогой суммарно**. Запрос на 20 мс, который выполняется 100 000 раз в минуту, вредит сильнее отчёта на минуту раз в сутки.
6. **План — `EXPLAIN ANALYZE`:** как база на самом деле выполняет запрос, читает ли таблицу целиком, где теряет время.
7. **Только потом** — настройки памяти и обслуживание: не раздулись ли таблицы (bloat), успевает ли autovacuum.

Итог: виновата обычно не «база вообще», а **один-два запроса без нужного индекса** или **слишком много соединений**.

```sql
-- соединения по состояниям (запрос со слайда)
SELECT state, count(*) AS c
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state ORDER BY c;

-- долгие запросы и брошенные транзакции
SELECT pid, usename, state, now() - xact_start AS xact_age, left(query, 80)
FROM pg_stat_activity
WHERE state IN ('active', 'idle in transaction')
ORDER BY xact_age DESC NULLS LAST;

-- кто кого блокирует
SELECT pid, pg_blocking_pids(pid) AS blocked_by, left(query, 80)
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- самые дорогие запросы суммарно (нужно расширение pg_stat_statements)
SELECT calls, round(total_exec_time) AS total_ms, round(mean_exec_time::numeric, 2) AS mean_ms, left(query, 80)
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;

-- EXPLAIN — только план; EXPLAIN ANALYZE — выполняет запрос и показывает реальное время
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'ada@example.com';
```

> `EXPLAIN ANALYZE` **реально выполняет** запрос — для `UPDATE`/`DELETE` оборачивать в `BEGIN; … ROLLBACK;`.

## 2. Потоковая (физическая) и логическая репликация

| | Физическая (потоковая) | Логическая |
| :--- | :--- | :--- |
| Уровень | файлы: реплика получает поток **WAL** и применяет байт в байт | изменения строк: издатель (publisher) публикует таблицы, подписчик (subscriber) получает |
| Результат | точная копия **всего кластера**, та же версия PostgreSQL | выбранные таблицы |
| Реплика | только чтение | **можно писать** |
| Между версиями | нет | **да** |
| Ограничения | — | не переносит изменения структуры (DDL), нужны первичные ключи, дороже по ресурсам |
| Для чего | **отказоустойчивость**, разгрузка чтения | **миграции**, выборочный обмен данными |

Смежный вопрос — **«как обновить версию PostgreSQL без простоя?»**: логическая репликация на новую версию, затем переключение приложения.

## 3. Концепции бэкапов

Три способа деления:

1. **Логический и физический.** Логический (`pg_dump`) — данные как набор команд: гибкий, переносится между версиями, но медленный на больших объёмах. Физический — копия файлов кластера (`pg_basebackup`): снимается и восстанавливается быстрее, но привязан к версии и платформе.
2. **Полный, инкрементальный, дифференциальный.** Полный — всё; инкрементальный — изменения с прошлого бэкапа; дифференциальный — изменения с последнего полного.
3. **PITR (Point-in-Time Recovery)** — **самое важное для DevOps**: базовая копия + архив WAL → восстановление на любой момент, например за минуту до того, как кто-то обнулил базу. Готовые инструменты — **pgBackRest** и **WAL-G**.

Закончить ответ двумя понятиями — схема бэкапов выбирается по ним:

- **RPO** (Recovery Point Objective) — сколько данных готовы потерять;
- **RTO** (Recovery Time Objective) — за сколько обязаны подняться.

## 4. Зачем нужны индексы

- Без индекса база **читает таблицу целиком**. Индекс — отдельная структура, где значения колонки хранятся упорядоченно, и можно сразу перейти к нужным строкам.
- **У индекса есть цена** (это и показывает понимание): он замедляет запись (обновляется при каждой вставке и изменении) и занимает место, иногда сравнимое с самой таблицей. Лишний индекс — лишние ресурсы.

**«Почему запрос медленный, хотя индекс есть?»**

- планировщик решил, что прочитать таблицу целиком дешевле;
- в условии **функция или приведение типа** — индекс по колонке не подходит (`WHERE lower(email) = …` при индексе по `email`);
- **низкая селективность** — в колонке 2–3 значения, толку от индекса мало;
- проверить — `EXPLAIN ANALYZE`: использовался ли индекс (`Index Scan` / `Bitmap Index Scan` или `Seq Scan`).

## 5. Отказоустойчивый кластер PostgreSQL

- PostgreSQL сам умеет реплицировать и повышать реплику до мастера по команде, но **автоматического переключения нет** — нужен кто-то, кто принимает решение.
- Это **Patroni**: ставится рядом с каждым экземпляром базы, следит за состоянием, управляет ролями. Сам ничего не помнит — **кто лидер, хранится в распределённом хранилище**, чаще всего **etcd** из **3 или 5 узлов** (решение принимает большинство).
- **Единая точка входа — HAProxy:** приложение ходит на один адрес и не знает, кто лидер. HAProxy спрашивает **REST API Patroni**, кто лидер, шлёт туда запись, а чтение может раскидывать по репликам.
- **Падение мастера:** Patroni на нём перестаёт продлевать в etcd запись «я лидер» → остальные видят, что лидера нет, выбирают **самую свежую реплику** и повышают её → другие реплики переподключаются к новому мастеру → HAProxy шлёт запись туда.

**Синхронная и асинхронная репликация:** асинхронная — переключение быстрое, но последние транзакции можно потерять; синхронная — ничего не теряем, но платим **задержкой каждого коммита**.

## 6. Что такое WAL и когда данные попадают в файлы

**WAL (Write-Ahead Log)** — журнал упреждающей записи. Правило: **любое изменение сначала пишется в журнал, и только потом — в файлы данных.**

1. Изменение: страница правится в памяти (**shared buffers**) и помечается «грязной», запись об изменении уходит в WAL.
2. **На коммите на диск сбрасывается журнал.** Подтверждение клиенту = запись есть в WAL, а не в файле таблицы.
3. Грязные страницы в файлы данных пишет позже **checkpoint** — по времени (`checkpoint_timeout`) или по объёму журнала (`max_wal_size`). Журнал до этой точки для восстановления больше не нужен.

Зачем так сложно:

- **быстро** — запись в журнал последовательная, а страницы разбросаны по файлам;
- **восстановление после сбоя** — последний checkpoint + проигрывание журнала;
- на WAL держатся **физическая репликация и PITR**.

**Частота checkpoint'ов:** часто — быстрое восстановление, но больше записи на диск; редко — меньше записи, но восстановление дольше.

## 7. Зачем PgBouncer

- PostgreSQL на **каждое соединение создаёт отдельный процесс** со своей памятью. 100 соединений — нормально, 1000 — серьёзная нагрузка просто на их обслуживание, даже без запросов. Приложения открывают пул на каждом экземпляре, и при множестве реплик приложения (подов) счёт быстро уходит в тысячи.
- **PgBouncer** — лёгкий пул соединений перед базой: клиенты подключаются к нему, а он держит немного реальных соединений и переиспользует их (на слайде: 1000 клиентов → ~30 серверных соединений, `SHOW POOLS;`).

| Режим | Соединение выдаётся | Когда |
| :--- | :--- | :--- |
| `session` | на всю сессию клиента | пользы мало — то же, что без пула |
| **`transaction`** | на время транзакции | **основной рабочий режим** |
| `statement` | на один запрос | редко |

Ещё PgBouncer помогает **пережить всплеск нагрузки** (клиенты ждут в очереди) и **переключать приложение между базами**, не трогая само приложение.

> В режиме `transaction` нельзя полагаться на состояние сессии между транзакциями (`SET`, advisory-блокировки, временные таблицы); подготовленные выражения поддерживаются с PgBouncer 1.21 (`max_prepared_statements`).

## 8. Виды JOIN — «на запомнить»

| JOIN | Что возвращает |
| :--- | :--- |
| `INNER` | только совпадения в обеих таблицах |
| `LEFT` | все строки левой + `NULL`, где справа ничего нет |
| `RIGHT` | наоборот |
| `FULL OUTER` | всё из обеих |
| `CROSS` | каждую строку с каждой |
| self-join | таблица соединяется сама с собой |

## 9. Мониторинг PostgreSQL

Стандартная схема: **postgres_exporter** рядом с базой → **Prometheus** забирает метрики → **Grafana** рисует → **Alertmanager** шлёт алерты. Важнее — **куда смотреть**:

1. место на диске;
2. число соединений относительно `max_connections`;
3. отставание реплики (replication lag);
4. длинные транзакции и висящие `idle in transaction`;
5. блокировки и взаимоблокировки (deadlocks);
6. доля попаданий в кэш (cache hit ratio) и активность записи WAL.

## 10. Что такое ACID

Четыре свойства транзакций:

- **Atomicity (атомарность)** — транзакция выполняется целиком или не выполняется вообще;
- **Consistency (согласованность)** — переводит базу из одного корректного состояния в другое;
- **Isolation (изоляция)** — параллельные транзакции не видят промежуточных результатов друг друга; степень задаётся **уровнями изоляции** (в PostgreSQL по умолчанию `READ COMMITTED`);
- **Durability (долговечность)** — после подтверждения данные не пропадут даже при отключении питания (это и обеспечивает WAL из вопроса 6).

## Бонус: «Что под капотом у SELECT?»

Вопрос, который однажды поставил автора в ступор; в ролике ответ оставлен зрителям. Набросок ответа (не из ролика):

1. клиент шлёт текст запроса своему backend-процессу (напрямую или через PgBouncer);
2. **парсер** строит дерево разбора, **анализатор** проверяет таблицы, колонки и права;
3. **rewriter** применяет правила и раскрывает представления (views);
4. **планировщик** по статистике (`ANALYZE`) выбирает самый дешёвый план — seq scan или индекс, порядок и способ JOIN;
5. **исполнитель** читает страницы через **shared buffers** (нет в кэше — с диска через кэш ОС);
6. для каждой строки проверяется **видимость по MVCC** — снимок данных на момент начала запроса (или транзакции на уровнях выше `READ COMMITTED`);
7. результат уходит клиенту.
