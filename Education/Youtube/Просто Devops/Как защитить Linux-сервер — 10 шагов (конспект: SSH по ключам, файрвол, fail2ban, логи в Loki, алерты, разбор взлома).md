# 🛡️ Как защитить Linux-сервер — 10 шагов (Просто DevOps)

Конспект ролика [«Как защитить Linux»](https://www.youtube.com/watch?v=SF6e_aYOGRE) канала [**«Просто DevOps»**](https://www.youtube.com/@prosto_devops) (18.10.2026, ~28 минут). Видео расшифровано whisper, команды сверены со слайдами. Рекламные вставки курса опущены.

**Главная мысль:** сервер в интернете начинают атаковать в первые минуты. Защититься на 100 % нельзя, поэтому шаги двух видов: **закрыть очевидные дыры**, чтобы бот ушёл к другому хосту, и **видеть, что происходит**, чтобы заметить взлом и разобраться в нём.

> Если делать только два шага из десяти — **вход только по ключам** и **логи на другой машине**.

## Откуда угроза

- **Sophos, 2019:** 10 серверов-приманок (honeypot) в облаках по миру. Первую, в Сан-Паулу, начали атаковать через **52 секунды** после запуска; в среднем каждая получала **~750 попыток входа в час** (больше 10 в минуту, круглосуточно).
- Атакуют не люди, а **автоматика по списку**. Она проверяет три вещи:
  1. есть ли программа с **известной уязвимостью**;
  2. можно ли войти с **простым паролем**;
  3. **торчит ли наружу** база или Redis **без пароля**.
- Если что-то сработало — ставят то, что приносит деньги: чаще всего **майнер**, реже спам-рассылку или бота для DDoS.

## Шаг 1. Научиться видеть: логи входов

Прежде чем защищать — увидеть. Иначе защита строится наугад.

- Главный источник — **журнал systemd**. Имя службы SSH зависит от дистрибутива: `ssh` в Debian/Ubuntu, `sshd` в CentOS и родственных.
- **Ловушка:** многие инструкции велят смотреть `/var/log/auth.log`. В Ubuntu он есть, а в Debian (с 12-й версии) — нет: по умолчанию не ставится **rsyslog**, всё лежит только в журнале.
- В **Debian 13** старые `last`, `lastb` и `lastlog` убраны: формат `wtmp`/`lastlog` не переживает 2038 год. Замена — пакеты `wtmpdb` (`wtmpdb last`) и `lastlog2`. Универсальный инструмент — `journalctl`.

Три вида строк, которые надо узнавать сразу:

| Строка | Что значит |
| :--- | :--- |
| `Failed password` | неверный пароль |
| `Invalid user` | вход под несуществующим пользователем — фон, боты |
| `Accepted` | **успешный вход** — каждая такая строка должна быть понятна: кто, откуда, почему в это время |

Подозрительно: вход в необычное время, с незнакомого адреса, новый пользователь, которого ты не создавал, `sudo` от того, кому не положено.

```bash
journalctl -u ssh --since "24 hours ago" | grep Accepted   # успешные входы за сутки
journalctl -u ssh -f                                       # в реальном времени, как tail -f
w                                                          # кто на сервере прямо сейчас
timedatectl                                                # синхронизированы ли часы
```

- **Время должно быть синхронизировано.** Если часы на двух серверах расходятся на 5 минут, при расследовании «следствие наступает раньше причины». В `timedatectl` смотреть `System clock synchronized: yes`.
- **Переживает ли журнал перезагрузку?** `journalctl --list-boots` — если там только текущая загрузка, журнал живёт в памяти. Лечится строкой `Storage=persistent` в `/etc/systemd/journald.conf`.
- **Не съест ли журнал диск?** `journalctl --disk-usage` показывает объём, лимит — `SystemMaxUse=500M` там же.

## Шаг 2. Автоматические обновления безопасности

Массовые взломы идут не через хитрые «нулевые дни», а через **давно известные дыры, для которых исправление уже вышло**, но не установлено. Бот смотрит версию и пробует готовый эксплойт.

Пример — **regreSSHion** (CVE-2024-6387, Qualys, лето 2024): выполнение кода с правами root в OpenSSH без пароля и ключа. Уязвимы версии с 8.5p1 до 9.7p1; Qualys насчитала **более 14 млн** потенциально уязвимых серверов в интернете. Исправление вышло сразу — вопрос был в том, кто его поставит.

- В Debian/Ubuntu обновления безопасности ставит пакет **unattended-upgrades**. В Ubuntu Server он установлен и включён из коробки, в минимальном Debian — нет:

  ```bash
  sudo apt install unattended-upgrades
  sudo dpkg-reconfigure -plow unattended-upgrades
  ```

- Логи: `/var/log/unattended-upgrades/` (`unattended-upgrades.log`, `unattended-upgrades-dpkg.log`). Если что-то сломалось — первым делом смотреть сюда.
- **Обновление ≠ исправление.** Новое ядро или библиотека установлены, но работает старая версия до перезапуска службы или сервера. В Ubuntu об этом скажет файл `/var/run/reboot-required`, а `needrestart` покажет, каким службам нужен перезапуск.
- Автоперезагрузка есть, но по умолчанию выключена — сначала подумать, что упадёт:

  ```
  // /etc/apt/apt.conf.d/50unattended-upgrades
  Unattended-Upgrade::Automatic-Reboot "true";
  Unattended-Upgrade::Automatic-Reboot-Time "02:00";
  ```

## Шаг 3. Не работать под root: пользователи и sudo

- Создаётся обычный пользователь с правом `sudo`. Смысл — **у каждого действия появляется автор**: каждый вызов `sudo` пишется в журнал (кто, из какого каталога, от чьего имени, какую команду). Без этого в журнале будет «root сделал то-то».

  ```bash
  journalctl _COMM=sudo          # все вызовы sudo
  sudo -l -U anna                # что разрешено пользователю
  ```

- `deploy ALL=(ALL) NOPASSWD: ALL` для всех подряд — **тот же root, только с лишним шагом**. Нужен перезапуск одного сервиса — разрешить только его:

  ```
  # /etc/sudoers.d/anna   (править через visudo -f)
  anna ALL=(root) /usr/bin/systemctl restart nginx
  ```

- **Удалять ненужных пользователей** — уволившихся, подрядчиков, временные `test`: каждый — ещё один забытый вход. `userdel -r test`.

## Шаг 4. SSH: вход только по ключам

Три строки в настройках sshd:

```
PasswordAuthentication no      # только ключи
PermitRootLogin no             # под root по SSH — никто
AllowUsers deploy anna         # кому вообще можно входить
```

**Порядок важен** — иначе закроешь вход и себе («сервер защищён идеально — от всех, включая владельца»):

1. `ssh-keygen -t ed25519` — ключ на своём компьютере;
2. `ssh-copy-id deploy@server` — ключ на сервер;
3. войти по ключу без пароля и **только потом** выключать пароль.

**Ловушка с `sshd_config.d`:**

- В sshd **побеждает первое найденное значение**, а не последнее.
- В начале `/etc/ssh/sshd_config` стоит `Include /etc/ssh/sshd_config.d/*.conf`. В облачных образах Ubuntu там часто лежит файл cloud-init (`50-cloud-init.conf`) с `PasswordAuthentication yes` — он прочитан раньше, и строка в конце основного файла молча игнорируется.
- Поэтому свои настройки кладут **в отдельный файл, который идёт раньше по алфавиту**, например `/etc/ssh/sshd_config.d/01-hardening.conf`.
- Проверять не файл, а **итог**: `sudo sshd -T | grep -Ei 'passwordauth|permitroot|allowusers'`.

Два правила, чтобы не отрезать себе доступ:

1. перед перезапуском — проверка синтаксиса `sudo sshd -t` (тишина = ошибок нет);
2. **не закрывать текущую сессию**, пока не вошёл в новой.

**Смена порта 22** — не защита, а способ уменьшить шум в логах: часть ботов стучится только в 22. Кто ищет именно твой сервер, найдёт и другой порт.

> В Ubuntu 24.04+ SSH запускается через сокет (`ssh.socket`), порт задаётся там: после правки `Port` нужны `systemctl daemon-reload` и `systemctl restart ssh.socket`.

## Шаг 5. Что слушает сервер и файрвол

Начинать не с файрвола, а с вопроса: **что вообще слушает сервер?**

```bash
sudo ss -tulpn
```

- `127.0.0.1:порт` — доступно только с самого сервера; `0.0.0.0:порт` — **на всех интерфейсах, в том числе из интернета**.
- Частая история: база или Redis для приложения на этом же сервере слушают `0.0.0.0` — «очень щедро». Сначала **поправить настройки программы** (слушать `127.0.0.1`), потом файрвол.

Файрвол — всё входящее запрещено, кроме явно разрешённого. В Ubuntu удобен **ufw** — обёртка над правилами ядра. **Порядок: запретить → разрешить SSH → включить**:

```bash
sudo ufw default deny incoming
sudo ufw allow 22/tcp           # или OpenSSH
sudo ufw allow 443/tcp
sudo ufw enable
```

Если включить раньше, чем разрешён SSH, — сессия оборвётся, чинить придётся через консоль провайдера.

- В облаке есть **группы безопасности** (security groups) — внешний файрвол, срабатывает до сервера. Закрыть лишнее и там: если кто-то выключит ufw, внешний останется.
- **Docker обходит ufw.** Контейнер с опубликованным портом доступен из интернета, хотя `ufw status` честно показывает, что всё закрыто: Docker пишет свои правила, и трафик к контейнерам идёт мимо цепочек ufw. Два выхода:
  1. публиковать только на localhost, если наружу всё равно отдаёт nginx: `docker run -p 127.0.0.1:8080:80 …`;
  2. ограничения — в цепочку **`DOCKER-USER`**, которую Docker оставляет для этого: `sudo iptables -I DOCKER-USER -i eth0 ! -s 192.0.2.10 -j DROP`.

## Шаг 6. fail2ban

Работает на логах из шага 1: считает неудачные входы с каждого адреса и при превышении **временно банит адрес в файрволе**. По умолчанию — **5 неудач за 10 минут → бан на 10 минут**.

```ini
# /etc/fail2ban/jail.local
[DEFAULT]
ignoreip = 127.0.0.1/8 ::1 198.51.100.0/24   # офис, VPN — никогда не банить

[sshd]
enabled  = true
port     = 22
backend  = systemd     # в Debian нет auth.log — читать журнал
maxretry = 5
findtime = 10m
bantime  = 10m
```

```bash
sudo fail2ban-client status sshd
sudo fail2ban-client set sshd unbanip 203.0.113.7    # если забанил сам себя
```

- Без `ignoreip` однажды пять раз ошибёшься в пароле и забанишь себя.
- Если вход по паролю уже выключен, fail2ban для SSH в основном **убирает шум и нагрузку**. По-настоящему полезен для сервисов, где пароль остался (почта, веб-панели) — для многих есть готовые правила.

## Шаг 7. Секреты на самом сервере

- Приватные ключи и файлы с паролями (`.env` и т. п.) — права **600**, а не 644 (644 читает любой пользователь сервера, даже тестовый). Проверка — `ls -l`, исправление — `chmod 600 файл`.
- **История команд:** `~/.bash_history` хранит пароль, набранный прямо в команде, открытым текстом. А пока команда работает, её аргументы видны всем через `ps`. Пароли передают **через файл с правами 600 или переменную окружения**, а не в аргументах.
- Не оставить команду в истории — **начать строку с пробела** (в Debian/Ubuntu `HISTCONTROL=ignoreboth` по умолчанию в `~/.bashrc`).

## Шаг 8. Логи — сразу на другую машину

Первое, что делает взломщик с правами root, — **чистит логи**. Это настолько стандартно, что в MITRE ATT&CK есть отдельная техника (T1070.002, очистка системных логов Linux). Поэтому логи должны **уезжать с сервера сразу**: что лежит на другой машине, с этого сервера не удалить. Второй довод практический: по десяти серверам с `journalctl | grep` никто ходить не будет.

**Grafana Loki** — один из самых популярных вариантов:

- на каждом сервере агент читает журнал и файлы логов и отправляет их в Loki, смотрят и ищут — в Grafana;
- агент сейчас — **Grafana Alloy**. **Promtail** — его предшественник, с **2 марта 2026** не поддерживается (EOL);
- отличие от ELK (Elasticsearch + Logstash + Kibana): ELK индексирует весь текст каждой строки (много памяти и диска), **Loki индексирует только метки** (сервер, сервис), а по тексту ищет перебором внутри выбранных меток — заметно дешевле, проще поднять на небольшом проекте.

Практические правила:

| Вопрос | Ответ |
| :--- | :--- |
| Что отправлять? | **Всё**: системный журнал, веб-сервер, приложение. Нужной обычно оказывается та строка, которую решил не отправлять |
| Сколько хранить? | С запасом: взлом замечают через недели и месяцы. Если логи живут 3 дня, вход взломщика из них уже исчез. Старое Loki складывает в дешёвое объектное хранилище (S3) |
| Права | Агент умеет **только отправлять**, но не удалять. Хранилище логов **не открывается ключами самого сервера** — иначе логи «просто ещё одна директория на том же сервере» |

## Шаг 9. Метрики и алерты

Логи отвечают «что произошло», но кто-то должен в них посмотреть — **алерты**.

- Метрики собирает **Prometheus**, на каждом сервере — **node_exporter** (процессор, память, диск, сеть).
- Метрики, которые выдают взлом:
  - **CPU 100 %**, когда посетителей нет — так выглядит майнер;
  - **резкий рост исходящего трафика** — спам или участие в DDoS;
  - **диск вдруг быстро заполняется**.
- На каждую — правило-алерт. Пример для процессора (в ролике словами: «простой → загрузка → больше 90 % дольше 15 минут»):

  ```yaml
  - alert: HighCPU
    expr: 100 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100 > 90
    for: 15m
  ```

- Алерты ставят и **на логи**: Loki выполняет запросы по расписанию. Три алерта, которые стоит завести на любом сервере:
  1. **успешный вход по SSH**;
  2. **создание нового пользователя**;
  3. **логи с сервера перестали приходить**.

  Набросок правил Loki (имена меток зависят от настройки Alloy):

  ```yaml
  - alert: SSHLogin
    expr: sum by (host) (count_over_time({unit="ssh.service"} |= "Accepted" [5m])) > 0
  - alert: NewUser
    expr: sum by (host) (count_over_time({job="journal"} |~ "useradd.*new user" [5m])) > 0
  - alert: LogsMissing
    expr: absent_over_time({host="srv1"}[15m])
  ```

- Всё уходит в **Alertmanager**, он шлёт туда, где увидят: корпоративный или обычный мессенджер, на худой конец почта. Главное — место, которое часто проверяют.

## Шаг 10. Алерт сработал: разбор взлома

Сценарий: ночь, CPU 100 % уже 20 минут, трафика нет. Логи уезжают в Loki, алерт настроен только на процессор.

1. **Ничего не перезагружать и не удалять.** Хочется убить процесс и спать, но вместе с ним пропадут следы: откуда запущен, от чьего имени, как попал.
2. **`top`** — какой процесс грузит процессор и **какой пользователь** его запустил.
3. **В Loki — всё по этому пользователю.** Картина: за сутки сотни `Failed password for test`, затем `Accepted password for test`. Пароль простой, вход по паролю не выключили, fail2ban не стоял.
4. **Где можно было поймать раньше:**
   - алерт на успешный вход сработал бы в момент входа — задолго до майнера;
   - ещё раньше: `Invalid user` — шум (имена, которых нет), а **сотни `Failed password` для существующего пользователя — прицельный подбор**: кто-то знает, что такой пользователь есть. Алерт на рост таких строк сработал бы до входа.
5. **Хронология:** вход → скачивание в `/tmp` (`wget`) → `chmod +x` и запуск → **crontab** для перезапуска майнера → **свой ключ в `authorized_keys`**, чтобы вернуться. Проверять crontab **всех** пользователей и **все** `authorized_keys` на сервере.
6. **Сервер считается скомпрометированным** — удалить майнер, crontab и ключ недостаточно, неизвестно, что ещё оставили:
   - **изолировать**, но не выключать: в облаке — группа безопасности, запрещающая всё, кроме твоего адреса;
   - **снимок диска** для глубокого разбора;
   - **пересобрать с нуля**;
   - **сменить все пароли, ключи и токены**, что на нём лежали, — даже те, «которые никто не видел»;
   - **закрыть найденную дыру на всех остальных серверах** (здесь — забытый пользователь и вход по паролю, то есть шаги 3–4).

> Взлом — неприятно, но нормально. Ненормально — **не знать**, что он произошёл. С логами и метриками есть хронология по минутам и спокойный разбор.

## Итог — чек-лист

1. Логи входов: `journalctl`, persistent-журнал, лимит, синхронизированные часы.
2. Автообновления безопасности + следить за перезапусками.
3. Свой пользователь, `sudo` по минимуму, лишние пользователи удалены.
4. SSH только по ключам, без root, `AllowUsers`; проверка через `sshd -T`.
5. Сервисы слушают `127.0.0.1`; файрвол «запрещено всё, кроме…»; помнить про Docker.
6. fail2ban с `ignoreip`.
7. Секреты — права 600, не в аргументах и не в истории.
8. Логи — сразу на другую машину, хранить долго, агенту — только запись.
9. Метрики и алерты: CPU, трафик, диск, вход по SSH, новый пользователь, пропажа логов.
10. При взломе: не трогать → хронология → изоляция, снимок, пересборка, смена всех секретов.

## Как это сделать на моих системах

Ролик показан на Debian/Ubuntu. Аналоги:

| Шаг | Gentoo (OpenRC) | Arch | Entware (ASUS RT-AX56U) |
| :--- | :--- | :--- | :--- |
| Логи входов | без systemd журнала нет: логи у syslog (`app-admin/sysklogd` / `app-admin/syslog-ng`) в `/var/log/messages` | `journalctl -u sshd` (служба `sshd`) | SSH роутера — dropbear прошивки, логи в *System Log* веб-интерфейса |
